Components

What each project is for, grouped as the source tree is. The pages before this one follow the jobs; this one follows the code, for the reader who has a project name and wants to know where it fits.

The hooks, the capture (APIDumper, APIDumperDLL, APIDumpLoader, APIDumpPrinter), the injection of a DLL (InjectionLauncher) and a plain replay are in API Interceptor, a submodule: see its components.

A project is one of three kinds. A library is linked into others. A DLL is loaded into a process, usually injected into the program that is being studied. A program is started by a person. The ones a person starts are the three tools of the analysis (APIDumpAnalysisExtractor, APIDumpAnalysisQuery, RecipeBake), StereoReplayPlayer, StereoReplayConsistencyChecker, StereoLauncher and VRPlayer. The rest is used by those.

Analysis

Turning a workload into a model and the model into a recipe. See Analysis & recipes.

APIDumpAnalysis

Library. The analysis itself and nothing that is of one API: the session that routes calls, the model builder, the keys and hashes, the tracking of how resources are used, the time series of the camera, the depth histograms, the .passes file (reader and writer), the queries. It is where an API is added to the analysis, by giving it a front end.

APIDumpAnalysisFrontends

Library. The front ends: for each API, what follows its state and says what its calls mean to the model. Direct3D 8 is the first. It is a library of its own because it needs D3D8Utils, which APIDumpAnalysis does not. The extractor, the replay engine and the live converter all use it.

APIDumpAnalysisExtractor

Program. Reads a workload and writes a .passes file.

APIDumpAnalysisQuery

Program. Asks a .passes file questions (info, timeline and the others) and prints the answers as JSON.

RecipeLoader

Library. Reads a recipe and checks it. It is what everything that only wants to read a recipe links: the replay player, the consistency checker, the launcher and the catalog.

RecipeApplier

Library. Applies a recipe: given a draw told by its signature and the view matrix, says whether to render it once, per eye, or not at all, and what its convergence distance is. The replay engine and the converter use it; neither needs to bake.

RecipeBake

Program. Reads a .passes file and the hand-written rules, and makes the recipe, including the convergence distances (the median depth by vertices) and the limits of the eye separation of each scene (from how near its surfaces are, and the comfort of the recipe). The baking is the class RecipeBaker, which is in the program because the program is its only user (the tests compile it too); the command line is CommandLine.

Replay

Executing a workload's calls again, without the program. See Replay.

StereoReplayEngineDLL

DLL, built for 32 and 64 bits. The replay engine. It walks the calls of a workload and hands each to the executor of its API (DirectDraw 7 and Direct3D 7, Direct3D 8, OpenGL, Win32 windows, or one that does nothing), found in a registry. It remaps the objects of the dump onto the live ones, restores the arguments a call needs, replays locks and client arrays, and paces the frames. It can execute a frame twice, which is what the recipe-driven stereo needs, binding the matrix of each eye. The executors are the parts that depend on an API.

StereoReplayPlayer

Program. A control window (ImGui, through UIHost) around the replay engine: choose a workload and optionally a recipe, play and pause. A 64-bit player starts the 32-bit one for a 32-bit workload.

StereoReplayConsistencyChecker

Program, without a window. Replays a workload several ways, hashes the images of each frame and compares the ways: that a replay is repeatable, and that a frame executed twice draws the same as once. It is the test that the replay engine is fit for stereo conversion, and it can write the images of a frame that differs.

Stereo

The live converter, and what carries its images to a screen. See Live stereo.

StereoCore

Library. The decisions of the conversion, without an API. The class StereoCore, which gives the library its name, decides the class of a draw from the recipe, the view matrix, and what to do with draws and frames the recipe does not know. ConvergenceModel says where the eyes converge and how far apart they are, MatrixSlots which matrices a rule is about and which to put in before a draw, and the resolution policy how much larger than the application asks to render. An API adapter asks it what to do and does it.

StereoConverterDLL

DLL, built for 32 and 64 bits, to match the application. The converter, injected into the program. Converter orders the work of each call; CallFeeder gives the analysis the calls as a dump would; the Direct3D 8 adapter renders the second eye (D3D8EyeRenderer), scales the resolution, forces windowed mode, and exports the frame into the channel's memory; FramePasser and SessionLog pass frames on and write the log.

StereoLauncher

Program. Starts a program with StereoConverterDLL injected, given a recipe, and reads the session log the converter writes.

StereoSession

Library. How the launcher hands a playback over to the converter in the application: through environment variables of the launcher, which the application inherits. Each playback has its own, so that several can run (SessionEnvironment, SessionInfo). It also says where the converter writes its log.

StereoTransport

Library. The channel between the converter and the presenter: a frame channel in shared memory, with a producer that writes the eyes of a frame and a consumer that takes the newest. The consumer also says what it accepts, how far to converge and how strong the 3D is. The exporter and importer are interfaces, so that the converter does not know what is on the other end.

StereoD3D12

Library. Puts the eyes of a frame from the memory of the channel into Direct3D 12 textures without a copy by the CPU. The presenter and the headset use it.

StereoXR

Library, 64-bit. The headset: a session of an OpenXR runtime that shows the eyes on a screen in the room, which can be flat or curved, sized to the view of the headset (screen_geometry); and the provider that lists the headsets of the machine.

StereoPresenter

Program, 64-bit. Takes the frames from the channel, whatever the bitness of the application, and shows them in a preview window or, with --headset, in a headset. It is started with the id of a session, which the VR player makes and also gives to the launcher; the VR player starts both.

VR player

The front end that chooses what to run and where to see it. See VR player.

VRPlayer

Program, 64-bit. A window that lists the applications of the catalog and the devices, starts the chosen application through the launcher and the presenter, and lets the user change the settings of a running session.

AppCatalog

Library. The list of applications that can be launched: for each, its executable, arguments, working directory and recipe, where it is downloaded from if it is not there, and the reason it is unavailable if it is. The name and description come from the recipe if the catalog does not give them.

AppInstaller

Library. Puts an application where it is played: HttpDownloader gets the zip file over https (WinHTTP, so the proxy and the certificates of the system), Sha256 checks it against the hash of the catalog, ZipExtractor unpacks it with miniz (and refuses a name which would put a file outside the directory), and AppInstaller does the three in a thread of its own, reports the progress, and moves the result into place whole, so that a cancel or a failure leaves nothing behind. It writes under the directory of the applications only.

VRDevices

Library. Where the list of devices comes from, behind an interface: a stub of made-up devices, and the provider of OpenXR runtimes in StereoXR.

UIHost

Library. A window drawn with ImGui over a Direct3D 11 device of its own: the device, the swap chain and the message loop. The control window of the player, the VR player and the presenter use it, so none of them repeats it.

Tests and third-party code

DemoVRPlayerTests

Program. The tests, with googletest, of every library above. The data files they use are reached through Tests::DataFixtures and the test doubles are in src/Tests/test_doubles.*; a few helpers of the tests of API Interceptor are used as they are. See Building.

deps

API Interceptor (with its own third-party code: Detours, Zstd, Dear ImGui, googletest and the Khronos headers of OpenGL) and the OpenXR SDK, for the headset, and miniz, for the zip files of the applications.
