Components

What each project is for, in the order of the source tree, which is the order of the release. The pages before this one follow the jobs; this one follows the code, for the reader who has a project name and wants to know where it fits.

The hooks, the capture (APIDumper, APIDumperDLL, APIDumpLoader, APIDumpPrinter), the injection of a DLL (InjectionLauncher) and a plain replay are in API Interceptor, a submodule: see its components.

The tree and the release

A project is one of three kinds. A library is linked into others. A DLL is loaded into a process, usually injected into the program that is being studied. A program is started by a person. The source tree is the release: a program has a folder in the folder its file is in, named after the file in snake_case without the prefix of the group (runtime/launcher for StereoLauncher, tools/stereo_replay/player for StereoReplayPlayer); the libraries are in one folder, src/libs, with the headers beside the sources. Every folder of the source is lower-case, with underscores; the namespaces are the same words in PascalCase.

Each folder of a program or a library has its own CMakeLists.txt, which says what it is made of and links; cmake/Install.cmake says where each program is installed, and a test (Layout) checks that this and the folders say the same. tools\api_dumper\ of the release is made of API Interceptor.

An include names the library, from src/libs (#include "analysis/api_dump_analysis/model.h"), or, for what a program takes of another program, the path from src (#include "tools/stereo_replay/engine_dll/types.h"). What a program includes of its own folder is named as it is ("command_line.h"). The namespaces of a library follow the path under src/libs, in PascalCase:Analysis::APIDumpAnalysis, Stereo::Core, Headset::XR, VRPlayer::AppCatalog, Utils::Images.

Libraries (src/libs)

Five, by what they are for. Each is a folder of parts, and a part is a namespace of the library.

Utils

Library. What knows nothing of this project and any of the others may use: it uses third-party code and the system only, and a test (Layout) checks that it includes nothing of the other libraries. Its parts:

BinaryIO

Bytes read and written as numbers, strings and blocks (ByteReader, ByteWriter), for the files of the analysis.

D3D12

A list of Direct3D 12 commands recorded, run by a queue and waited for (D3D12CommandRunner: the allocator, the list and the fence), and a texture filled with one colour (D3D12TextureClearer).

Files

A file from the network, checked and unpacked, and the file system under it: HttpDownloader gets a file over https (WinHTTP, so the proxy and the certificates of the system), Sha256 hashes it with the cryptography of the system, ZipExtractor unpacks it with miniz (and refuses a name which would put a file outside the directory), and FileSystem has what they share (names in UTF-8, directories). The downloader is behind an interface (IDownloader) so that what installs needs no network to be tested.

Hashing

Hasher: 64-bit digests of bytes and of values (xxHash, of the Zstandard that the interceptor has).

Images

Images as plain data: written as PNG files (compressed by miniz) or as a GIF, compared (how many pixels differ, where, by how much, and an image that shows it), and put together (two images as a red-cyan anaglyph or side by side, many as a contact sheet). The tools that look at frames use it, so that none has a writer of its own.

Json

A JSON reader and writer, and the reading of numbers (NumberParser), used by the recipes, the catalog and the query tools.

Parallel

ParallelFor: a range of items split over several threads.

Statistics

SeriesStats: count, mean and worst of a series of timings, as the presenter and the converter log them.

UIHost

A window drawn with ImGui over a Direct3D 11 device of its own: the device, the swap chain and the message loop. The control window of the replay player, the VR player and the presenter use it, so none of them repeats it.

Analysis

Library. Turning a workload into a model and the model into a recipe, and what the programs of tools/analysis and the replay and the converter use of them. See Analysis & recipes. It reads a workload through the loader of the interceptor. Its parts:

APIDumpAnalysis

The analysis itself and nothing that is of one API: the session that routes calls, the model builder, the keys and hashes, the tracking of how resources are used, the time series of the camera, the depth histograms, the .passes file (reader and writer), the queries. It is where an API is added to the analysis, by giving it a front end.

APIDumpAnalysis/frontends

The front ends: for each API, what follows its state and says what its calls mean to the model. Direct3D 8 is the first, and Direct3D 7 the second. The folder has a subfolder for each API (d3d7/, d3d8/), one for what the two share (shared/, and not common/, which a compiler on a case-insensitive disk takes for the Common/ of API Interceptor in an include), and AnalysisSession, which routes the calls to the front end of the API and so is above all three. The two share FixedFunctionFrontend, which follows the objects the program makes and the state of the fixed-function pipeline that does not depend on the API (transforms, lights, render states, textures, a release), and FixedFunctionState, which keeps that state; each API's own front end has the resources, the draws and the vertices. The namespace is Frontends for all of them: the folders sort the files, and the class names (D3D8Frontend) say the API. They need D3D8Utils and D3D7Utils of the interceptor. The extractor, the replay engine and the live converter all use them.

APIDumpDependencies

What each frame of a workload does with what the frames before it left in the resources: the AccessLog keeps the accesses that the model builder tells (IAccessSink), the DependencyAnalyzer works out the dependencies (one thread for each of several resources at a time), the .deps file keeps them (DepsFile, on the same sections as a .passes file), and the query commands answer about them. PerEyeCandidates is the one rule that says which resources each eye is to have a copy of. Nothing in it knows an API.

APIDumpSlicing

What the slicer is made of: the writer of a workload file (WorkloadWriter, which compresses with the writer of the dumper) and the cut of the first frames (HeadSlicer).

Recipe

What a recipe is, and the two things done with it that are not baking. types.h is the recipe as data (rules, draw selectors, convergence, the policy for unknown frames). RecipeLoader reads a recipe and checks it; it is what everything that only wants to read a recipe uses: the replay player, the consistency checker, the launcher and the catalog. RecipeApplier applies it: given a draw told by its signature and the view matrix, it says whether to render it once, per eye, or not at all, and what its convergence distance is; the replay engine and the converter use it, and neither needs to bake. The applier uses the types and not the loader, so a program which only reads a recipe does not need the applier's headers.

Stereo

Library. The decisions of the conversion and the images it makes. See Live stereo. Its parts:

Core

The decisions of the conversion, without an API. The class StereoCore decides the class of a draw from the recipe, the view matrix, and what to do with draws and frames the recipe does not know. ConvergenceModel says where the eyes converge and how far apart they are, MatrixSlots which matrices a rule is about and which to put in before a draw, and the resolution policy how much larger than the application asks to render. ScreenParallaxPlanner decides what is done to the vertices of a draw that are already in the space of the picture (moved by their depth, pushed as a whole, or left alone), for the replay engine and the live converter alike. An API adapter asks it what to do and does it.

D3D7

What is done to the vertices of a Direct3D 7 draw that are already in the space of the picture, for an eye: moved by their depth, or all by the same pixels. It works on the bytes of the vertices, so the replay engine (a dumped draw) and the live converter (an application that runs) share it.

Session

How the launcher hands a playback over to the converter in the application: through environment variables of the launcher, which the application inherits. Each playback has its own, so that several can run (SessionEnvironment, SessionInfo). It also says where the converter writes its log.

Transport

The channel between the converter and the presenter: a frame channel in shared memory, with a producer that writes the eyes of a frame and a consumer that takes the newest. The consumer also says what it accepts, how far to converge and how strong the 3D is. The exporter and importer are interfaces, so that the converter does not know what is on the other end.

Headset

Library. What shows the images in a headset. The OpenXR session is of the 64-bit programs. Its parts:

D3D12

Puts the eyes of a frame from the memory of the channel into Direct3D 12 textures without a copy by the CPU (D3D12FrameUploader), on the commands of a D3D12CommandRunner of Utils, which also fills the textures of a swap chain with black. The presenter and the headset use it.

XR

The headset: a session of an OpenXR runtime that shows the eyes on a screen in the room, which can be flat or curved, sized to the view of the headset (screen_geometry); and the provider that lists the headsets of the machine.

VRDevices

Where the list of devices comes from, behind an interface: a stub of made-up devices, and the provider of OpenXR runtimes in XR.

VRPlayer (libs/vr_player)

Library (the target is VRPlayerBackend, since VRPlayer is the program). What the VR player is made of, besides the headset and the window: the part of the player which does not draw. The namespace is VRPlayer, the same as the program's. See VR player. Its parts:

AppCatalog

The list of applications that can be launched: for each, its executable, arguments, working directory and recipe, where it is downloaded from if it is not there, and the reason it is unavailable if it is. The name and description come from the recipe if the catalog does not give them.

AppInstaller

Puts an application where it is played: AppInstaller gets the zip file over https, checks it against the hash of the catalog and unpacks it (with what Utils::Files has for the three) in a thread of its own, reports the progress, and moves the result into place whole, so that a cancel or a failure leaves nothing behind. It writes under the directory of the applications only.

runtime

What the VR player starts. The live converter, and what carries its images to a screen. See Live stereo. The converter and the launcher are built for x86 and for x64 (see build.bat), since the launcher has to be of the architecture of the application.

StereoConverterDLL

DLL, built for 32 and 64 bits, to match the application. The converter, injected into the program. Converter orders the work of each call; CallFeeder gives the analysis the calls as a dump would; the Direct3D 8 adapter (d3d8/) renders the second eye (D3D8EyeRenderer), scales the resolution, forces windowed mode, and exports the frame into the channel's memory, and the Direct3D 7 one (d3d7/) does the same with the surfaces and the draws of its API (D3D7EyeRenderer, D3D7SurfaceTwins); FramePasser and SessionLog, which both use, pass frames on and write the log.

StereoLauncher

Program. Starts a program with StereoConverterDLL injected, given a recipe, and reads the session log the converter writes.

StereoPresenter

Program, 64-bit. Takes the frames from the channel, whatever the bitness of the application, and shows them in a preview window or, with --headset, in a headset. It is started with the id of a session, which the VR player makes and also gives to the launcher; the VR player starts both.

tools/analysis

Turning a workload into a model and the model into a recipe. See Analysis & recipes. The library is Analysis.

APIDumpAnalysisExtractor

Program. Reads a workload and writes a .passes file.

APIDumpAnalysisQuery

Program. Asks a .passes file questions (info, timeline and the others) and prints the answers as JSON. It checks that the workload is the one the file is of (--workload says where it is, --no-verify skips the check).

APIDumpDependencyExtractor

Program. Reads a workload and writes a .deps file. It reads on several threads, and leaves out the data chunks above 64 KiB (vertices and pixels, which it does not look at): the 4 GB capture of a demo takes about 8 seconds.

APIDumpDependencyQuery

Program. Asks a .deps file questions (info, resources, resource, frame, carries, per-eye) and prints the answers as JSON. It checks that the workload is the one the file is of, as the query tool of the .passes file does.

APIDumpSlicer

Program. Writes the first frames of a workload, frames 0 to B, as a workload of its own: APIDumpSlicer in.workload slice.workload --frames B. The segments of the file which are wholly in the slice are copied as they are (they are Zstandard frames of their own, found by the index), and only the one that frame B ends in is decoded, cut after the call that ends the frame, and written again, so a slice replays to the same images as the workload up to that frame; StereoReplayConsistencyChecker --same-frames-as checks it. --strip-chunks-above N writes the big data chunks empty (they keep their numbers) for a slice that is only to be analysed. It is the first of the slices; one that leaves out what the frames of a range do not depend on needs the dependency analysis.

RecipeBake

Program. --check writes nothing: it says which kinds of frames (shapes) and which draw signatures of a workload the baked recipe does not know, with how many frames and where the first is, so that a recipe of another capture, or of a shorter one, is found out before a replay leaves those frames to the unknown-frame policy (exit code 5 if there are any). --overlays writes nothing either: it prints as JSON the draws that may be 2D overlays, by the recipe (a draw it leaves alone, as a replay asks by the keys of the draw and of its pass, and as a converter that plays the application as it runs asks by the signature over the cameras of its pass) and by the hint of the analysis (the camera of the pass never changes), with where the two disagree (OverlayCandidateFinder). Reads a .passes file (and, with --deps, the .deps file of the same workload, which says which textures each eye is to have a copy of) and the hand-written rules, and makes the recipe, including the convergence distances (the median depth by vertices) and the limits of the eye separation of each scene (from how near its surfaces are, and the comfort of the recipe). The baking is the class RecipeBaker, which is in the program because the program is its only user (the tests compile it too); the command line is CommandLine.

tools/stereo_replay

Executing a workload's calls again, without the program. See Replay. Each program has _x64 or _x86 in the name of its file, so that the 64-bit player finds the 32-bit one next to itself.

StereoReplayEngineDLL

DLL, built for 32 and 64 bits. The replay engine. It is the replay engine of the interceptor (its executors for DirectDraw 7 and Direct3D 7, Direct3D 8, OpenGL and the Win32 windows, the remapping of objects, locks and client arrays) with what stereo needs added: a frame executor that plays a frame twice and binds the matrix of each eye, one that paces the frames, and a Direct3D 7 executor that keeps a copy of some objects for each eye. Its public headers (i_playback_controller.h, types.h and the others) are in its folder, beside its sources. What is of Direct3D 7 only (the rewriting of the vertices of a draw for an eye, D3D7DrawRewriter) is in d3d7/.

StereoReplayPlayer

Program. A control window (ImGui, through UIHost) around the replay engine: choose a workload and optionally a recipe, play and pause. A 64-bit player starts the 32-bit one for a 32-bit workload.

StereoReplayConsistencyChecker

Program, without a window. Replays a workload several ways, hashes the images of each frame and compares the ways: that a replay is repeatable, and that a frame executed twice draws the same as once. It is the test that the replay engine is fit for stereo conversion, and it can write the images of a frame that differs. A file for each way of working: replay_runner replays a workload the ways it compares, comparison compares the ways (and one workload with another), screenshot_mode writes the image of a frame or a sheet of frames, profile_mode says where the time of a replay goes, and overlay_probe_mode makes the overlay probe; command_line reads and checks the options (it says what is wrong with them, and has tests, like the other programs), and main.cpp loads the recipe and chooses the way of working.

VRPlayer

The front end that chooses what to run and where to see it. See VR player.

VRPlayer

Program, 64-bit. A window that lists the applications of the catalog and the devices, starts the chosen application through the launcher and the presenter, and lets the user change the settings of a running session.

Tests and third-party code

DemoVRPlayerTests

Program. The tests, with googletest, of every library and program above. The data files they use are reached through Tests::DataFixtures and the fake DirectDraw is in src/tests/fake_direct_draw.h; a few helpers of the tests of API Interceptor (replay_test_doubles.h and others) are used as they are. They include a test of the layout of the source against the release, and one that the code is not written twice (known_duplicates.txt). See Building.

deps

API Interceptor (with its own third-party code: Detours, Zstd, Dear ImGui, googletest and the Khronos headers of OpenGL) and the OpenXR SDK, for the headset, and miniz, for the zip files of the applications.
