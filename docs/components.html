Naming

The source tree is the release. A program has a folder in the folder its file is in, named after the file in snake_case without the prefix of its group. The libraries are in one folder, src/libs, with the headers beside the sources. Every folder of the source is lower-case, with underscores; the namespaces are the same words in PascalCase.

Each folder of a program or a library has its own CMakeLists.txt, which says what it is made of and links. cmake/install.cmake says where each program is installed, and a test (Layout) checks that this and the folders say the same. tools\api_dumper\ of the release is made of API Interceptor.

Parallel in detail

ClassWhat it does
ParallelForSplits a range of items over several threads.
JobThreadA thread that does one queued job at a time. The owner queues a job (with a step that puts what the job needs in place, run with the lock taken), goes on, and waits for the job when it needs it (with a step that takes what the job made). try_queue hands a job over only if the thread is free, for an owner that leaves a frame out instead of waiting; the host memory exporters of Direct3D 8 (with two of them) and of OpenGL are built on it.
JobStateSays where the job is.
SrwMutexA mutex that works like std::mutex to the code that takes it and costs one atomic operation when nobody else has it, for the locks of callbacks that are taken very many times.

APIDumpAnalysis/frontends

For each API, what follows its state and says what its calls mean to the model. Direct3D 8, Direct3D 7 and OpenGL have one; all three are an IAPIFrontend.

FolderWhat is in it
D3D7/, D3D8/, OpenGL/The code of one API.
shared/What they share. It is not named common/, which a compiler on a case-insensitive disk takes for the common/ of API Interceptor in an include.

The namespace is Frontends for all of them: the folders sort the files, and the class names (D3D8Frontend) say the API. D3D8Frontend also has what an adapter needs without an instance: get_vertex_count() and is_pre_transformed_vertex_shader(). They need D3D8Utils and D3D7Utils of the interceptor. The extractor, the replay engine and the live converter all use the front ends.

PartWhat it doesUsed by

APIDumpAnalysisExtractor

Program. Reads a workload and writes a .passes file. The three extractors are each a main.cpp and an extractor.h with the step that is the program's own; the rest is ExtractorTool of Analysis, and the three query programs are the same on QueryTool.

APIDumpAnalysisQuery

Program. Asks a .passes file questions (info, timeline and the others) and prints the answers as JSON. It checks that the workload is the one the file is of (--workload says where it is, --no-verify skips the check).

APIDumpDependencyExtractor

Program. Reads a workload and writes a .deps file. It reads on several threads, and leaves out the data chunks above 64 KiB (vertices and pixels, which it does not look at).

APIDumpDependencyQuery

Program. Asks a .deps file questions (info, resources, resource, frame, carries, per-eye, slice) and prints the answers as JSON. It checks that the workload is the one the file is of, as the query tool of the .passes file does.

APIDumpSlicer

Program. Writes the first frames of a workload, frames 0 to B, as a workload of its own: APIDumpSlicer in.workload slice.workload --frames B.

  • The segments of the file which are wholly in the slice are copied as they are (they are Zstandard frames of their own, found by the index).
  • Only the segment that frame B ends in is decoded, cut after the call that ends the frame, and written again. A slice therefore replays to the same images as the workload up to that frame; StereoReplayConsistencyChecker --same-frames-as checks it.
  • --strip-chunks-above N writes the big data chunks empty (they keep their numbers) for a slice that is only to be analysed.

APIDumpTextureExtractor

Program. Reads a workload and writes a .textures file, and the file of blobs beside it (Analysis).

  • It reads every data chunk: the pixels of an upload are in them, so --skip-chunks-above is refused.
  • It reads the file back after writing it and ends with an error if it is not what was made.
  • --include-render-content ends the process with a message, since what rendering made is not in the workload and no program reads the textures back.

APIDumpTextureQuery

Program. Prints, as JSON, what a .textures file says.

CommandWhat it prints
infoThe events of each kind and where the contents are.
resources, resource <id>The levels of a texture and its events in the order of the calls.
at <frame> <resource> <level>Lays the writes to a level over each other up to the end of that frame (or --call) and prints the pieces that no later write covered, each with the event that made it and where its bytes are (a chunk of the workload, or the file of blobs; none for what rendering made), and the last snapshot point of the level. A level that was given a size and no pixels has no piece.

The options that every query program has (--compact, --limit, --offset, --no-verify, --workload) are read by QueryCommandLine, which the other two query programs use too; the loop over the arguments is ArgumentWalker in utils/command_line, which the extractors use as well.

RecipeBake

Program. Four modes; -o writes the baked recipe to another file instead of replacing the recipe.

ModeClassWhat it does
BakingRecipeBakerReads a .passes file (and, with --deps, the .deps file of the same workload, which says which textures each eye is to have a copy of) and the hand-written rules, and makes the recipe, including the convergence distances (the median depth by vertices) and the limits of the eye separation of each scene (from how near its surfaces are, and the comfort of the recipe).
--checkRecipeCheckerWrites nothing. Says which kinds of frames (shapes) and which draw signatures of a workload the baked recipe does not know, with how many frames and where the first is, so that a recipe of another capture, or of a shorter one, is found out before a replay leaves those frames to the unknown-frame policy (exit code 5 if there are any). It also says which passes the recipe leaves alone look like 3D scenes, and which draws a replay and the converter treat differently (exit code 6).
--overlaysOverlayCandidateFinder, DrawFactsWrites nothing either. Prints as JSON the draws that may be 2D overlays, with where the opinions disagree (below).
--scenesSceneReporterWrites nothing. Prints as JSON each scene (kind of frame) that has depth: where its frames are, where the eyes converge and how far apart they may be with the recipe as it is, and the parallax of its nearest and farthest surfaces as a part of the picture width and as an angle on a screen that is --screen-degrees wide, at the strength 1.

The overlay report

A draw is a candidate by two kinds of opinion, and the report says where they disagree.

OpinionWhat it is
By the recipeA draw it leaves alone, as a replay asks by the keys of the draw and of its pass, and as a converter that plays the application as it runs asks by the signature over the cameras of its pass.
By the hints of the analysisThe camera of the pass never changes, or the draw was drawn with an orthographic projection (the last column of the matrix is 0, 0, 0 and something, and the matrix is not the identity, which is what a program that sets none has). This is a part of what a draw structure is, so that the panels of a screen in the pass of a 3D scene are other draws than the scene is made of, whatever the state they share.

Each candidate also carries the facts the analysis kept of the draws of its structure in all their passes (DrawFacts, the FACT section of the .passes file, version 2):

  • the counters n_draws, n_blended_draws, n_draws_sampling_copied_color (a draw that works on the picture below it, whose content is already made for each eye), n_draws_after_3d_draw, n_draws_eye_space, n_draws_flat_layer and n_draws_with_footprint;
  • the smallest and the largest part of the picture that the box around the vertices covers (a structure that is a sprite in some draws and a backdrop in others differs);
  • the depth range of the vertices.

The reasons say it: samples_copied_picture, covers_view, covers_view_in_some_draws, blends_over_picture.

The baking is the class RecipeBaker, which is in the program because the program is its only user (the tests compile it too); the command line is CommandLine.

StereoReplayPlayer

Program. A control window (ImGui, through UI of Utils) around the replay engine: choose a workload and optionally a recipe, play, pause and seek. A 64-bit player starts the 32-bit one for a 32-bit workload.

Program, without a window. Replays a workload several ways, hashes the images of each frame and compares the ways: that a replay is repeatable, and that a frame executed twice draws the same as once. It is the test that the replay engine is fit for stereo conversion, and it can write the images of a frame that differs. There is a file for each way of working:
