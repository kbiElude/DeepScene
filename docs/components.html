Naming

The folders of the source are the folders of the release. A program has a folder in the folder of its group (runtime, tools/analysis, tools/stereo_replay), named after the program in snake_case without the prefix of its group. The libraries are in src/libs, with the headers beside the sources. Folders are lower-case with underscores, except the ones named after an API (D3D7, D3D8, OpenGL); the namespaces are the same words in PascalCase.

Each program and each library has its own CMakeLists.txt, which says what it is made of and links. cmake/install.cmake says where each program is installed, and a test (Layout) checks that this and the folders say the same.

Parallel in detail

ClassWhat it does
ParallelForSplits a range of items over several threads.
JobThreadA thread that does one queued job at a time. The owner queues a job, goes on, and waits for it when it needs the result. A step run with the lock taken puts what the job needs in place when it is queued, and another takes what it made when it is waited for. The host memory exporters of Direct3D 8 (two threads) and of OpenGL (one) are built on it.
JobThread::try_queue()Hands a job over only if the thread is free, for an owner that leaves a frame out instead of waiting. The OpenGL exporter uses it.
JobStateSays where the job of a JobThread is.
SrwMutexA mutex that works like std::mutex to the code that takes it and costs one atomic operation when nobody else has it, for the locks of callbacks that are taken very many times.

APIDumpAnalysis/frontends

For each API, what follows its state and says what its calls mean to the model. Direct3D 8, Direct3D 7 and OpenGL have one; all three are an IAPIFrontend.

FolderWhat is in it
D3D7/, D3D8/, OpenGL/The code of one API.
shared/What they share. It is not named common/, which a compiler on a case-insensitive disk takes for the common/ of API Interceptor in an include.
AnalysisSessionRoutes the calls to the front end of the API, and so is above all three.

The namespace is Frontends for all of them: the folders sort the files, and the class names (D3D8Frontend) say the API. The extractor, the replay engine and the live converter all use the front ends. They use D3D8Utils and D3D7Utils of the interceptor.

Session and Transport in detail

ClassPartWhat it does
SessionEnvironmentSessionHands a playback to the converter through environment variables of the launcher, which the application inherits. Each playback has its own, so several can run. It also says where the converter writes its log.
SessionInfoSessionWhat the converter reads of it: the recipe, the id of the session, and whether it logs everything or only why it stops.
FrameChannelTransportPasses images from the application to the program that shows them, through memory that both share (a 32-bit application can feed a 64-bit program). It has room for three images: the producer never waits, and the consumer never sees an image that is being written.
FrameChannel settingsTransportThe two sides say which kinds of transport they offer and accept. The consumer also gives how far to converge, how far apart the eyes are and how strong the 3D is.
IFrameExporterTransportThe producer's end, for one graphics API: takes the eye images that the application drew and gets them to the program that shows them.
IFrameImporterTransportThe consumer's end: makes the newest frame available until it is released.
HostMemoryImporterTransportThe importer for frames that the producer wrote in the memory of the channel.

The converter does not know what is on the other end of the interfaces.

APIDumpAnalysisQuery

Program. Asks a .passes file questions (info, timeline and the others) and prints the answers as JSON. It checks that the workload is the one the file is of (--workload says where it is, --no-verify skips the check).

APIDumpDependencyExtractor

Program. Reads a workload and writes a .deps file. It reads on several threads, and by default leaves out the data chunks above 64 KiB (vertices and pixels, which it does not look at; --skip-chunks-above 0 reads them all).

APIDumpDependencyQuery

Program. Asks a .deps file questions (info, resources, resource, frame, carries, per-eye, slice) and prints the answers as JSON. It checks that the workload is the one the file is of, as the query tool of the .passes file does.

APIDumpSlicer

Program. Writes the first frames of a workload, frames 0 to B, as a workload of its own: APIDumpSlicer in.workload slice.workload --frames B [--strip-chunks-above N] [--threads N]. --frames 0-B means the same.

  • The segments of the file which are wholly in the slice are copied as they are (they are Zstandard frames of their own, found by the index).
  • Only the segment that frame B ends in is decoded, cut after the call that ends the frame, and written again. A slice therefore replays to the same images as the workload up to that frame; StereoReplayInspector --same-frames-as checks it.
  • --strip-chunks-above N writes the big data chunks empty (they keep their numbers) for a slice that is only to be analysed.
  • --threads N is the number of threads that read the workload ahead (2 by default).

APIDumpTextureExtractor

Program. Reads a workload and writes a .textures file, and the file of blobs beside it (Analysis).

  • It reads every data chunk: the pixels of an upload are in them, so --skip-chunks-above is refused.
  • It reads the file back after writing it and ends with an error if it is not what was made.
  • --include-render-content ends the process with a message, since what rendering made is not in the workload and no program reads the textures back.

APIDumpTextureQuery

Program. Prints, as JSON, what a .textures file says.

CommandWhat it prints
infoThe events of each kind and where the contents are.
resources, resource <id>The levels of a texture and its events in the order of the calls.
at <frame> <resource> <level>Lays the writes to a level over each other up to the end of that frame (or --call) and prints the pieces that no later write covered, each with the event that made it and where its bytes are (a chunk of the workload, or the file of blobs; none for what rendering made), and the last snapshot point of the level. A level that was given a size and no pixels has no piece.

The options that every query program has (--compact, --limit, --offset, --no-verify, --workload) are read by QueryCommandLine, which all three query programs use; the loop over the arguments is ArgumentWalker in utils/command_line, which the extractors use as well. The texture query adds --call to at.

RecipeBake

Program. Five modes: baking, and four reports. -o writes the baked recipe to another file instead of replacing the recipe.

ModeClassWhat it does
BakingRecipeBakerReads a .passes file (and, with --deps, the .deps file of the same workload, which says which textures each eye is to have a copy of) and the hand-written rules, and makes the recipe.
It includes the convergence distances (the median depth by vertices) and the limits of the eye separation of each scene (from how near its surfaces are, and the comfort of the recipe).
--checkRecipeCheckerWrites nothing. Says which kinds of frames (shapes) and which draw signatures of a workload the baked recipe does not know, with how many frames and where the first is, so that a recipe of another capture, or of a shorter one, is found out before a replay leaves those frames to the unknown-frame policy (exit code 5 if there are any).
It also says which passes the recipe leaves alone look like 3D scenes, and which draws a replay and the converter treat differently (exit code 6).
--overlaysOverlayCandidateFinderWrites nothing either. Prints as JSON the draws that may be 2D overlays, with where the opinions disagree (below).
--parityParityAuditorWrites nothing. Compares what the replay and the live converter decide for each draw of the capture, by asking RecipeApplier::decide_draw() both ways (by pass and draw key, and by signature over each camera of the pass), for each size the draw was seen with, and lists the draws on which they differ (exit code 7).
--scenesSceneReporterWrites nothing. Prints as JSON each scene (kind of frame) that has depth: where its frames are, where the eyes converge and how far apart they may be with the recipe as it is, and the parallax of its nearest and farthest surfaces as a part of the picture width and as an angle on a screen that is --screen-degrees wide, at the strength 1.
(shared)PassCameraReaderReads the cameras that a pass was drawn with. --overlays and --parity use it.

Exit codes: 0 done, 1 bad arguments, 2 a file cannot be read, 3 the recipe cannot be baked, 4 the file cannot be written, 5 and 6 from --check, 7 from --parity.

The overlay report

A draw is a candidate by the opinion of the recipe or by a hint of the analysis, and the report says where they disagree.

OpinionWhat it is
By the recipeA draw it leaves alone, as a replay asks by the keys of the draw and of its pass, and as a converter that plays the application as it runs asks by the signature over the cameras of its pass.
By the camera of the passThe camera of the pass never changes.
By the projection of the drawThe draw was drawn with an orthographic projection: the last column of the matrix is 0, 0, 0 and something, and the matrix is not the identity, which is what a program that sets none has. This is part of what a draw structure is, so that the panels of a screen in the pass of a 3D scene are other draws than the scene is made of, whatever the state they share.

Each candidate also carries the facts the analysis kept of the draws of its structure in all their passes (DrawFacts, the FACT section of the .passes file, version 2):

  • the counters n_draws, n_blended_draws, n_draws_sampling_copied_color (a draw that works on the picture below it, whose content is already made for each eye), n_draws_after_3d_draw, n_draws_eye_space, n_draws_flat_layer and n_draws_with_footprint;
  • the smallest and the largest part of the picture that the box around the vertices covers (a structure that is a sprite in some draws and a backdrop in others differs);
  • the depth range of the vertices.

The reasons say it: samples_copied_picture, covers_view, covers_view_in_some_draws, blends_over_picture.

The baking is the class RecipeBaker, which is in the program because the program is its only user (the tests compile it too); the command line is CommandLine.
