Analysis & recipes

A workload says what a program did. The analysis says what it meant: which draws make the scene, which the interface, and how deep the scene is. A recipe keeps the answer in a form the live converter can follow.

What the analysis is for

The stereo conversion draws a scene twice, each eye a little to the side. For the result to look right, the converter has to know two things about every frame. The first is which draws are the 3D scene and which are the flat interface, which must not be shifted. The second is the convergence distance: the distance from the camera at which the pictures of the two eyes coincide. What is at that distance appears at the screen; nearer things stand out of it, and farther things lie behind it. A distance that does not suit the scene is uncomfortable to look at.

The convergence distance is a property of the scene, so the analysis measures it. For the draws of every pass it counts how far from the camera the things drawn are, and keeps the count as a depth histogram: a row of bins, each a range of distances, each holding the number of vertices drawn in that range. A histogram is made when a draw is counted (The depth of a draw), is kept with the kind of frame it was made in, and is read by the recipe baker, which takes the median as the convergence distance. A second histogram, of the surfaces that the draws draw, tells how near the nearest of them are, and the baker uses it to limit how far apart the eyes may be. The rest of this page follows the analysis in the order that things happen, and explains each word where it is first needed.

Pipeline

How the analysis is performed

Direct3D 8 is the first API, not the only one. The analysis is built to take more: everything about an API is in its front end, and everything after the front end (the model builder, the keys, the model, the .passes file, the queries, the recipes) does not know which API the calls were of. Direct3D 8 is used as the example throughout because it is the one that has a front end today; OpenGL is already hooked, dumped and replayed, and other APIs are to follow. One front end per API says what that means in practice.

The analysis reads a workload once, from start to end, and never holds the whole of it. Each call goes through three stages: the session routes it, the front end of its API follows the state of the device and turns the call into events about resources, passes and draws, and the model builder turns the events into the model. What is kept grows with the variety of what the application did, not with the length of the capture: a frame of a hundred thousand is a small record that points to its shape (the kind of frame it is).

1. Reading the workload

AnalysisSession::run() opens the file with WorkloadReader, which returns one segment at a time: a block of calls with the data chunks they refer to, the way the dumper cut it (see the capture page of API Interceptor). Only the segment in hand is in memory; the one before it is gone. After each segment a progress report is made, which the extractor prints every --progress-interval seconds. --max-frames stops the analysis after that many frames.

  • The session notes what identifies the workload: its file name, its size, and the hash of its first 4 KiB. A .passes file thereby says which workload it was made from.
  • It notes the pointer size and the clock frequency of the dumped process, which the segments carry.
  • If the file ends in the middle of a segment (the application was killed), the complete part is analysed and the summary says the workload was truncated.

2. Routing a call

For each call process_call():

  1. takes the API group of the call (D3D8, OpenGL, GDI32 and so on), and counts the call under it;
  2. tells the model builder which call this is (begin_call), so that everything reported from now on can be traced to its index and time;
  3. hands the call to the front end of the group, or counts it as ignored if the group has none;
  4. notes whether the call ended a frame. The call that ends a frame (the present) belongs to that frame; calls after the last present are trailing and are in no frame.

The summary that comes out holds the totals: calls, calls by group, calls ignored, unfollowed (a call of an object the front end does not know, or whose arguments could not be read), unsupported (see below), trailing, segments, and the resolution hazards found (calls whose meaning depends on the size of the target in pixels; see section 4).

3. One front end per API

A front end follows the state of one API, and reports what its calls come to, with everything resolved: a draw is reported with the resources it uses, not with the calls that bound them. It is the only part of the analysis that knows what a function of the API is called, what its arguments mean, or what state the device has. The session picks the front end by the API group of the call; a group with no front end is counted as ignored.

The contract is small. A front end implements IAPIFrontend::on_call(call, workload), keeps whatever state its API has, and reports to the model builder through a fixed set of events:

EventMeaning
on_create_resource, on_destroy_resourceA resource appears or goes, with its description.
on_set_attachments, on_set_viewportWhat is rendered to, and where.
on_update_constantA constant takes a value, with a meaning if the front end knows one.
on_clear, on_copy, on_uploadWork that touches a resource but is not a draw.
on_drawA draw, described with every resource and piece of state it uses.
on_frame_presentedThe frame ends.

What a front end must not do is let its API show through. The shared vocabulary is chosen so that more than one API can say what it means in it:

  • A binding point is where a resource is bound, in three numbers (a stage or texture unit; a set, a binding and an array element; a register space, a register and an array element). Whatever the API has not got is 0.
  • A constant location is a range of bytes in a block of one of four kinds: a buffer, the loose constants of a shader or program (constant registers, the default uniform block), the state of a fixed-function pipeline (transforms, lights, materials), or push constants.
  • A resource is a buffer (index or vertex), a shader, a swap chain image, or a 2D, 3D or cube texture, with extents, mip and layer counts, a sample count and a format class (colour, compressed, depth, depth-stencil). The raw format value is meaningful only to the front end that wrote it.
  • Shader stages include compute, geometry and tessellation, and a draw has a list of shaders (empty for the fixed-function pipeline), which Direct3D 8 does not need but later APIs will.
  • A resolution hazard is a category (clears with rectangles, point sizes, screen-space vertices, ...). What it takes to recognize one in a call is the front end's.

Some of this room is not used yet: no front end today produces compute shaders or push constants. It is there so that adding an API does not mean changing the model.

Nothing after the front end changes: the model builder, keys, model, file format and the query tool are the same for every API. A draw signature (see section 6) means the same kind of thing in every API: what a draw is when it is issued, told by the resources it uses. A process can use more than one API, and the keys of their front ends can then be in one file.

Where things stand: Direct3D 8 has every piece above. DirectDraw 7 and Direct3D 7 have the hooks, the printer names and an analysis front end, and a replay executor, but no converter adapter. OpenGL and the Win32 window calls (GDI32, User32, WGL) have the hooks, the printer names and the replay executors, but no analysis front end and no converter adapter. Recipe rules name the functions they apply to, and the functions a rule can name today are the SetTransform of Direct3D 8 and of Direct3D 7 (the replay and the converter play only the first); the key scheme and the baked section do not depend on the API.

4. The Direct3D 8 front end

The first front end, and the one every example here is of. Its parts are specific to Direct3D 8, which is why its names are all D3D8*.

The model builder never sees a D3D8 call, which is why it is API-neutral. The D3D8 front end has these parts:

PartJob
CallViewReads the typed arguments of a call and its data chunks; knows whether the call succeeded. A call that failed changes nothing.
ObjectTrackerThe objects that are alive, by address, and what each is in the model: a resource, or a part of one (the surface of a mip level of a texture). An address is forgotten when its object is released, so an object made at the same address later is not taken for the old one.
D3D8PipelineStateWhat the device has bound and set that a draw depends on: buffers, textures, shaders or the vertex format, render states, texture stage states and lights. It produces the state key and the vertex layout key of each draw.
D3D8ResourceDescriberTurns the arguments of a Create* call into a description of the resource: its kind, extents, format class (colour, compressed, depth, depth-stencil), and the flags worth telling resources apart by.
ObjectNamerGives each resource a debug name, for the people who read the output.

What the calls come to:

CallsWhat is reported

CreateTexture, CreateVertexBuffer, CreateRenderTarget, CreateVertexShader and the other Create*A resource is created, with its description. A shader's description holds the hash of its code.
Release down to zero, DeleteVertexShader, DeletePixelShaderThe resource is destroyed.
GetBackBuffer, GetSurfaceLevel, GetCubeMapSurface, GetRenderTarget, GetDepthStencilSurfaceNothing is reported; the surface that comes back is entered in the tracker as a part of its resource.

CopyRects, UpdateTextureA copy from a resource to another.

DrawPrimitive, DrawIndexedPrimitive and the UP variantsA draw, described from the pipeline state: topology, vertex count, buffers, textures, shaders, whether it reads colour or depth.

Three counters tell how far the front end can be trusted. Unfollowed calls had an unknown object or unreadable arguments. Unsupported calls are of things it does not follow at all: state blocks, patches, additional swap chains, MultiplyTransform, volume unlocks; passes and draws made with them are not right. Resolution hazards are calls whose meaning depends on the size of the target in pixels (clears and copies of rectangles, point sizes, vertices in screen space, shader creation, size queries); they say whether the application can be made to render larger without it noticing. The same classifier (D3D8ResolutionHazards) is used by the live converter, so that both say the same.

DirectDraw 7 and Direct3D 7 have a front end of their own (D3D7Frontend), which shares the call view, the object tracker, the namer and the state of the fixed-function pipeline (FixedFunctionState, which makes the state key from the rules an API gives it) with this one. What differs is what a resource is:

CallsWhat is reported
CreateSurface, DuplicateSurfaceA resource. The primary surface is a swap chain image the size of the screen (SetDisplayMode); a surface with the depth buffer caps is a depth resource; the rest are 2D textures, render targets if they are made for a 3D device.
GetAttachedSurfaceFor the back buffer of a chain, a resource made like the primary surface. For the next mip level of a texture, a part of the texture. Surfaces the tracker knows already are left alone.
AddAttachedSurfaceA depth buffer attached to a surface is the one rendered with when the surface is rendered to.
CreateDevice, SetRenderTargetThe target becomes the surface, with the depth buffer that is attached to it, and the viewport is the whole of it.
Blt, BltFast, LoadA copy; or an upload with no data of the workload if there is no source (a fill with a colour or a depth).
Unlock of a surface or a vertex bufferAn upload of the data the application wrote.
DrawPrimitive, DrawIndexedPrimitive and their strided and vertex buffer formsA draw. The vertex layout key is the vertex format code; the vertices are in the application's memory unless a vertex buffer is given.
Flip, and a Blt to the primary surfaceThe frame ends.

State blocks, MultiplyTransform, ProcessVertices and the GDI device contexts of surfaces (GetDC, ReleaseDC) are counted as unsupported. The geometry of a draw is sampled (D3D7GeometryTracker) from the vertices the dumper stored with the call, from the arrays of a strided draw, or from what was unlocked into a vertex buffer; pre-transformed vertices (XYZRHW), whose positions are in pixels, are not sampled.

5. Passes and draws

The model builder works with passes. It starts a pass with the first draw or clear after the previous pass ended. A pass ends when:

  • what is rendered to changes;
  • a clear or a viewport change comes after a draw;
  • a copy or an upload touches what the pass renders to (the pass must be done for the copy to see the result);
  • the frame ends.

A buffer written between two draws does not end a pass. Rendering to the same target in two scenes, one after the other, is two passes.

When a pass ends, complete_pass() makes its pass structure: where it renders to (the keys of its colour and depth views) and how (clears, viewport), the kinds of draws it holds (sorted, each once), and the constants in effect (sorted). A structure that was seen before is not stored again: the StructureInterner keeps one copy of each, numbers it, and the model refers to it by the number. A pass instance, the occurrence of a pass in a frame, is a small record: its calls, its draw count, its structure number.

A draw is described by the front end with what the API has resolved by then, and the builder makes two things of it. The draw structure says what the draw is: the keys of its index buffer, vertex buffers, shaders and textures (with where each is bound), its state key, vertex layout key and topology, with the counts left out. It is stored once for every kind of draw. The draw signature says what the draw is at the moment it is issued, which is what a live converter can know (see below).

The depth of a draw

When a draw is made, the builder also works out how deep it is, and counts it into the depth histogram of the open pass.

  • Depth is the distance from the camera, along the way the camera looks. It is taken for the origin of the object: the translation of its model matrix (the identity, if none was set), through the view matrix. It is worked out only if the pass has a view matrix and a perspective projection; an orthographic projection shrinks nothing that is far, so there is no depth to converge at.
  • Weight is the vertex count of the draw, so that a large object counts for more than a particle.
  • Bins are on a logarithmic scale, eight to each doubling of the distance, from 1/128 to 217 in the units of the camera (192 bins), since depth is felt in proportion to itself. A draw behind the camera or nearer than the first bin is not counted; one beyond the last goes in the last.
  • A histogram can tell the depth below which a fraction of its weight is. The recipe baker asks for one half, the median.
  • Covering the view: while the vertices of a draw are carried to the picture, the draw is said to cover the view if they reach all four edges (within half a percent of them, whether in view or beyond). A signature is not enough to tell them: a flash and a text are drawn through one dynamic buffer with one state, so they have the same signature. The key is the signature and the size of the draw (the number of its vertices or indices, and its topology), which the converter knows from the call; a key is kept (covering_draw_key_map, by the pass structure the draw was in) if any draw with it that was looked at covers the view (a quad that wipes in is the whole picture only for a time, and is not to be moved for the times that it is), and baked into the recipe as covering_draws, from the passes that the recipe leaves alone only, since the mesh of a scene can have the key of a quad of an overlay; the converter does not push a draw that has one of them (see the overlay in Recipe format). A key is not proof, though: two pieces of a sky dome can be drawn as quads of the same size as a flash, so the converter also looks at the vertices that the draw itself uses, and leaves a draw alone only if they reach both sides of the view (a piece of the sky that was left alone while its neighbour moved left a crack in one eye).
  • Surface depth is the same measure for the vertices of the draw, not the origin of its object. The origin of a large mesh can be far away, or behind the camera, while its walls are close: a tunnel built of a few large polygons around the camera is a scene whose objects all have their origins elsewhere. So the front end also follows what is written to vertex and index buffers (the data of each unlock, at the offset of its lock), and for a draw looks at up to 64 of its vertices, spread over it. Each is carried to the space of the camera (model matrix, then view matrix) and counted, with the weight of the draw shared among them, if it is in front of the near plane of the projection and inside the view. Only the positions of vertices that have one in the space of the model are read (XYZ, and XYZ with blend weights); pre-transformed vertices and those of a vertex shader are not sampled. This is done only by the analysis of a workload, which has the time: the converter inside an application is built without history, keeps no buffers, and never reads a vertex.

The histogram of the open pass stays with it. When the frame ends, it is added to the one of the same pass structure in the same kind of frame (section 7), so that a pass of one scene is not mixed with the same pass in another. A pass with nothing in front of the camera has none (it can still have a surface histogram, if its surfaces are in front of the camera and the origins of its objects are not). The surface histograms are kept the same way, per shape and pass structure. The baker later takes the median, by vertices, for each draw signature that the affected passes draw (the convergence of the recipe), and for each frame shape (scene_convergence).

6. How things are recognized again: keys

Addresses, creation order and times differ from run to run, and several threads can change the order of the creation calls. Everything the analysis stores as an identity is therefore a key: a 64-bit digest of the values that make the thing what it is, which comes out the same in another run. The rule for what is hashed is in Hasher (integers little-endian, floats by their bits, sizes with what has a variable size) and must never change, since keys are written into .passes files and recipes.

  • Description key: of everything that makes a resource what it is when it is created (kind, format, extents, flags, and the hash of the contents if it starts with immutable ones). Not its name, address or ID.
  • Resource key (ResourceKeyTable): the description key, plus the key of the pass that wrote to the resource earlier in this frame. When a pass ends, its targets are recorded as written by it. The table is reset at each frame, so the keys of a frame do not depend on the frames before.
  • Unwritten key: the key a resource would have if no pass of the frame had written to it. A pass that clears its target does not depend on what was there, so the key of its views is the unwritten one.
  • Draw signature key: a draw as it can be recognized when it is issued. The pass a draw belongs to is not known until the pass ends, so the signature uses the unwritten keys of the structure and the targets. This is the key a live converter can match, and what a recipe's rules are about.
  • Frame shape key: the key of the set of the pass keys of the frame. Order is ignored, since independent passes may run in any order.

Two different structures with the same key are possible in principle. They are counted (key collisions, in the summary of a query) and the structures are compared when interned, so a shared key does no harm besides the count.

7. Frames, shapes and representative frames

A present ends the frame. The builder then:

  1. ends the open pass;
  2. makes the frame's shape (the sorted numbers of its pass structures) and its key, and interns the shape, so that a frame becomes a small frame record: when it began and ended, the calls it spans, its draw and pass counts, and the number of its shape;
  3. adds the depth histogram of each pass to the one of the same pass structure in the same shape of frame (the depth of a draw), kept in the model per (shape, pass structure);
  4. closes the books on resource access (next section);
  5. keeps the detail of the frame (the instance of each pass, and the copies and uploads between them) only if it is a representative frame of its shape: the first frame of the shape, then the lightest and the heaviest by their draw count, if those are other frames;
  6. starts the next frame: the key table forgets who wrote to what, and the resources that were destroyed during the frame are forgotten.

A capture of a demo has hundreds of thousands of frames of a few dozen shapes, so the detail of three frames per shape is what the model can afford, and what a person needs to understand a shape.

8. What else is recorded

  • Resource access (ResourceAccessTracker). For each resource: the first read, the first and last write, and in how many frames it was read, written, and loop carried (read before it was written in the frame, and written in it, which is what feedback effects do). From these it is classed as loop carried, unused (never read or written), unread (written, never read), static (never written, or last written no later than it was first read; made once and read afterwards) or frame local (everything else). This tells what a replay must carry from one frame to the next.
  • Camera constants. A constant is tracked only if the front end gave it a meaning (the matrices of SetTransform). The constants in effect when a pass ends are part of its structure, by what they are, not their values. The camera ones (view, projection and their products) are also recorded as a time series per pass structure: a sample is stored only when the value changes, with the number of updates.
  • Depth histograms are made with the draws (the depth of a draw); the model keeps one for each shape of frame and pass structure, and the DEPT section stores them.
  • The timeline (TimelineBuilder, built when a query asks): the frames in time order as runs of one shape and their speed, how often each shape and pass structure occurs, and the setup frames, which are much longer than a typical frame.

9. Writing and reading the result

The model, the summary and the workload reference make an AnalysisResult, which PassesFile writes. Each section is serialized in a thread of its own and compressed with Zstandard (level 19); its header carries the size, the tag, the version and an XXH64 hash of the raw bytes. The file is written beside the real one (name.passes.tmp) and takes its place when it is complete, so a failure leaves the old file as it was. A reader skips sections it does not know; a known section of another version is an error.

Reading checks what a file that this code wrote must satisfy: sizes that fit before anything is allocated for them, resource IDs consecutive from 1, a resource that is part of one made before it, structures in order and without repeats, frame shapes that refer to passes that exist. A file that fails is refused. The format of the sections is described in passes_format.h:

TagSection
METAThe workload, the clock, the call totals, the hazards found and the key collisions.
RSRCThe resources: created, destroyed, described, keyed, and the resource each is a part of.
DRAWThe draw structures, by key.
PASSThe pass structures, numbered.
SHPEThe frame shapes, numbered.
FRAMOne small record per frame.
RACCThe access totals of each resource.
REPRThe representative frames of each shape, with their detail.
SERIThe time series of the camera constants.
DEPTThe depth histograms, by shape and pass structure.
COVRThe keys (signature and size) of the draws that cover the whole of the view (a flash, a fade): see the depth of a draw. A file made before it existed has none, and is made again.
SURFThe same, for the surfaces that the draws draw (vertices, not the origins of objects). A file made before it existed has none, and is made again.

Workload data (textures, vertices) is not stored: the file holds chunk IDs that point into the workload. The vertices are read while the file is made, and only the histograms of what they say are kept.

10. The same analysis, live

The converter inside the application runs the same AnalysisSession, fed by CallFeeder with the calls as they are made, and built without history: no frame records, no representative detail, no camera series. What it keeps grows only with the kinds of frames, passes and draws and with the resources created. The two things it needs are available as the application runs: the draw signature of each draw, at the moment the draw is issued, which it matches against the recipe; and the shape key of each frame, when the present is made, from which it eases toward the scene's convergence distance. Because the same code makes the keys, a rule baked from a workload matches a draw of the running program. The converter's way of getting the calls to the session (CallFeeder and the lists of the calls it follows) is part of the Direct3D 8 adapter, as is everything named D3D8* there; StereoCore and the rest do not know the API.

11. What it does not do

  • Only Direct3D 8 has a front end so far. Calls of an API that has none (OpenGL, GDI32 and the others today) are counted and skipped, and the analysis says how many. A capture of an OpenGL program gives an empty model until its front end exists.
  • The unsupported calls above are not followed; a capture that uses them gives passes and draws that are not right, and the summary says how many calls there were.
  • It never reads pixels. Contents appear only as the hash that goes into a resource's description key. Vertices it does read, while the file is made, for the surface depth (the depth of a draw); only a few dozen positions per draw, and only histograms are kept.
  • It does not judge. Which passes are an interface and which a scene is for the recipe (by rules, or by the person who writes them), with the analysis giving the facts: what each pass reads and writes, how deep it is, how often it occurs.

To look at a result, run APIDumpAnalysisExtractor file.workload -o file.passes (the 64-bit build; it reads the workload on several threads, --threads N sets how many, and the 4 GB capture of a demo takes about 40 s) and then APIDumpAnalysisQuery file.passes <command> (info, timeline, pipelines, resources, pass, frame, depth, overlays: the passes whose camera never changes, and under draws each draw signature of them, with the pass, the frames it is in, the first of them, and why it is a candidate; each says how deep the vertices of its pass are (depth: near, median, far, and whether they are flat): a pass whose vertices are at one depth is likely an overlay, one whose vertices are at many depths is a 3D scene seen from one place, and is left out of the unaffected list that the command offers for a recipe. Kasparov has 198 passes of a camera that never changes, since all it draws is pre-transformed, and only 50 of them are flat). Its output is JSON, with keys as hex strings. A .passes file remembers which workload it is of (its size and hashes of 4 KiB from its start, middle and end; see WorkloadIdentity), and the query tool checks the workload against it, so that a file cannot be asked about the wrong capture: a different workload is refused (exit code 4), a workload which cannot be found only gives a warning, --workload PATH says where it is if it was moved, and --no-verify skips the check. For the small sample capture in the tests the extractor reports 16836 calls, 10 frames, 4 frame shapes, 13 pass structures in a fraction of a second.

The model

Two kinds of 64-bit digest are used, and they are not interchangeable. A hash is the digest of bytes (the contents of a resource, the code of a shader, the start of a file). A key is the identity of a structure (a pass, a draw, a resource's description), made from the values that define it by KeyBuilder; a key can contain hashes. Both are made with Hasher, and what it does with a value never changes, since keys are stored in .passes files and recipes.

The vocabulary is API-neutral on purpose: a binding point is where a resource is bound, a constant location is where a shader constant lives. Nothing in the analysis assumes fixed-function D3D8 terms, so other APIs can feed it.

  • Draw signature: a key, the digest of the state a draw is made with (KeyBuilder::compute_draw_signature_key). The live converter and the offline analysis compute it the same way, so a rule baked offline matches a draw in the running program.
  • Pass: draws that render into the same targets in one go. Frame shape: the kinds of passes a frame is made of (order ignored), as a key.
  • Depth histogram: how deep the draws of a pass are, as a histogram weighted by vertices (the depth of a draw). The recipe's convergence distances are taken from it. The surface depth histogram is the same for the vertices of the draws, and gives the limits of the eye separation.

Recipe

The complete file format is in Recipe format.

Dependencies between frames

The analysis above says what the passes of a frame are. It does not say how the frames depend on each other, which a stereo replay needs: a frame played once for each eye reads, among other things, what the frame before it left in the resources, and that is not the same for both eyes if the frame before rendered it. The dependencies are made apart, by a pass of their own over the workload, and kept in a .deps file, so that nobody waits for the workload to be read again to ask about them.

The model builder tells every use of a resource to a sink (IAccessSink, AccessEvent): what it is used as (sampled, color or depth attachment, clear target, copy, upload, vertex and index input, shader code), whether it is read, written or both (a draw that blends reads what it writes), how much of it a write reaches (all of it, part of it, or not told), which part (mip levels and layers) and on which queue. The last two are empty for Direct3D 7 and 8, and are there for the APIs to come. The front ends only translate their calls into these events, so that a front end for another API makes the dependencies without the analysis knowing it.

From them, for each resource and each frame, the DependencyAnalyzer says whether the frame uses what an earlier frame left in it: certainly (something reads it, or blends into it, or tests against it, before anything has replaced all of it), possibly (only part of it was written before it is read, or how much is not known: a draw is not known to reach all of a target), or not at all. It names the frame which wrote what a frame uses, and sorts the resource as carried over, carried possibly, frame local, static or unused. It can only over-report what is carried, never under-report it.

A resource needs a copy for each eye when it is rendered to and some frame uses what an earlier frame left in it, whether that frame writes it too or not: two targets that frames render to by turns, each reading the other, are both carried, and neither is written and read by the same frame (which the totals of the .passes file, that a resource is read before it is written in a frame that also writes it, do not see). RecipeBake --deps bakes them into the recipe.

Targets that the frames write by turns are a rotation group: two or more resources of one description (and so of one key), each written in more than one frame, never by two writes in a row. A double buffer made by hand is one, and so are the images of a swap chain that the application takes in the order the API hands them out, which need not repeat. A group is one thing for the eyes: if the frames use earlier content of one of its resources, all of them are listed, so that an eye never finds what another eye's frame rendered in the one whose turn it comes to. APIDumpDependencyQuery per-eye says for each candidate which group it is in (and whether it is there only because of the group), and lists the groups with the order that the frames take them in: cycle (each resource once, then the same order again) or irregular. A resource is named by its description and its ordinal, never by its place in the order, which differs from run to run.

A .deps file knows the workload it is of (its size, and hashes of 4 KiB from its start, its middle and its end), and the query tool refuses another. It is written by APIDumpDependencyExtractor, which reads the workload on several threads and leaves out the vertices and pixels.
