Adding an app

How to take a 2D program from nothing to a recipe that turns it into stereo 3D, and to a line in the catalog of the VR player. The facts about the program are read from its analysis by an LLM; a person decides, and looks at the pictures.

The converter handles Direct3D 8 programs whose camera is set with SetTransform, Direct3D 7 programs whose vertices are already in pixels, and OpenGL programs of the fixed function (see What this does not cover). The steps are the same for each of them; only what the rules can name changes (step 4). For another API they are the same once it has its front end and its converter adapter (Adding an API). The catalog has one program of each of the three APIs.
The commands are written from the folder of a release (build_final): the programs are in tools\api_dumper, tools\analysis and tools\stereo_replay (see The collected build). my_demo and app.exe stand for the program being added.

The steps

Eight steps, each ending in a file or a decision that the next step reads.

1. Capture the program

tools\api_dumper\APIDumper_x86.exe --dump-n-frames 3000 --dump-swapchain-on-present c:\path\to\app.exe [app arguments]

Result: result_dump.workload, a recording of every API call and of the back buffer of each frame.

The options

Option or fileEffect
APIDumper_x86.exe / APIDumper_x64.exeThe dumper for a 32-bit or a 64-bit program.
--dump-n-frames NThe workload is written when N frames are reached, or when the program exits.
--dump-swapchain-on-presentStores the back buffer of each frame, which is what lets anyone later see what a frame looked like.
--spill-threshold-mbKeeps a 32-bit program from running out of memory while the workload is written. A capture can be large: a few minutes of a demo are gigabytes.
result_dump.workloadThe output, written in the working directory of the program.

What to capture

What is captured decides what the recipe knows. The analysis groups frames into shapes (the kinds of passes a frame is made of), and a recipe knows only the shapes it saw; any other frame is treated as the recipe says (on_unknown_frame, mono by default).

So one capture should walk through every kind of screen the program has: the loader, the menu, each scene, the transitions. Play it the way a user would, once.

2. Extract the passes

tools\analysis\APIDumpAnalysisExtractor_x64 result_dump.workload -o app.passes --stats
tools\analysis\APIDumpDependencyExtractor_x64 result_dump.workload -o app.deps --stats

Result: app.passes (the passes and frame shapes) and app.deps (which frames and textures each frame needs).

What the two files are for

FileUsed by
app.passesThe query tool (step 3) and the baker (step 5). A file whose section version is not the reader's is refused: analyse the workload again.
app.depsThe baker (--deps), to know which textures need a copy for the second eye; the replay tools, to seek faster.

Both extractors read the workload with several threads (--threads), and --max-frames stops at a frame.

One script for steps 2, 5 and a check

scripts\analyze_capture.ps1 -Workload result_dump.workload -Recipe recipe.json -OutDir folder [-MaxFrames N] [-ToolsDir dir] runs this step, the bake of step 5 and RecipeBake --check on the result. It writes <name>.passes, <name>.deps, <name>.baked.json and a log of each tool into folder, which must not be the folder of the recipe; the recipe is only read. To use the baked recipe, copy it over by hand.

Is the capture good?

Before going on, look at the summary the extractor prints, or at APIDumpAnalysisQuery app.passes info.

FieldGood valueIf it is not
n_unfollowed_calls0The analysis could not make sense of a call (its arguments were not as expected). The passes found may be wrong; the cause is a bug or a gap in the front end, not something a recipe can fix.
n_unsupported_calls0The program calls an API that the front end does not know. Same consequence as above.
key_collisions0Two different structures with the same key would be taken for one.
n_resolution_hazardsempty, or understoodA hazard is a call whose meaning depends on the size of the target in pixels, so rendering larger than the program asks would break it (see One translator per API).
frame_shapesa small numberHundreds of shapes mean that something that varies from frame to frame (a particle pass, a loading bar) is cutting the frames up. Understand that before writing any rule.

3. Investigate with an LLM

The question is the one the analysis deliberately does not answer (What it does not do): which passes of this program are the 3D scene, and which are an interface that must not be shifted? The analysis gives the facts; deciding is the work of whoever reads them.

Result: for every kind of pass, a decision (scene, interface or unclear) with the facts that support it.

Why an LLM can do this reading

The tools are built around three properties.

  • APIDumpAnalysisQuery prints JSON, with --compact for one line, and pages it with --limit and --offset, so that no answer is larger than the model can hold.
  • Everything is named by a key (a hex string) or an id that the model copies and does not have to understand. It never reads pixels, and of vertices only a few positions per draw, for the depth of surfaces; contents appear only as hashes.
  • The commands go from the whole to the part, so the model can spend its reading where the facts are unclear.

The commands, from the whole to the part

overlays lists passes whose camera never changes, and the draws that were drawn with an orthographic projection even in a pass of a 3D scene. pass <id> shows the constants of the camera and their values over time. depth lists only a pass with a perspective camera and draws in front of it.

Facts that tell a scene from an interface

Fact (command)Points to
A view_matrix constant whose value changes from frame to frame (pass: series)a scene: the camera moves
A projection_matrix that is perspective, and a depth buffer that is cleared and used (pass: clears, depth_stencil_view_key)a scene
No depth buffer, an orthographic projection, a camera that never changes, a few draws of a few vertices (overlays, pass)an interface (HUD, menu, text, a full-screen quad)
The pass is listed by depth, with a spread between depth_near and depth_far (the surface_depth_* fields tell the same for the vertices, and surface_depth_nearest for the nearest 0.05% of them)a scene; an overlay has no depth at all, or one depth
A viewport that covers only a part of the target (pass: viewport)a scene drawn into a window, or a panel of an interface; look at the others
A pass that reads a target that another pass of the frame wrote (resources with --class frame_local, pass)post-processing or a composite; it follows the pass that made its input (see step 6)
A pass with a camera that never changes but is deep, with many verticesprobably a scene seen from one place: overlays says so itself, “a hint, not a fact”
How often it occurs (pipelines: n_frames; timeline)a pass in every frame is part of the program's pipeline; one in a few frames is a transition or an effect

Giving the model its job

Give it a shell where it can run the query tool, the text of APIDumpAnalysisQuery's usage, the recipe format, and the table above. Ask for evidence, not for a verdict. A prompt that works:

You are helping to make a stereo-3D recipe for a 2D program (Direct3D 8, Direct3D 7 or OpenGL).
The analysis of its capture is in app.passes. Run APIDumpAnalysisQuery on it
(usage and recipe format attached), with --compact and --limit, and do not
read anything else: you have no access to the program, its code or its pixels.

Decide for every kind of pass whether it is
  scene      - 3D, to be drawn once for each eye
  interface  - 2D (HUD, menu, text, full-screen quad), to be drawn once
  unclear    - the facts do not say

For each, give the pass id and its key, the facts that decided it (command and
field), and your confidence. Start from `pipelines`, then `overlays`, then `pass`
for every pass that is in a shape. Look at one representative frame of each shape
(`frame --shape`) before you finish.

Copy keys exactly as printed: a key you typed from memory or shortened is wrong.
Do not infer a pass from the name of a resource. If two passes look alike, say so.
When you are done, write the "unaffected" part of the recipe (pass_keys and, where a
single draw inside an affected pass is an interface, draw_keys) and list every pass you
marked unclear, with the question that would settle it.

Two habits that make the answers good

  1. Ask for the unclear list. A model that has to say what it does not know checks more than one that has to decide everything.
  2. Read the evidence, not the verdict. The facts are fields of the JSON that you can run again yourself, and a verdict that rests on none of them is a guess.

Where the facts are not enough, a multimodal model can be given the back buffers of the frames (APIDumpPrinter writes the surface dumps of a workload to its working directory), and a person can always look.

4. Draft the rules

The input of the baker is a recipe without the baked section: what the person knows, and what the analysis cannot.

Result: recipe.json, the hand-written part only.

A Direct3D 8 program that sets its camera with SetTransform

It is nearly always the same shape (the recipe of a Direct3D 8 program in apps/recipes has these rules):

{
  "recipe_version": 0,
  "key_scheme_version": 1,
  "target": { "name": "my_demo", "description": "text for people" },
  "known_shape_keys": [ "0x..." ],        the shapes of step 2 that the recipe is made for
  "on_unknown_frame": "mono",             what a frame of another shape does: mono, skip or fail
  "unaffected": {
    "pass_keys": [ "0x..." ]              the interface passes, from step 3
  },
  "rules": [
    { "name": "view", "call": "IDirect3DDevice8::SetTransform",
      "when": { "state": "D3DTS_VIEW" },
      "action": { "type": "eye_offset", "order": "post", "axis": "x" } },
    { "name": "projection", "call": "IDirect3DDevice8::SetTransform",
      "when": { "state": "D3DTS_PROJECTION", "matrix": "perspective" },
      "action": { "type": "eye_convergence" } }
  ]
}
PartMeaning
unaffectedThe answer of step 3. Everything not listed is a scene draw, so a missed interface pass shows as an interface that is doubled; a pass wrongly listed shows as a scene that does not move between the eyes.
eye_offset ruleMoves each eye along an axis by half of the separation, which is a setting of the VR player (the depth choice), not of the recipe.
eye_convergence ruleShears the projection so that what is at the convergence distance is at the screen; the distance is measured and baked in step 5. See Recipe format for every action.
known_shape_keysShould be the shapes of the capture.
on_unknown_frameLeave at mono unless a program has screens that must not appear at all (skip) or that should never occur (fail, which stops the converter with a message, useful while testing).

Direct3D 7 with vertices in pixels, and OpenGL

There is no matrix call to put a rule on, so rules is empty. What the recipe says instead:

ProgramWhat the recipe holds
Direct3D 7, vertices in pixelsscreen_parallax: the convergence distance and the angle of view, since the vertices have neither.
OpenGLview_anchor_shift (where the eyes converge for a scene with no distance of its own), a comfort section with limits for single scenes (scene_overrides) and "measure_depth": true, so that the converter reads the depth of what is drawn.

Recipe format has each of them.

Checking what the LLM wrote

An LLM can write this file, and the model of step 3 usually already has what it needs. Check three things:

  1. Every key is one from the output of APIDumpAnalysisQuery (the loader checks that a key is well formed, but it cannot know that the program has it).
  2. known_shape_keys are shapes and not pass keys.
  3. Nothing was added that the evidence did not support.

5. Bake the recipe

tools\analysis\RecipeBake_x64 recipe.json app.passes --deps app.deps -o my_demo.json

Result: my_demo.json, the recipe with its baked section.

What the baker adds

A converter in the running program can use only what is known when a draw is issued, and a pass or a shape is not (the pass is not over yet). The baker therefore turns what is known offline into what is known live.

BakedWhat it is
draw_rulesFor every draw signature the analysis saw: an interface or a scene, with the view matrix where one signature is both.
convergence distancesFor each signature and for each shape: the median depth by vertices of what it draws.
known signaturesThe list of signatures it knew.
flat_layer_draws, overlay_draws, eye_space_drawsThe keys of the draws that are flat layers, overlays over a 3D scene, or in eye space (see How far away is it?). Only with comfort.automatic_layers in the recipe; without it the baked section has none of the three.

It prints a summary: the number of signatures, of rules, of signatures that only the view matrix tells apart, and how many have a distance.

What the result can mean

  • Exit 3 means the recipe cannot be baked, and says why. The usual one: a signature that is drawn as an interface in one pass and as a scene in another, with the same view matrix, so that nothing known when it is issued tells the two apart. The message names the signature; the remedy is in the rules (draw_keys say which draws of an affected pass are an interface).
  • Signatures with no distance are draws that were never in front of the camera in the capture; they use the distance of their frame's shape.
  • Bake again whenever the capture changes. The baked part is generated; do not edit it. Without -o the recipe is written over itself, so keep the unbaked one apart.

Three modes that write nothing

ModeWhat it prints
--checkWhich kinds of frames and which draw signatures of the capture the recipe does not know (exit 5), and which passes it leaves alone look like 3D scenes (exit 6). It also lists the draw keys whose draws disagree (some in the space of the picture and some not, some over a 3D scene and some not, or some in eye space and some not: no one rule can class such a key); those change no exit code.
--overlaysAs JSON, the draws that may be 2D overlays.
--parityThe draws on which the replay and the live converter decide differently (class or push). Run it after baking: it must list none.
--scenesEach scene with where its frames are, where the eyes converge, how far apart they may be and what that makes of the parallax of its nearest and farthest surfaces (--screen-degrees says how wide the screen is). It is what the comfort numbers are tuned with (Recipes).

6. Check it offline

The offline replay tools take a recipe, so a recipe can be checked on the capture before it meets the program. This is the step where a person looks.

tools\stereo_replay\StereoReplayPlayer_x86.exe --recipe my_demo.json --eye both --eye-separation 0.1 result_dump.workload
tools\stereo_replay\StereoReplayInspector_x86.exe result_dump.workload --recipe my_demo.json --from 0 --to 200 --dump-dir out

Result: images of both eyes for frames of every shape, and a verdict on what to change.

The two tools

ToolWhat it does
StereoReplayPlayerRenders the frames for both eyes and shows the images side by side. Use --eye left and --eye right to see one at a time.
StereoReplayInspectorReplays the frames twice, the first time for the left eye and the second for the right, and compares the images with those of a replay without the recipe. With a recipe that changes nothing it must find no difference; with the real one, differences are expected, and the inspector's job is to say where the replay itself is unstable (a frame that cannot be executed twice is not one that stereo conversion can handle).

Some frames of any program differ on a second execution; compare with the same run without the recipe before blaming the recipe.

Looking without a window

Checker optionEffect
--screenshot N --out file.png --recipe my_demo.jsonWrites frame N, both eyes side by side, or --eye anaglyph.
--contact-sheet K --out sheet.pngPuts K frames spread over the range on one picture.
--overlay-report candidates.jsonTakes the output of RecipeBake --overlays and makes an animation for each draw that may be an overlay, with and without it, to look at in index.html of --dump-dir.

The player and the inspector come as _x86 (for the capture of a 32-bit program) and _x64.

What you see, and where to go back to

What you seeLikely causeGo back to

The world is right but a post-processed result or a reflection is off by an eyea pass that reads a target was not drawn for the eye that made itstep 3: resources and pass for the pass that reads it

7. Try it live

Add the program to the catalog (step 8) and start it from VRPlayer, or start StereoLauncher yourself:

runtime\StereoLauncher_x86.exe --recipe my_demo.json --session test --log --wait c:\path\to\app.exe

Result: the program running in stereo, and a session log to read.

Launcher options and the log

OptionEffect
--sessionNames the playback.
--working-directorySays where the application runs.
--logOn StereoLauncher, or on VRPlayer (which has no control for it in the window, and passes the switch on): the converter writes a session log, %TEMP%\apistereo_<session>.log. <session> is the --session value; VRPlayer uses its process ID and a tick count, <pid>-<ticks>. Lines ending in “(presenter)” come from the headset path.

What to look for in the log

In the logMeaning
Frames of a scene the recipe has no distance for (scene_convergence); the statistics line counts themA program that is mostly in such frames is in screens that were not in the capture (step 1).
A refusalA rule that depends on a pass or a frame shape (pass_keys or shape_keys in the when of a rule) cannot be followed live, since neither is known when a draw is issued, and the converter then stops with a message instead of drawing wrong images. The interface passes of unaffected are not of this kind: the baker turns them into rules by signature.
The statistics line at the endThe numbers of affected, unaffected and skipped draws, of draws of a signature the recipe does not know, of frames of a scene it has no distance for, and of matrices kept, then the twins and the unmirrored calls (Direct3D 7, OpenGL), the counts of the OpenGL draws, and what the callbacks cost per frame. A large count of unknown draws means that the program draws things in play that were not in the capture.

Judge what you see in the window first and in the headset second: the window shows the same images, and it is where a fault is easiest to tell from discomfort.

8. Put it in the catalog

The catalog is apps/apps.json, and the recipes it names are in apps/recipes/. build.bat copies both to build_final\apps\, so a release has them. VRPlayer lists the programs alphabetically by name, ignoring case, and by id when names are equal.

Result: the program appears in the list of VRPlayer.

How an entry is used

The program itself is not kept in the repository: the entry says where it can be downloaded, and VRPlayer gets it the first time it is launched, into apps/<id>/ (see VR player).

The entry

Copy the baked recipe to apps/recipes/my_demo.json, and add an entry:

{
  "catalog_version": 0,
  "apps": [
    {
      "id": "my_demo",                          letters, digits, '-' and '_'
      "recipe": "recipes/my_demo.json",         relative to the catalog
      "executable": "my_demo/my_demo.exe",      where it is once it is downloaded: in apps/<id>/
      "arguments": "-fullscreen=0",             (optional) the command line of the application
      "working_directory": "my_demo",          (optional) relative to the catalog; the directory of the executable by default
      "launch_button": "Launch",              (optional) the text of a button of the dialog that the program shows first; the launcher presses it for the user (waited for up to 60 s)
      "untick_checkbox": "Fullscreen",        (optional) the text of a checkbox of that dialog; the launcher unticks it just before it presses the button (a program that asks to run full screen would otherwise change the screen resolution and cover the window that shows the images)
      "title": "My demo",                      (optional) the title in the list, written "name by group (year)" in this repository: otherwise, the name of the recipe's target
      "unavailable_reason": "...",             (optional) why the player cannot start it although the recipe is there (a program that the converter cannot run); the entry is listed with the reason
      "download": {                             (optional) where the program comes from, if it is not there
        "urls": ["https://mirror.example/my_demo.zip"],   https only; one after the other until one works
        "sha256": "...",                       of the zip file, in hex: what is not that is not used
        "size": 12345,                        bytes of the zip file
        "unpacked_size": 23456,               the most that the files may take together
        "page": "https://example/my_demo"      (optional) where it can be got by hand
      }
    }
  ]
}

What makes an entry or the catalog unusable

FaultResult
The recipe cannot be found or is not validThe entry is listed as unavailable, with the reason.
The executable cannot be found and the entry has no downloadThe entry is listed as unavailable, with the reason.
A field the loader does not knowThe whole catalog is unreadable (the window says why).
A download without urls, sha256, size or unpacked_sizeThe whole catalog is unreadable.
An executable outside apps/<id>/ in an entry with a downloadThe whole catalog is unreadable.

The zip file has to hold the program with the paths of executable under apps/<id>/. Get its sha256 from a copy you trust (certutil -hashfile my_demo.zip SHA256), and check that the program may be downloaded by whoever uses the catalog.

Doing it again

A recipe is made for one version of a program.

The program changes, or a screen is missing

Capture again (step 1), extract again, and give the model the new analysis and the old recipe. Keys of passes whose structure did not change are the same, so what is already decided stays decided, and the model only has to look at what is new (the shapes and passes not in known_shape_keys).

The analysis tools change the keys

key_scheme_version changes, the loader refuses the old recipe, and the whole of steps 2 to 5 is done again from the same capture.

What this does not cover

LimitDetail
A Direct3D camera has to be set with SetTransformThe calls a rule can apply to are IDirect3DDevice8::SetTransform and IDirect3DDevice7::SetTransform (which has transform states named D3DTRANSFORMSTATE_VIEW and so on). A program that passes its matrices to a vertex shader as constants (SetVertexShaderConstant) has a camera that the converter cannot move: the analysis follows such constants, but a rule that changes them is new work in the loader, the baker and the converter, not a recipe.
Direct3D 7 for vertices in pixels onlyA Direct3D 7 program whose vertices a matrix moves has no adapter (see Direct3D 7).
Direct3D 8 draws with vertices in pixelsThey are moved for each eye when the vertices come with the call (DrawPrimitiveUP, DrawIndexedPrimitiveUP); those from a vertex buffer end the application.
OpenGL of the fixed functionA camera that is the model-view matrix is converted (see OpenGL). A program that loads its cameras inside display lists, or has more than one context, is not tried. See What is supported.
The LLM reads facts; it does not see the programA fault that the facts cannot show (a pass that is an interface in some frames and a scene in others, with the same structure) is found by a person, in step 6.

Checklist

  • Captured every screen of the program, with --dump-swapchain-on-present.
  • info: no unfollowed or unsupported calls, no key collisions, hazards understood, a small number of shapes.
  • Every pass has a decision with evidence; the unclear ones are settled by a person.
  • The recipe's keys are all from the query output; known_shape_keys are the shapes of the capture.
  • Baked without error; the signatures without a distance are understood.
  • StereoReplayPlayer shows no doubled interface and a scene with depth, in both eyes, on frames of every shape.
  • The live session log shows no refusal and few unknown frames or draws.
  • The recipe is in apps/recipes/, the entry (with where the program is downloaded from, and its hash) in apps/apps.json, and build.bat was run.
