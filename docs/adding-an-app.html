Adding an app

How to take a 2D program from nothing to a recipe that turns it into stereo 3D, and to a line in the catalog of the VR player. The facts about the program are read from its analysis by an LLM; a person decides, and looks at the pictures.

The converter handles Direct3D 8 programs whose camera is set with SetTransform, and Direct3D 7 programs whose vertices are already in pixels (see What this does not cover). The steps are the same for another API once it has its front end and its converter adapter (What adding an API takes); only what the rules can name changes.
The commands are written from the folder of a release (build_final): the programs are in tools\api_dumper, tools\analysis and tools\stereo_replay (see The collected build).

The steps

1. Capture the program

tools\api_dumper\APIDumper_x86.exe --dump-n-frames 3000 --dump-swapchain-on-present c:\path\to\app.exe [app arguments]

Use APIDumper_x86.exe for a 32-bit program and APIDumper_x64.exe for a 64-bit one. The workload is written as result_dump.workload in the working directory of the program, when the frame count is reached or when it exits. A capture can be large (a few minutes of a demo is gigabytes); --spill-threshold-mb keeps a 32-bit program from running out of memory while it is written. --dump-swapchain-on-present stores the back buffer of each frame, which is what lets anyone later see what a frame looked like.

What to capture decides what the recipe knows. The analysis groups frames into shapes (the kinds of passes a frame is made of), and a recipe knows only the shapes it saw; any other frame is treated as the recipe says (on_unknown_frame, mono by default). So one capture should walk through every kind of screen the program has: the loader, the menu, each scene, the transitions. Play it the way a user would, once.

2. Extract the passes

tools\analysis\APIDumpAnalysisExtractor_x64 result_dump.workload -o app.passes --stats

Before going on, look at the summary it prints, or at APIDumpAnalysisQuery app.passes info. A capture is good for the next steps when:

  • n_unfollowed_calls and n_unsupported_calls are 0. The first counts calls that the analysis could not make sense of (a call whose arguments were not as expected); the second, calls of an API that the front end does not know. Either means the passes found may be wrong, and the cause is a bug or a gap in the front end, not something a recipe can fix.
  • key_collisions is 0 (two different structures with the same key would be taken for one).
  • n_resolution_hazards is empty, or it is understood: a hazard is a call whose meaning depends on the size of the target in pixels, so rendering larger than the program asks would break it (see the Direct3D 8 front end).
  • frame_shapes is a small number. Hundreds of shapes mean that something that varies from frame to frame (a particle pass, a loading bar) is cutting the frames up; that is worth understanding before writing any rule.

3. Investigate with an LLM

The question is the one the analysis deliberately does not answer (What it does not do): which passes of this program are the 3D scene, and which are an interface that must not be shifted? The analysis gives the facts; deciding is the work of whoever reads them. An LLM is good at this reading, for three reasons that the tools are built around:

  • APIDumpAnalysisQuery prints JSON, with --compact for one line, and pages it with --limit and --offset, so that no answer is larger than the model can hold.
  • Everything is named by a key (a hex string) or an id that the model copies and does not have to understand. It never reads pixels, and of vertices only a few positions per draw, for the depth of surfaces; contents appear only as hashes.
  • The commands go from the whole to the part, so the model can spend its reading where the facts are unclear: info (what is in the file), pipelines (the kinds of frames, each made of which kinds of passes), overlays (passes whose camera never changes: candidates for an interface), pass <id> (one kind of pass in full: its targets, clears, viewport, camera constants and their values over time), frame --shape <id> (one real frame of a shape), resources (what is written and read), depth (how deep the draws of each pass are: the near, median and far depth, and the vertices counted), and timeline (which shape is on screen when).

Giving the model its job

Give it a shell where it can run the query tool, the text of APIDumpAnalysisQuery's usage, the recipe format, and the table above. Ask for evidence, not for a verdict. A prompt that works:

You are helping to make a stereo-3D recipe for a 2D Direct3D 8 program.
The analysis of its capture is in app.passes. Run APIDumpAnalysisQuery on it
(usage and recipe format attached), with --compact and --limit, and do not
read anything else: you have no access to the program, its code or its pixels.

Decide for every kind of pass whether it is
  scene      - 3D, to be drawn once for each eye
  interface  - 2D (HUD, menu, text, full-screen quad), to be drawn once
  unclear    - the facts do not say

For each, give the pass id and its key, the facts that decided it (command and
field), and your confidence. Start from `pipelines`, then `overlays`, then `pass`
for every pass that is in a shape. Look at one representative frame of each shape
(`frame --shape`) before you finish.

Copy keys exactly as printed: a key you typed from memory or shortened is wrong.
Do not infer a pass from the name of a resource. If two passes look alike, say so.
When you are done, write the "unaffected" part of the recipe (pass_keys and, where a
single draw inside an affected pass is an interface, draw_keys) and list every pass you
marked unclear, with the question that would settle it.

Two habits make the answers good. The first is to ask for the unclear list: a model that has to say what it does not know checks more than one that has to decide everything. The second is to read the evidence, not the verdict: the facts are fields of the JSON that you can run again yourself, and a verdict that rests on none of them is a guess. Where the facts are not enough, a multimodal model can be given the back buffers of the frames (APIDumpPrinter writes the surface dumps of a workload to its working directory), and a person can always look.

4. Draft the rules

The input of the baker is a recipe without the baked section: what the person knows, and what the analysis cannot. For a program that sets its camera with SetTransform it is nearly always the same shape (this is how apps/recipes/fr08.json starts):

{
  "recipe_version": 0,
  "key_scheme_version": 1,
  "target": { "name": "myapp", "description": "text for people" },
  "known_shape_keys": [ "0x..." ],        the shapes of step 2 that the recipe is made for
  "on_unknown_frame": "mono",             what a frame of another shape does: mono, skip or fail
  "unaffected": {
    "pass_keys": [ "0x..." ]              the interface passes, from step 3
  },
  "rules": [
    { "name": "view", "call": "IDirect3DDevice8::SetTransform",
      "when": { "state": "D3DTS_VIEW" },
      "action": { "type": "eye_offset", "order": "post", "axis": "x" } },
    { "name": "projection", "call": "IDirect3DDevice8::SetTransform",
      "when": { "state": "D3DTS_PROJECTION", "matrix": "perspective" },
      "action": { "type": "eye_convergence" } }
  ]
}
  • unaffected is the answer of step 3. Everything not listed is a scene draw, so a missed interface pass shows as an interface that is doubled; a pass wrongly listed shows as a scene that does not move between the eyes.
  • The eye_offset rule moves each eye along an axis by half of the separation, which is a setting of the VR player (the depth choice), not of the recipe. eye_convergence shears the projection so that what is at the convergence distance is at the screen; the distance is measured and baked in step 5. See Recipe format for every action.
  • known_shape_keys should be the shapes of the capture. Leave on_unknown_frame at mono unless a program has screens that must not appear at all (skip) or that should never occur (fail, which stops the converter with a message, useful while testing).

An LLM can write this file, and the model of step 3 usually already has what it needs. Check three things in what it wrote: that every key is one from the output of APIDumpAnalysisQuery (the loader checks that a key is well formed, but it cannot know that the program has it), that known_shape_keys are shapes and not pass keys, and that nothing was added that the evidence did not support.

5. Bake the recipe

tools\analysis\RecipeBake_x64 recipe.json app.passes -o myapp.json

A converter in the running program can use only what is known when a draw is issued, and a pass or a shape is not (the pass is not over yet). The baker therefore turns what is known offline into what is known live: for every draw signature the analysis saw, whether it is an interface or a scene (draw_rules, with the view matrix where one signature is both), the distance at which the eyes converge for each signature and for each shape (the median depth by vertices of what it draws), and the list of signatures it knew. It prints a summary: the number of signatures, of rules, of signatures that only the view matrix tells apart, and how many have a distance.

  • Exit 3 means the recipe cannot be baked, and says why. The usual one: a signature that is drawn as an interface in one pass and as a scene in another, with the same view matrix, so that nothing known when it is issued tells the two apart. The message names the signature; the remedy is in the rules (draw_keys say which draws of an affected pass are an interface).
  • Signatures with no distance are draws that were never in front of the camera in the capture; they will use the distance of their frame's shape.
  • Bake again whenever the capture changes. The baked part is generated; do not edit it.

6. Check it offline

The offline replay tools take a recipe, so a recipe can be checked on the capture before it meets the program. This is the step where a person looks.

tools\stereo_replay\StereoReplayPlayer_x86.exe --recipe myapp.json --eye both --eye-separation 0.1 result_dump.workload
tools\stereo_replay\StereoReplayConsistencyChecker_x86.exe result_dump.workload --recipe myapp.json --from 0 --to 200 --dump-dir out
  • StereoReplayPlayer renders the frames for both eyes and shows the images side by side. Look for the things below, with --eye left and --eye right to see one at a time.
  • StereoReplayConsistencyChecker replays the frames twice, the first time for the left eye and the second for the right, and compares the images with those of a replay without the recipe. With a recipe that changes nothing it must find no difference; with the real one, differences are expected, and the checker's job is to say where the replay itself is unstable (a frame that cannot be executed twice is not one that stereo conversion can handle). Mind that some frames of any program differ on a second execution; compare with the same run without the recipe before blaming the recipe.

7. Try it live

Add the program to the catalog (step 8) and start it from VRPlayer, or start StereoLauncher yourself. With --log on StereoLauncher (VR Player has no control for it, and the log is off), the converter writes a session log, %TEMP%\apistereo_<session>.log; lines ending in “(presenter)” come from the headset path. What to look for in it:

  • Frames of a scene the recipe has no distance for (scene_convergence): the statistics line counts them. A program that is mostly in such frames is in screens that were not in the capture (step 1).
  • A refusal: a rule that depends on a pass or a frame shape (pass_keys or shape_keys in the when of a rule) cannot be followed live, since neither is known when a draw is issued, and the converter then stops with a message instead of drawing wrong images. The interface passes of unaffected are not of this kind: the baker turns them into rules by signature.
  • The statistics line at the end: the numbers of affected, unaffected and skipped draws, of draws of a signature the recipe does not know, of frames of a scene it has no distance for, and of matrices kept. A large count of unknown draws means that the program draws things in play that were not in the capture.

Judge what you see in the window first and in the headset second: the window shows the same images, and it is where a fault is easiest to tell from discomfort.

8. Put it in the catalog

The catalog is apps/apps.json, and the recipes it names are in apps/recipes/; build.bat copies both to build_final\apps\, so a release has them. The program itself is not kept in the repository: the entry says where it can be downloaded, and VRPlayer gets it the first time it is launched, into apps/<id>/ (see VR player). Copy the baked recipe to apps/recipes/myapp.json, and add an entry:

{
  "catalog_version": 0,
  "apps": [
    {
      "id": "myapp",                            letters, digits, '-' and '_'
      "recipe": "recipes/myapp.json",           relative to the catalog
      "executable": "myapp/myapp.exe",          where it is once it is downloaded: in apps/<id>/
      "arguments": "-fullscreen=0",             (optional) the command line of the application
      "working_directory": "myapp",            (optional) relative to the catalog; the directory of the executable by default
      "title": "My app",                       (optional) the title in the list: otherwise, the name of the recipe's target
      "download": {                             (optional) where the program comes from, if it is not there
        "urls": ["https://mirror.example/myapp.zip"],   https only; one after the other until one works
        "sha256": "...",                       of the zip file, in hex: what is not that is not used
        "size": 12345,                        bytes of the zip file
        "unpacked_size": 23456,               the most that the files may take together
        "page": "https://example/myapp"        (optional) where it can be got by hand
      }
    }
  ]
}

An entry whose recipe cannot be found, or whose executable cannot be found and has no download, is listed as unavailable, with the reason. The zip file has to hold the program with the paths of executable under apps/<id>/. Get its sha256 from a copy you trust (certutil -hashfile myapp.zip SHA256), and check that the program may be downloaded by whoever uses the catalog.

Doing it again

A recipe is made for one version of a program. When the program changes, or when a screen of it is missing, capture again (step 1), extract again, and give the model the new analysis and the old recipe: keys of passes whose structure did not change are the same, so what is already decided stays decided, and the model only has to look at what is new (the shapes and passes not in known_shape_keys). When the analysis tools themselves change in a way that changes keys, key_scheme_version changes, the loader refuses the old recipe, and the whole of steps 2 to 5 is done again from the same capture.

What this does not cover

  • The camera has to be set with SetTransform. The calls a rule can apply to are IDirect3DDevice8::SetTransform and IDirect3DDevice7::SetTransform (which has transform states named D3DTRANSFORMSTATE_VIEW and so on). A program that passes its matrices to a vertex shader as constants (SetVertexShaderConstant) has a camera that the converter cannot move: the analysis follows such constants, but a rule that changes them is new work in the loader, the baker and the converter, not a recipe.
  • Direct3D 8, and Direct3D 7 for vertices in pixels. A Direct3D 7 program whose vertices a matrix moves has no adapter (see Direct3D 7). An OpenGL program can be captured, analysed in part and replayed, but there is no front end that gives it passes, and no converter adapter. See One API is not all of them.
  • The LLM reads facts; it does not see the program. A fault that the facts cannot show (a pass that is an interface in some frames and a scene in others, with the same structure) is found by a person, in step 6.

Checklist

  • Captured every screen of the program, with --dump-swapchain-on-present.
  • info: no unfollowed or unsupported calls, no key collisions, hazards understood, a small number of shapes.
  • Every pass has a decision with evidence; the unclear ones are settled by a person.
  • The recipe's keys are all from the query output; known_shape_keys are the shapes of the capture.
  • Baked without error; the signatures without a distance are understood.
  • StereoReplayPlayer shows no doubled interface and a scene with depth, in both eyes, on frames of every shape.
  • The live session log shows no refusal and few unknown frames or draws.
  • The recipe is in apps/recipes/, the entry (with where the program is downloaded from, and its hash) in apps/apps.json, and build.bat was run.
