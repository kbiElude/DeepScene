Adding an app

How to take a 2D program from nothing to a recipe that turns it into stereo 3D, and to a line in the catalog of the VR player. The facts about the program are read from its analysis by an LLM; a person decides, and looks at the pictures.

The converter handles Direct3D 8 programs whose camera is set with SetTransform, Direct3D 7 programs whose vertices are already in pixels, and OpenGL programs of the fixed function (see What this does not cover). The steps are the same for each of them; only what the rules can name changes (step 4). For another API they are the same once it has its front end and its converter adapter (Adding an API). The catalog has one program of each of the three APIs.
The commands are written from the folder of a release (build_final): the programs are in tools\api_dumper, tools\analysis, tools\stereo_replay and runtime (see The collected build). my_demo and app.exe stand for the program being added.

The steps

Eight steps, each ending in a file or a decision that the next step reads.

1. Capture the program

tools\api_dumper\APIDumper_x86.exe --dump-n-frames 3000 --max-frame-rate 60 c:\path\to\app.exe [app arguments]

Result: result_dump.workload, a recording of every API call and of the data they point to. Run it from the folder of the program (the working directory is where the file goes).

Capture the program the way the catalog launches it, with the same choices in its start dialog (untick_checkbox, the video mode). A program that does not set a viewport draws to the whole of its window, and the size of the window is part of what identifies each draw: a recipe made from a capture of another mode matches nothing when the program is played.

The options

Option or fileEffect
APIDumper_x86.exe / APIDumper_x64.exeThe dumper for a 32-bit or a 64-bit program.
--dump-n-frames NThe capture ends when N frames have been presented, or when the program exits. Without it, only the exit ends it.
--dump-swapchain-on-presentOptional, and not needed by the analysis or the replay. Stores the back buffer of each frame (OpenGL, Direct3D 7 and 8) so that anyone can see what the frame looked like without replaying it. It is large: at 1280 by 720, 3.7 MB for every frame, which is about nine tenths of the file for a program that draws little. StereoReplayInspector --screenshot shows a frame without it.
--max-frame-rate NHolds the program to at most N frames a second (1 to 1000) while it is captured. A program with no limit of its own, such as an old demo that does not wait for the screen, makes thousands of frames a second, so a few minutes of it are hundreds of thousands of frames, and the analysis and the replay take as many times as long. At 60 a second, four and a half minutes are about 15,000 frames and under a gigabyte (without the images of the frames). The hold applies only while the program is captured, and it does not make up for a frame that was late. A program that pauses while its window is not in the foreground stops making frames when something else takes the focus, so leave it alone while it is captured.
--spill-threshold-mb NWrites the data waiting in memory to the file once it reaches N megabytes (128 by default), so that a 32-bit program does not run out of memory. The file is written, and compressed with up to eight threads, off the thread of the program, which waits only if the previous write is not done. The data of the calls that the dumper holds is bounded too (at four times N, counting what each piece costs besides its bytes): a frame that holds more ends the capture with a message. When a capture stops at --dump-n-frames, the program runs on and the dumper keeps nothing. A capture can be large: with the images of the frames, a few minutes of a demo are tens of gigabytes.
result_dump.workloadThe output, written in the working directory of the program.

What to capture

What is captured decides what the recipe knows. The analysis groups frames into shapes (the kinds of passes a frame is made of), and a recipe knows only the shapes it saw; any other frame is treated as the recipe says (on_unknown_frame, mono by default).

So one capture should walk through every kind of screen the program has: the loader, the menu, each scene, the transitions. Play it the way a user would, once.

2. Extract the passes

tools\analysis\APIDumpAnalysisExtractor_x64 result_dump.workload -o app.passes --stats
tools\analysis\APIDumpDependencyExtractor_x64 result_dump.workload -o app.deps --stats

Result: app.passes (the passes and frame shapes) and app.deps (which frames and textures each frame needs).

What the two files are for

FileUsed by
app.passesThe query tool (step 3) and the baker (step 5). A file made by another version of the analysis (file, section or key scheme) is refused: extract again.
app.depsThe baker (--deps), to know which textures need a copy for the second eye; the replay player (--deps), to seek faster.

The options both extractors share

OptionEffect
-o fileThe file to write; by default the name of the workload with .passes or .deps.
--max-frames NStops after the Nth frame.
--threads NThreads that read the workload ahead of the analysis (the cores of the machine, up to 8, by default; 0: none).
--statsPrints what was found when done.
Exit code0 done, 1 bad arguments, 2 the workload cannot be read, 3 the output cannot be written.

One script for steps 2 and 5, and the checks

scripts\analyze_capture.ps1 -Workload result_dump.workload -Recipe recipe.json -OutDir folder [-MaxFrames N] [-ToolsDir dir]

It runs the two extractors, the bake of step 5, and then two checks of the baked recipe. The names come from the workload (result_dump here). folder must not be the folder of the recipe: the recipe is only read, and to use the baked one you copy it over by hand.

Written into folderWhat it is
result_dump.passes, result_dump.depsThe two files above.
result_dump.baked.jsonThe baked recipe (RecipeBake -o, never in place).
check.logRecipeBake --check on the baked recipe; the script prints its first lines.
parity.logRecipeBake --parity: the draws on which the replay and the live converter decide differently; exit 7 is a finding the script accepts, and it prints the first lines.
extract_passes.log, extract_deps.log, bake.logWhat each of the other tools printed.

-ToolsDir defaults to build_final\tools\analysis; the script runs the _x64 tools.

Is the capture good?

Before going on, look at APIDumpAnalysisQuery app.passes info. The extractor's --stats prints the same numbers as lines (unfollowed, unsupported, Key collisions).

FieldGood valueIf it is not
n_unfollowed_calls0The analysis could not make sense of a call (its arguments were not as expected). The passes found may be wrong; the cause is a bug or a gap in the front end, not something a recipe can fix.
n_unsupported_calls0The program calls an API that the front end does not know. Same consequence as above.
key_collisions0Two different structures with the same key would be taken for one.
n_resolution_hazardsempty, or understoodA hazard is a call whose meaning depends on the size of the target in pixels, so rendering larger than the program asks would break it (see One translator per API).
frame_shapesa small numberHundreds of shapes mean that something that varies from frame to frame (a particle pass, a loading bar) is cutting the frames up. Understand that before writing any rule.

3. Investigate with an LLM

The question is the one the analysis deliberately does not answer (What it does not do): which passes of this program are the 3D scene, and which are an interface that must not be shifted? The analysis gives the facts; deciding is the work of whoever reads them.

Result: for every kind of pass, a decision (scene, interface or unclear) with the facts that support it.

Why an LLM can do this reading

The tools are built around three properties.

  • APIDumpAnalysisQuery prints JSON, with --compact for one line, and pages it with --limit and --offset, so that no answer is larger than the model can hold.
  • Everything is named by a key (a hex string) or an id that the model copies and does not have to understand. It never reads pixels, and of vertices only a few positions per draw, for the depth of surfaces; contents appear only as hashes.
  • The commands go from the whole to the part, so the model can spend its reading where the facts are unclear.

The commands, from the whole to the part

CommandWhat it adds
overlaysThe passes whose camera never changes, and the draws drawn with an orthographic projection even in a pass of a 3D scene. It ends with an unaffected list that can be pasted into a recipe, and it is a hint.
pass <id>The constants of the camera and their values over time.
depthFor each pass with vertices in front of the camera, in each kind of frame: the depth of its draws, and of its vertices where the analysis could read them.

Facts that tell a scene from an interface

Fact (command)Points to
A view_matrix constant whose value changes from frame to frame (pass: series)a scene: the camera moves
A projection_matrix that is perspective, and a depth buffer that is cleared and used (pass: clears, depth_stencil_view_key)a scene
No depth buffer, an orthographic projection, a camera that never changes, a few draws of a few vertices (overlays, pass)an interface (HUD, menu, text, a full-screen quad)
The pass is listed by depth, with a spread between depth_near and depth_far (the surface_depth_* fields tell the same for the vertices, and surface_depth_nearest for the nearest 0.05% of them)a scene; an overlay has no depth at all, or one depth
A viewport that covers only a part of the target (pass: viewport)a scene drawn into a window, or a panel of an interface; look at the others
A pass that reads a target that another pass of the frame wrote (resources with --class frame_local, pass)post-processing or a composite; it follows the pass that made its input (see step 6)
A pass with a camera that never changes but is deep, with many verticesprobably a scene seen from one place: overlays says so itself, “a hint, not a fact”
How often it occurs (pipelines: n_frames; timeline)a pass in every frame is part of the program's pipeline; one in a few frames is a transition or an effect

Giving the model its job

Give it a shell where it can run the query tool, the text of APIDumpAnalysisQuery's usage, the recipe format, and the table above. Ask for evidence, not for a verdict. A prompt that works:

You are helping to make a stereo-3D recipe for a 2D program (Direct3D 8, Direct3D 7 or OpenGL).
The analysis of its capture is in app.passes. Run APIDumpAnalysisQuery on it
(usage and recipe format attached), with --compact and --limit, and do not
read anything else: you have no access to the program, its code or its pixels.

Decide for every kind of pass whether it is
  scene      - 3D, to be drawn once for each eye
  interface  - 2D (HUD, menu, text, full-screen quad), to be drawn once
  unclear    - the facts do not say

For each, give the pass id and its key, the facts that decided it (command and
field), and your confidence. Start from `pipelines`, then `overlays`, then `pass`
for every pass that is in a shape. Look at one representative frame of each shape
(`frame --shape`) before you finish.

Copy keys exactly as printed: a key you typed from memory or shortened is wrong.
Do not infer a pass from the name of a resource. If two passes look alike, say so.
When you are done, write the "unaffected" part of the recipe (pass_keys and, where a
single draw inside an affected pass is an interface, draw_keys) and list every pass you
marked unclear, with the question that would settle it.

Two habits that make the answers good

  1. Ask for the unclear list. A model that has to say what it does not know checks more than one that has to decide everything.
  2. Read the evidence, not the verdict. The facts are fields of the JSON that you can run again yourself, and a verdict that rests on none of them is a guess.

Where the facts are not enough, a multimodal model can be given pictures of frames: StereoReplayInspector --screenshot and --contact-sheet (step 6) write them as PNG files. A capture made with --dump-swapchain-on-present also has the back buffers, which APIDumpPrinter writes as raw RGBA files, one for each frame, which is a lot of data. A person can always look.

4. Draft the rules

The input of the baker is a recipe without the baked section: what the person knows, and what the analysis cannot.

Result: recipe.json, the hand-written part only.

A Direct3D 8 program that sets its camera with SetTransform

It is nearly always the same shape (the recipe of a Direct3D 8 program in apps/recipes has these rules):

{
  "recipe_version": 0,
  "key_scheme_version": 1,
  "target": { "name": "my_demo", "description": "text for people" },
  "known_shape_keys": [ "0x..." ],        the shapes of step 2 that the recipe is made for
  "on_unknown_frame": "mono",             what a frame of another shape does: mono, skip or fail
  "unaffected": {
    "pass_keys": [ "0x..." ]              the interface passes, from step 3
  },
  "rules": [
    { "name": "view", "call": "IDirect3DDevice8::SetTransform",
      "when": { "state": "D3DTS_VIEW" },
      "action": { "type": "eye_offset", "order": "post", "axis": "x" } },
    { "name": "projection", "call": "IDirect3DDevice8::SetTransform",
      "when": { "state": "D3DTS_PROJECTION", "matrix": "perspective" },
      "action": { "type": "eye_convergence" } }
  ]
}
PartMeaning
unaffectedThe answer of step 3. Everything not listed is a scene draw, so a missed interface pass shows as an interface that is doubled; a pass wrongly listed shows as a scene that does not move between the eyes.
eye_offset ruleMoves each eye along an axis by half of the separation, which is a setting of the VR player (the depth choice), not of the recipe.
eye_convergence ruleShears the projection so that what is at the convergence distance is at the screen; the distance is measured and baked in step 5. See Recipe format for every action.
known_shape_keysShould be the shapes of the capture. Left out, every frame is known; an empty list is refused.
on_unknown_framemono when left out. skip for screens that must not appear at all; fail for screens that should never occur (it stops the converter with a message, useful while testing).
targetOptional. name is the title in the catalog when the entry has none; description is optional and is shown under the title in the VR player.
rulesRequired; [] for a program with no matrix call to follow (below).

Direct3D 7 with vertices in pixels, and OpenGL

There is no matrix call to put a rule on, so rules is empty. What the recipe says instead:

ProgramWhat the recipe holds
Direct3D 7, vertices in pixelsscreen_parallax: the convergence distance and the angle of view, since the vertices have neither.
OpenGLview_anchor_shift (where the eyes converge for a scene with no distance of its own), a comfort section with limits for single scenes (scene_overrides) and "measure_depth": true, so that the converter reads the depth of what is drawn.

Recipe format has each of them.

Checking what the LLM wrote

An LLM can write this file, and the model of step 3 usually already has what it needs. Check three things:

  1. Every key is one from the output of APIDumpAnalysisQuery (the loader checks that a key is well formed, but it cannot know that the program has it).
  2. known_shape_keys are shapes and not pass keys.
  3. Nothing was added that the evidence did not support.

5. Bake the recipe

tools\analysis\RecipeBake_x64 recipe.json app.passes --deps app.deps -o my_demo.json

Result: my_demo.json, the recipe with its baked section.

What the baker adds

A converter in the running program can use only what is known when a draw is issued, and a pass or a shape is not (the pass is not over yet). The baker therefore turns what is known offline into what is known live.

BakedWhat it is
draw_rulesFor every draw signature the analysis saw: an interface or a scene, with the view matrix where one signature is both.
convergence, scene_convergenceFor each signature and for each shape: the median depth by vertices of what it draws.
scene_max_separationFor each shape with depth: how far apart the eyes may be, from its nearest (and farthest) surfaces and the comfort of the recipe.
per_eye_texturesThe textures that each eye has its own copy of (told by --deps; without it, by what each frame reads and writes).
known_signaturesThe list of signatures it knew.
flat_layer_draws, overlay_draws, eye_space_drawsThe keys of the draws that are flat layers, overlays over a 3D scene, or in eye space (see How far away is it?). Only with comfort.automatic_layers in the recipe; without it the baked section has none of the three.

What the summary says

LineRead it as
signatures, rulesHow many draw signatures there are, how many rules they got, and how many of those are for signatures that only the view matrix tells apart.
distancesHow many signatures have a distance where the eyes converge, and how many have none.
kinds of framesHow many scenes have a distance of their own, none, or a limit on how far apart the eyes may be.
texturesHow many textures have a copy for each eye.
resolutionCalls whose meaning depends on the size of the target (the hazards of step 2), when there are any.

What the result can mean

ResultMeaning
Exit 3The recipe cannot be baked, and the message says why. The usual cause: a signature drawn as an interface in one pass and as a scene in another, with the same view matrix (or a pass with no matrix), so that nothing known when a draw is issued tells the two apart. The message names the signature; the remedy is in the rules (draw_keys say which draws of an affected pass are an interface).
Signatures with no distanceDraws that were never in front of the camera in the capture; they use the distance of their frame's shape.
Baking againDo it whenever the capture changes. The baked part is generated: do not edit it. Without -o the recipe is written over itself, so keep the unbaked one apart.

Other exit codes: 1 bad arguments, 2 a file cannot be read, 4 the file cannot be written.

Four modes that write nothing

ModeWhat it prints
--checkWhich kinds of frames and which draw signatures of the capture the recipe does not know (exit 5). Which passes it leaves alone look like 3D scenes, or are left alone by the replay and not by the live converter (exit 6). It also lists the draw keys whose draws disagree (some in the space of the picture and some not, some over a 3D scene and some not, or some in eye space and some not: no one rule can class such a key); those change no exit code.
--overlaysAs JSON, the draws that may be 2D overlays.
--parityThe draws on which the replay and the live converter decide differently (class or push). Run it after baking: it must list none, and exit 7 says it listed some.
--scenesAs JSON, each scene with where its frames are, where the eyes converge, how far apart they may be and what that makes of the parallax of its nearest and farthest surfaces (--screen-degrees says how wide the screen is, 90 by default). It is what the comfort numbers are tuned with (Recipes).

The modes cannot be combined.

6. Check it offline

The offline replay tools take a recipe, so a recipe can be checked on the capture before it meets the program. This is the step where a person looks.

tools\stereo_replay\StereoReplayPlayer_x86.exe --recipe my_demo.json --eye both --eye-separation 0.1 --deps app.deps result_dump.workload
tools\stereo_replay\StereoReplayInspector_x86.exe result_dump.workload --recipe my_demo.json --eye-separation 0.1 --from 0 --to 200 --dump-dir out

Result: images of both eyes for frames of every shape, and a verdict on what to change.

The two tools

ToolWhat it does
StereoReplayPlayerRenders the frames for both eyes and shows the images side by side. --eye left and --eye right show one at a time. --eye-separation is 0.1 when left out, in the units of the camera of the program; the window has a slider for it. --frames A-B plays only those frames, and --deps makes a seek quicker (the file with the name of the workload and .deps is used when there is one).
StereoReplayInspectorReplays frames --from to --to (0 to 999 by default). With a recipe it executes each frame twice, the first time for the left eye and the second for the right, and compares the images with those of a replay without the recipe. --eye-separation is 0 when left out, which changes nothing: give it a value. --dump-dir receives the images of the first frame in which an execution differs.

With a recipe that changes nothing the inspector must find no difference; with the real one, differences are expected. Its other job is to say where the replay itself is unstable: a frame that cannot be executed twice is not one that stereo conversion can handle. Some frames of any program differ on a second execution; compare with the same run without the recipe before blaming the recipe.

Looking without a window

Inspector optionEffect
--screenshot FRAMES --out file.png --recipe my_demo.jsonWrites the frames, both eyes side by side: FRAMES are numbers, ranges A-B and ranges with a step A-B:S, separated by commas (569,1760-1990:10), and the replay runs once for all of them. Several frames go to files with the frame number before the extension (file_1800.png), played as --history plays; a frame the workload does not have is not written, and is said. A single frame goes to file.png; --eye left, right or anaglyph (red-cyan) says otherwise. Without --recipe it is the frame as it is.
--contact-sheet K --out sheet.pngPuts K frames spread evenly from --from to --to on one picture, and prints their numbers in the order shown.
--overlay-report candidates.json --recipe my_demo.json --dump-dir outTakes the output of RecipeBake --overlays and makes, for each draw that may be an overlay, an animation of its frame with and without the draw, to look at in index.html of --dump-dir. --deps makes it quicker.

The player and the inspector come as _x86 (for the capture of a 32-bit program, which is the one to use for Direct3D 7 and 8) and _x64.

Tuning the comfort

The comfort section of the recipe holds the numbers that step 6 changes. RecipeBake --scenes shows what they make of each scene. The recipe is baked again after each change.

OptionEffect
max_near_parallaxHow far apart the pictures of the eyes may be at the nearest surface of a scene, as a part of the width of the picture (0.03 is three in a hundred). Lower it when something near has an extreme shift.
near_fractionWhich part of the surfaces (by vertices) counts as the nearest: 0.001 by default. Make it larger to count more of them.
overlay_parallaxHow far toward the viewer the draws that the rules leave alone are pushed (0.04 is four in a hundred of the width). VR Player pushes them by it and has no control for it; 0 or leaving it out means the application wants none. Which draws are pushed is the pushed lists and, with push_unaffected, every draw the rules leave alone.
push_unaffected, push_by_defaultBoth off by default. The first pushes every draw the rules leave alone, for an application whose left-alone draws are all an overlay. The second pushes what the recipe pushes when no VR player has said whether to (a run of the converter alone).
ease_by_time, snap_at_cutsBoth off by default. The first eases the eyes toward a scene by the time that goes and not by frame; the second puts them at the new scene at once when the scene is cut to a very different one.

One more field, outside comfort: frame_pacing says what the converter does when no screen keeps time. hold_to_rate (the default, 60 frames a second) suits a program that ties its music to the clock; screen_only leaves it free. An OpenGL program that gives thousands of glBegin blocks a frame can have record_immediate_mode_blocks set to true: the converter then makes the blocks again for each eye from its own recording, not from a display list that the driver compiles for each block (the recipe fields, Recorded blocks). With the blocks recorded, render_left_then_right_eye also draws the right eye once for a run of calls instead of at each block (The right eye once for a run).

7. Try it live

Add the program to the catalog (step 8) and start it from VRPlayer. To try an entry without building again, run the release's player on the catalog of the repository, which also downloads the program into the repository's apps\<id>\:

VRPlayer.exe --catalog c:\path\to\repository\apps\apps.json --log

Result: the program running in stereo in the window of the presenter (or in the headset), and a session log to read.

Without VRPlayer

The launcher starts the program with the converter in it. Start the presenter first with the same session name when you want to see the images:

runtime\StereoPresenter_x64.exe --session test --log
runtime\StereoLauncher_x86.exe --recipe my_demo.json --session test --log --wait c:\path\to\app.exe

Result: the log, a short summary printed by the launcher when the program exits, and its exit code. Without the presenter nothing shows the second eye, and the program stays on screen as it is.

Launcher options

OptionEffect
--recipe, --sessionBoth required. The session names the playback, so that the programs that take part in it find each other.
--arguments "text"The command line of the application, as it is. Arguments after the application's path are an error.
--working-directoryWhere the application runs; the current directory by default.
--click-button "text", --untick-checkbox "text"For the dialog that a program shows before it starts: untick the checkbox, press the button (not looking at case or at &); given up after a minute. The checkbox needs the button. The catalog's launch_button and untick_checkbox are these.
--logThe converter writes a session log; without it, only why it stops the application is written.
--waitDoes not return until the application exits, and then prints its exit code (and, with --log, the summary).
Exit code0 done, 1 bad arguments, 2 the program or the converter or the recipe cannot be used, 3 (with --wait) the converter stopped the application and the log says why. The launcher has to be of the architecture of the application.

The log

ItemDetail
Where%TEMP%\apistereo_<session>.log. <session> is the --session value; VRPlayer uses its process ID and a tick count, <pid>-<ticks>.
--log on VRPlayerThe window has no control for it; the switch is passed on to the launcher and the presenter. Lines ending in “(presenter)” come from the headset path.
StatisticsOne line every 600 frames. A program that ends sooner has none.

What to look for in the log

In the logMeaning
Frames of a scene the recipe has no distance for (scene_convergence); the statistics line counts themA program that is mostly in such frames is in screens that were not in the capture (step 1).
A refusal (“The application cannot be converted:”)A rule that depends on a pass or a frame shape (pass_keys or shape_keys in the when of a rule) cannot be followed live, since neither is known when a draw is issued, and the converter then stops the application with a message instead of drawing wrong images.
A “Warning:” that unaffected.pass_keys names passesThe live converter does not know passes: it follows the draw rules that the baker made from them. RecipeBake --parity says whether the two agree.
The statistics lineThe numbers of affected, unaffected and skipped draws, of draws of a signature the recipe does not know, of frames of a scene it has no distance for, and of matrices kept, then the twins and the unmirrored calls (Direct3D 7, OpenGL), the counts of the OpenGL draws, and what the callbacks cost per frame. A large count of unknown draws means that the program draws things in play that were not in the capture.

Judge what you see in the window first and in the headset second: the window shows the same images, and it is where a fault is easiest to tell from discomfort.

8. Put it in the catalog

The catalog is apps/apps.json, and the recipes it names are in apps/recipes/. build.bat installs both into build_final\apps\, so a release has them. VRPlayer lists the programs alphabetically by name, ignoring case, and by id when names are equal.

Result: the program appears in the list of VRPlayer.

build.bat empties build_final first, which removes the programs that were downloaded into build_final\apps\, and it must not run while VRPlayer is open.

How an entry is used

The program itself is not kept in the repository: the entry says where it can be downloaded, and VRPlayer gets it the first time it is launched, into apps/<id>/ (see VR player).

The entry

Copy the baked recipe to apps/recipes/my_demo.json, and add an entry:

{
  "catalog_version": 0,
  "apps": [
    {
      "id": "my_demo",
      "title": "My demo by my group (2001)",
      "recipe": "recipes/my_demo.json",
      "executable": "my_demo/my_demo.exe",
      "download": {
        "urls": [ "https://mirror.example/my_demo.zip" ],
        "sha256": "<64 hex digits>",
        "size": 12345,
        "unpacked_size": 23456
      }
    }
  ]
}

The fields of an entry

FieldNeededMeaning
idyesLetters, digits, - and _. Unique in the catalog; it names the folder apps/<id>/ that the program is downloaded into.
recipeyesThe baked recipe, relative to the catalog.
executableyesRelative to the catalog. With a download it has to be inside apps/<id>/.
titlenoThe title in the list. Written name by group (year) in this repository. Without it: the name of the recipe's target, then the id.
argumentsnoThe command line of the application, as --arguments of the launcher.
working_directorynoRelative to the catalog. The directory of the executable by default.
launch_buttonnoThe text of a button in the dialog that the program shows first. The launcher presses it for the user, and waits up to a minute for it.
untick_checkboxnoThe text of a checkbox in that dialog, which the launcher unticks just before it presses the button. Needs launch_button. A program that asks to run full screen would otherwise change the screen resolution and cover the window that shows the images.
unavailable_reasonnoWhy the player cannot start the program although the recipe is there. The entry is listed with this reason.
downloadnoWhere the program comes from when it is not there (below).

The fields of download

FieldNeededMeaning
urlsyesA list of addresses, at least one, all https://. They are tried one after the other until one works.
sha256yesOf the zip file, 64 hex digits. A file that does not hash to it is not used.
sizeyesBytes of the zip file (a whole number, 1 to 4294967296). It is the total of the progress bar, and the hash decides what is used.
unpacked_sizeyesThe most that the unpacked files may take together (same range). A zip file that holds more is not unpacked.
pagenoWhere the program can be got by hand. It is named in the message when no address works.

The contents of the zip file are unpacked into apps/<id>/, so executable is <id>/ followed by the path of the program inside the zip file. Get its sha256 from a copy you trust (certutil -hashfile my_demo.zip SHA256), and check that the program may be downloaded by whoever uses the catalog. The recipe's target.description, when there is one, is shown under the title.

What makes an entry or the catalog unusable

FaultResult
The recipe cannot be found or is not validThe entry is listed as unavailable, with the reason.
The executable cannot be found and the entry has no downloadThe entry is listed as unavailable, with the reason.
A field the loader does not know, a missing id, recipe or executable, an id with other characters or one that another entry has, a catalog_version that is not 0The whole catalog is unreadable (the window says why).
A download without urls, sha256, size or unpacked_size, an address that is not https, a hash that is not 64 hex digitsThe whole catalog is unreadable.
An executable outside apps/<id>/ in an entry with a downloadThe whole catalog is unreadable.

Doing it again

A recipe is made for one version of a program.

The program changes, or a screen is missing

Capture again (step 1), extract again, and give the model the new analysis and the old recipe. Keys of passes whose structure did not change are the same, so what is already decided stays decided, and the model only has to look at what is new (the shapes and passes not in known_shape_keys).

The analysis tools change the keys

key_scheme_version changes, the loader refuses the old recipe, and the whole of steps 2 to 5 is done again from the same capture.

What this does not cover

LimitDetail
A Direct3D 8 camera has to be set with SetTransformThe live converter acts on IDirect3DDevice8::SetTransform. The loader accepts a rule on IDirect3DDevice7::SetTransform too (transform states D3DTRANSFORMSTATE_VIEW and so on), but a Direct3D 7 program is converted live only with vertices in pixels (next row). A program that passes its matrices to a vertex shader as constants (SetVertexShaderConstant) has a camera that the converter cannot move: the analysis follows such constants, but a rule that changes them is new work in the loader, the baker and the converter, not a recipe.
Direct3D 7 for vertices in pixels onlyA Direct3D 7 program whose vertices a matrix moves has no adapter (see Direct3D 7).
Direct3D 8 draws with vertices in pixelsThey are moved for each eye when the vertices come with the call (DrawPrimitiveUP, DrawIndexedPrimitiveUP); those from a vertex buffer end the application.
OpenGL of the fixed functionA camera that is the model-view matrix is converted (see OpenGL). A program that loads its cameras inside display lists, or has more than one context, is not tried. See What is supported.
The LLM reads facts; it does not see the programA fault that the facts cannot show (a pass that is an interface in some frames and a scene in others, with the same structure) is found by a person, in step 6.

Checklist

  • Captured every screen of the program.
  • info: no unfollowed or unsupported calls, no key collisions, hazards understood, a small number of shapes.
  • Every pass has a decision with evidence; the unclear ones are settled by a person.
  • The recipe's keys are all from the query output; known_shape_keys are the shapes of the capture.
  • Baked without error; the signatures without a distance are understood.
  • RecipeBake --check knows every shape and signature, and --parity lists no draw.
  • StereoReplayPlayer shows no doubled interface and a scene with depth, in both eyes, on frames of every shape.
  • The live session log shows no refusal and few unknown frames or draws.
  • The recipe is in apps/recipes/, the entry (with where the program is downloaded from, and its hash) in apps/apps.json, and VRPlayer lists the program as available.
