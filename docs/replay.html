Replay

Executing the calls of a workload again, without the program. Here it is done for both eyes: it is where recipes are tried, where a frame is checked to be drawable twice, and the proving ground for everything the live converter will later do inside a running program.

The engine

The replay engine belongs to API Interceptor (ReplayEngineCore, a static library; see its documentation). It walks the calls of a workload one after the other with an executor for each API, and knows nothing of stereo. What this project adds goes in through two interfaces of the engine: an IFrameExecutor, which plays the calls of a frame (the engine presents the frame and pauses between two), and the executors of the calls, which a class can derive from. The result is StereoReplayEngineDLL.

Two eyes

With a recipe, the engine executes every frame twice. The recipe tells, for each draw, whether it is drawn once, for each eye, or not at all (RecipeApplier), and the matrices of the eye are bound to the draws that are drawn per eye (EyeMatrixBinder), by the rules of Stereo. A frame is rewritten (FrameRewriter) before it is run, and the two images go to a sink, which is how the player shows them.

  • The state put back. save_state and restore_state are a state block in Direct3D 8; Direct3D 7 has none, so what the replayed calls set is kept.
  • Per-eye textures. A texture that is rendered to, and that a frame uses what an earlier frame left in (per_eye_textures of the recipe), has a copy for each eye: the executor makes it twice when the application makes it, sets the copy up with the same calls, and plays the calls of each eye on its own copy, so what an eye's frame renders is what that eye's next frame reads.
  • Vertices in pixels. A program whose vertices no matrix moves (Kasparov) has no matrix to give the eyes; the engine moves the x of each vertex of an affected Direct3D 7 draw before it is played (D3D7DrawRewriter, using Stereo::D3D7::ScreenParallax), by the screen-space formula. A draw into a texture is moved like any other, so the texture is the picture of the eye; the quad that draws the texture to the screen is flat and stays.

Seeking

There is no way to jump into the middle of a workload: the state of the device is made by every call before it. A frame back in time starts the replay over; a frame ahead is reached by hurrying through the frames before it, unpaced, not presented and not read back. A seek is then as long as the replay up to the frame, which for a long capture is long. The dependencies make most of it unnecessary.

  • What it needs: the .deps file of the workload (APIDumpDependencyExtractor; the player takes the file of the workload's name, or --deps), and for the chunk skipping the .index of the workload (APIDumpPrinter --index); without the index every chunk is read.
  • Planned by FrameSlicePlanner, carried out by SliceSkipper.
  • Correctness is checked rather than assumed: the image of the target frame of a seek with the dependencies must be byte for byte that of the replay of every frame. The checker's screenshots, with --deps and without, are how to check it.
  • A capture where every frame reads what the previous one wrote (fr08) gains nothing: no frame is dead.
  • Frames are counted as the converter counts them live (the window of a running converter says Frame N), so a frame seen there can be typed here.

The programs

ProgramWhat it is
StereoReplayPlayerA window (ImGui, through UIHost of Utils) around the engine: choose a workload and optionally a recipe, play and pause, see both eyes in a preview. It has a seek bar (a slider, a step, and a box to type a frame in; g <frame> with --console); while a seek is under way the status says seeking, and paused once the frame is reached. A frame back in time asks first. The eye separation slider changes the distance for the frames from then on; when it is let go of while paused, the frame on show is played again.
StereoReplayConsistencyCheckerNo window. Replays a workload several ways and compares the images; takes screenshots; profiles; makes the overlay probe. Its modes are in the next section.

In the release (see Building) the engine and the two programs are in tools\stereo_replay\, each as _x64 and _x86; a 64-bit player starts the 32-bit one for a 32-bit workload, and the 32-bit ones replay the Direct3D 7 and 8 captures, which are of 32-bit programs. In the source they are in src/tools/stereo_replay, in engine_dll, player and consistency_checker.

What the checker is for

The checker is the test that the engine is fit for stereo: that a replay is repeatable, and that a frame executed twice draws the same as once. It is also where everything else about a recipe is tried without a window.

ModeSays
(none) with --ways, --parallelReplays the frames as they are, again, executed twice, with the state put back, and for the eyes of the recipe; hashes each frame's image and compares the ways. It can write the images of the first frame that differs, with an image of the pixels that differ. Each way is a replay from the start; --parallel replays them at the same time, each with an engine of its own.
--screenshot N --out f.pngOne frame as a PNG: with a recipe both eyes side by side (or --eye left, right, anaglyph), without one the frame as it is. Frames before N are played once for the left eye unless --history is given; --deps makes it quick and exact.
--contact-sheet K --out f.pngOne PNG of K frames spread evenly over a range, each as a screenshot is.
--same-frames-as other.workloadWhether two workloads give the same images (exit code 3 if not): how a slice is checked against its workload.
--profileWhere the time of the calls went: the functions and the frames that took longest.
--overlay-probe candidates.jsonOf the draws that may be 2D overlays (RecipeBake --overlays), which ones really make pixels: the frame where each is first seen is replayed with the draw and without it (the recipe skips it), and the images are compared. It writes an animated GIF, a still, a JSON and an index.html per run, and flags a draw that the recipe leaves alone but is deep or covers much of the picture. The work can be shared between processes (--jobs N).

The checker's source has a file for each of these ways of working (replay_runner, comparison, screenshot_mode, profile_mode, overlay_probe_mode), a command_line that has tests, and a main.cpp that loads the recipe and chooses.
