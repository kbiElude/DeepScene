Analysis

A workload says what a program did. The analysis says what it meant: which draws make the scene, which the interface, how deep the scene is, and which frames depend on which. It lives in src/libs/analysis.

What it is for

For stereo the converter needs two things for every draw: whether it is part of the 3D scene (to be drawn once per eye) or flat (drawn once), and the convergence distance of the scene it is in. The program does not say either. The analysis reads the capture once and records the facts from which both are decided, and the recipe keeps the decision in a form the live converter can follow. The analysis itself never judges: which passes are an interface is for the recipe, by rules, or by the person who writes them.

The model

A capture of a demo has hundreds of thousands of frames but only a few dozen kinds of frames. The model is built around that: what is kept grows with the variety of what the program did, not with the length of the capture.

How a call goes through

AnalysisSession::run() reads the workload one segment at a time (a block of calls with their data chunks, as the dumper cut it) and works on the one in hand; reader threads may have the next few ready, which changes nothing in the result. For each call it takes the API group, counts the call under it, tells the model builder which call this is (so that everything that comes out can be traced to a call index and time), hands the call to the front end of the group, and notes whether the call ended a frame. The totals it keeps include calls unfollowed (an object the front end does not know, or arguments it could not read) and unsupported (things it does not follow at all); both mean that what was found may be wrong, and a good capture has none.

One front end per API

A front end follows the state of one API and reports what its calls come to, with everything resolved: a draw is reported with the resources it uses, not with the calls that bound them. It is the only part of the analysis that knows what a function is called, what its arguments mean, or what state a device has. The contract is IAPIFrontend::on_call and a fixed set of events to the model builder:

EventMeaning
on_create_resource, on_destroy_resourceA resource appears or goes, with its description.
on_set_attachments, on_set_viewportWhat is rendered to, and where.
on_update_constantA constant takes a value, with a meaning if the front end knows one (a matrix of the model, the view, the projection).
on_clear, on_copy, on_uploadWork that touches a resource and is not a draw.
on_drawA draw, described with every resource and piece of state it uses.
on_texture_eventWhat happens to a texture (see What happens to the textures); only when something listens.
on_frame_presentedThe frame ends.

What a front end must not do is let its API show through. The shared vocabulary is chosen so that more than one API can say what it means in it: a binding point (where a resource is bound, in three numbers), a constant location (a range of bytes in a block of one of four kinds: a buffer, loose shader constants, fixed-function state, push constants), a resource with a format class (colour, compressed, depth, depth-stencil), shader stages that include compute and tessellation, and resolution hazards (calls whose meaning depends on the size of the target in pixels, which say whether the program can be rendered larger without noticing). Some of this room is not used by the front ends that exist; it is there so that adding an API does not mean changing the model.

Direct3D 8, Direct3D 7 and OpenGL have front ends, in api_dump_analysis/frontends/D3D8, .../D3D7 and .../OpenGL. What they share is in frontends/shared: the call view and the report of a call that cannot be followed (all three), and, for the two Direct3D ones, the object tracker (what is alive at which address, and what it is in the model; an address is forgotten when its object is released), FixedFunctionState (the fixed-function pipeline's state, from which the state key is made), IFixedFunctionFrontend, the base class that follows the objects and that state for both, and GeometrySampler, which picks a few dozen vertices of a draw (spread over it, from the vertex and index bytes a geometry tracker kept, described by a GeometrySamplingRange) for the surface depth; the Direct3D 8 and 7 geometry trackers use it, and the OpenGL front end has a sampler of its own (GLGeometrySampler). What differs is what a resource is: in Direct3D 8 a texture, vertex buffer or surface; in Direct3D 7 a DirectDraw surface, whose roles (primary, back buffer, depth, texture) come from its caps. The OpenGL front end follows the contexts (which one each thread has current, and the state of each), the window as the default framebuffer (made at the first clear, with the size of the viewport by then), the viewport, the scissor box and test, the values a clear uses, the stack of attributes (glPopAttrib puts back what the program set after the glPushAttrib, as far as the mask says), the matrices (a stack each for the model-view, the projection, and the texture and color ones, which are only kept right), the draws of arrays (glDrawArrays and glDrawElements: the dumper stores the part of each array that the draw reads, and the front end makes a buffer resource of each array and of the indices, once for each different bytes, so that the same data is the same resource in any draw or frame, and keeps the bytes of each: those of a piece are kept for the frame it is seen in (each eye of a stereo frame draws it), and on if the piece is seen in a second frame, which is reuse across frames; such a buffer is told apart in the match key by its kind alone, is_application_memory, so that a draw is told apart by its layout, topology and state and not by the bytes it reads), the draws of immediate mode (one draw for each glBegin and glEnd with vertices in them, of the topology that its mode makes, and of the pipeline state that was set when it ended: the enabled capabilities, the depth, alpha and blend functions, the masks, the culling and polygon modes and the shade model), the textures (a texture of the program is a resource once its first glTexImage2D gives it a size, the pixels in the call are an upload, and a draw samples the texture that each texture unit has bound if the unit has the target enabled; enabling is per unit, as glActiveTexture says, and what is bound is saved by glPushAttrib), the copies of the window to textures (glCopyTexImage2D and glCopyTexSubImage2D: the color of the window, or its depth for a texture of depth, is read and the level of the texture written, which ends the pass that rendered the window; a texture that is written by a copy and read in the same frame is frame local), the clears, and the end of the frames (SwapBuffers, a function of GDI32). What depends on the size of the window in pixels is counted as resolution hazards: copies, partial clears (a scissor test on with a box that is not the window), scissor boxes, widths of lines, sizes of points, and reads of pixels. A display list is followed: the calls made between glNewList and glEndList are kept in it, with the data that they refer to (the workload they were made in is let go of before the list is called), and made again at each glCallList, whatever the state is then, and at once too for GL_COMPILE_AND_EXECUTE; the lists of the contexts are shared, as wglShareLists makes them, a list that calls itself is stopped at a depth of 64, and each list is told what it does to what an eye has of its own (GLListEyeDependence): a list that only draws and sets state, or moves the matrices relative to the current ones, is the same for both eyes of a stereo frame, and one that loads a matrix, sets a projection, a viewport or a scissor box has values of its own, so that a replay has to make it for each eye (a list that calls another is what the other is, and one that calls a list that is not defined is taken for the worst). OpenGL has one matrix for the model and the view together and a projection of its own, so the front end tells the model builder the two as they are, each when it changes: MODEL_VIEW_MATRIX and PROJECTION_MATRIX, defined by the API, in the state of the fixed-function pipeline; it does not tell a model from a view, and a draw is of a right-handed camera, so that its depth is the distance in front of the eye. It does not follow glCallLists, glBitmap, glDrawPixels or glCopyPixels, which end the process with a message that says the function. A read of the framebuffer (glReadPixels) is counted as a resolution hazard (pixel readbacks); what the program makes of the pixels is in the calls that follow. AnalysisSession routes calls to the three front ends. Adding one is described in Contributing.

Passes and draws

The model builder works with passes. A pass starts with the first draw or clear after the previous pass ended, and ends when what is rendered to changes, when a clear or a viewport change comes after a draw, when a copy reads or writes what the pass renders to (or an upload writes it), or when the frame ends. A buffer written between two draws does not end a pass.

When a pass ends its pass structure is made: where it renders to and how, the kinds of draws it holds (sorted, each once) and the constants in effect (by what they are, not their values). A draw is described twice. The draw structure says what the draw is: the keys of its buffers, shaders and textures, its state, vertex layout and topology, with the counts left out. The draw signature says what the draw is at the moment it is issued, which is all a live converter can know.

Keys

Addresses, creation order and times differ from run to run, and several threads can change the order of creation calls. Everything the analysis stores as an identity is therefore a key: a 64-bit digest of the values that make the thing what it is, which comes out the same in another run. The rule for what is hashed (Hasher in libs/utils/hashing: integers little-endian, floats by their bits, sizes with what has a variable size) must never change, since keys are written into .passes files and recipes. A hash is the digest of bytes (the contents of a resource, the code of a shader; Hasher::hash_bytes takes an AVX2 path for big data on a processor that has it, which gives the same digest as the plain one); a key is the identity of a structure, built from values by KeyBuilder, and can contain hashes.

The one that matters most is the draw signature key. The pass a draw belongs to is not known until the pass ends, so the signature uses the unwritten keys of the structure and the targets. It is what a live converter can match, and what a recipe's rules are about: the same code makes the keys offline and in the running program, so a rule baked from a capture matches a draw of the program as it runs. Two different structures with the same key are possible in principle; they are counted and compared when interned, so a collision does no harm beyond the count.

The depth of a draw

When a draw is made, the builder also works out how deep it is and counts it into the depth histogram of the open pass (and the x scale of a perspective projection, weighted by vertices, into a mean for the pass: how wide the picture is, in the PROJ section of the file, which the comfort of a recipe needs), from which the recipe's convergence distances come.

  • Depth is the translation of the model matrix (the identity if none was set), carried through the view matrix. It is only worked out for a pass with a view matrix and a perspective projection: an orthographic one has nothing to converge at.
  • Weight is the vertex count, so a large object counts for more than a particle. Bins are logarithmic, eight to each doubling of the distance from 1/128 to 217 (192 bins); a draw behind the camera or nearer than the first bin is not counted, and one beyond the last bin is counted in it.
  • Surface depth is the same measure for the vertices of the draw. The origin of a large mesh can be far away, or behind the camera, while its walls are close (a tunnel made of a few polygons around the camera), so the front end also follows what is written to vertex and index buffers and, for a draw, samples up to 64 of its vertices (GeometrySampler), carries each to camera space and counts it if it is in front of the near plane and inside the view. The Direct3D 8 and Direct3D 7 front ends read the positions of vertices in model space (the first three floats of a vertex) and pre-transformed vertices (x and y in pixels, and the reciprocal of the depth), whose depth comes from that reciprocal and which are measured against the viewport instead of a projection. Direct3D 8 reads them from the buffers of a draw and from the memory of the application that a DrawPrimitiveUP or DrawIndexedPrimitiveUP call brings with it; Direct3D 7 from the vertices that come with its draw calls. Vertex-shader inputs are not read. This is done only by the offline analysis, which has the time: the converter inside a program keeps no buffers and reads no vertex. The depth of the origin and of the surfaces, the width of the picture, whether a draw reaches the edges of the view, and the facts of a draw structure are measured by DrawMeasurer (api_dump_analysis/draw_measurer.h), which keeps nothing: the model builder says what the draw is made with (the constants, the viewport) and where the results go.
  • Covering the view. A draw whose vertices reach all four edges of the picture (within half a percent) is a flash or a fade, and must not be pushed or moved sideways. A signature does not tell them from text (both go through one dynamic buffer with one state), so the key used is the signature and the size of the draw, kept if any draw with it covered the view and baked as covering_draws. A key is not proof, so the converter also looks at the vertices the draw uses. The baker also lists the draws that are flat (at one depth) and whose footprint, as the facts of the draws kept it, reaches both the left and the right edge, as side_reaching_draws: the bars and scrollers of a 2D pass, which a push moves with the picture made wider by it.
  • Layers, overlays and eye space. The facts also count, for each key, the draws that are made in the space of the picture (pre-transformed vertices, or an orthographic projection), the draws that come after a draw with a perspective projection and a camera in the same frame, and the draws whose object is at the camera (the origin of the model-view is at the depth of 0, so that it looks attached to it) while all the sampled vertices are in front of the camera at a real depth. What the facts say comes from the matrices and the vertices as the front end gives them, never from a call of an API, so one rule serves Direct3D and OpenGL alike. For a recipe with comfort.automatic_layers the baker lists the keys it finds: flat_layer_draws (in the space of the picture, and not always over a 3D scene, or working on a copy of the picture), overlay_draws (in the space of the picture, always over a 3D scene) and eye_space_draws. A key counts only if all of its draws agree. The facts are section version 2 of the .passes file, so a file made before has to be analysed again.

Frames, shapes and what is recorded

A present ends a frame. The builder then ends the open pass, makes the frame's shape (the sorted numbers of its pass structures; order is ignored, since independent passes may run in any order) and interns it, so a frame becomes a small record that points at its shape; it adds the depth histogram of each pass to the one of the same pass structure in the same shape; it closes the books on resource access; and it keeps the detail of the frame (the instance of each pass, the copies and uploads between them) only if it is a representative frame of its shape: the first frame of the shape, then the lightest and the heaviest by draw count if those are others.

  • Resource access (ResourceAccessTracker): for each resource, its first read and first and last write, and in how many frames it was read, written and loop carried (read before it was written in the frame, and written in it: what feedback effects do). It is classed loop carried, unused, unread, static (made once and read afterwards) or frame local. This tells what a replay must carry from one frame to the next.
  • Camera constants are tracked only when the front end gave them a meaning; the camera ones are recorded as a time series per pass structure, a sample only when the value changes.
  • The timeline (built when a query asks): frames in time order as runs of one shape, how often each shape and pass occurs, and the setup frames, which are much longer than a typical frame.

Dependencies between frames

The model says what the passes of a frame are, not how frames depend on each other, which a stereo replay needs: a frame played once per eye reads what the frame before it left in the resources, and that is not the same for both eyes if the frame before rendered it. The dependencies are made apart, by a pass of their own over the workload, and kept in a .deps file.

The model builder tells every use of a resource to a sink (IAccessSink): what it is used as, whether it is read, written or both, how much of it a write reaches, which part, on which queue. The front ends only translate their calls into these events, so a front end for another API makes the dependencies without the analysis knowing it. From them the DependencyAnalyzer says, for each resource and frame, whether the frame uses what an earlier frame left in it: certainly, possibly (only part was written first, or how much is not known), or not at all. It can only over-report what is carried, never under-report it.

For a resource whose writes all say where they land (a copy and an upload tell the rectangle of the level they reach), the file also keeps the rectangle that each frame wrote (written_rectangle_vec of each version) and the one that holds all of them (written_extent). And for such a resource it keeps, for each version, the resources whose content before the frame flows into it through the calls of the frame, in the order they are made in (input_resource_vec): a draw that samples a texture after the copy to the resource has no part in the version, and one that samples it before does, in which case the version says nothing and its writer is taken to need all that it uses. APIDumpDependencyQuery resource prints both.

  • Per-eye textures. A resource needs a copy for each eye when it is rendered to and some frame uses what an earlier frame left in it, whether that frame writes it too or not. RecipeBake --deps puts them in the recipe. Targets that frames write by turns (a double buffer, a swap chain's images) are a rotation group and are listed together, so an eye never finds what another eye's frame rendered.
  • Dead frames. A frame is dead for a seek if nothing the target frame or any later frame reads comes of it. The replay uses this to leave out most of the work when it jumps to a frame (Replay).

What happens to the textures

A .textures file says what each level of each texture of a workload holds, and when. The front end of an API tells the model builder (ITextureSink) each event of a texture, with the call and the frame it is in, and TextureCollector keeps them in the order of the calls. An event covers a region of a level (x, y, width and height are in texels, whatever the format; a region of a compressed texture starts on a block and ends on one or at the edge of the level), a run of layers (slices of an array or a volume, faces of a cube), and a sample if the texture is multisampled; it carries the size, the format and the depth or layer count that the level has after it, so that a texture that is specified again, or changed in a part, has the content of each moment told. The kinds of event are:

  • Upload. The pixels of a call are the content of a region. They are in the workload already, so the file keeps no copy: the table of contents has the data chunk, with the size and two hashes of the bytes, and a reader that takes the chunk from the workload can tell that it is the one. An upload with a null pointer gives the level a size and no content: the dumper makes a data chunk of every pointer to pixels, and of a null pointer one that has no bytes, so a chunk with no bytes is that (a texture that is to be copied to, as the one of 1024 by 512 texels that Gerbera makes).
  • Render write. A copy from the window. The window (the swapchain) is never stored.
  • Generated levels. glGenerateMipmap and GL_GENERATE_MIPMAP make the levels below the first, each told as an event, and to the dependencies as a copy of the level above.
  • Snapshot. The first time that something reads a level whose content is not in the workload (rendering made it, or the driver did) after it changed, its content at that call is to be kept: a snapshot point. A change of such a level, by a copy, a part laid over it or the making of levels, makes it be read again the next time it is read. A snapshot covers the smallest rectangle that holds what rendering has made of the level since it was given (a level that is given a size and no pixels, then filled in a part by copies, is snapshot in that part, not whole), and the whole level for the levels that the driver makes. The analysis only says where the points are. Keeping what rendering made would take a replay that reads the textures back; APIDumpTextureExtractor --include-render-content asks for it, and the program ends with a message instead of writing a file that lacks it (APIDumpTextureQuery info shows includes_render_content, which is false).

The formats are named in the words of no API (Utils::Graphics::TextureFormat, with the block, the bytes and whether it is compressed, has depth or stencil, or is sRGB); the front end of each API turns its own values into them, and keeps the value of the API beside a format it does not know. What a content that is stored is made of is kept in the file of blobs, the name of the .textures file with .data after it: each content a Zstandard frame with a checksum, after a filter that loses nothing, once for each content.

The front end of OpenGL follows GL_TEXTURE_2D textures: their levels, the pixels given to them (with the rows laid out as glPixelStorei says), the parts of levels, what is copied to them, and the levels the driver makes. A texture of another target (cube maps, volumes, arrays, multisampled ones), compressed images, fixed storage, a texture that is a part of a framebuffer, and pixels that go to a buffer or come from one end the process with a message that says the function; a parameter that decides the levels is followed only for GL_TEXTURE_2D (GL_TEXTURE_BASE_LEVEL other than 0 ends it too). Only the OpenGL front end tells the textures; the Direct3D ones send no texture events, so their .textures files are empty of events. The calls about textures are followed by GLTextureHandler (frontends/OpenGL/gl_texture_handler.h), which keeps the textures and their parameters; the front end keeps the window, so it makes the copies of the window to a texture, with the parts of the handler that make a level.

The files, and the same analysis live

The model, the summary and the reference to the workload make an AnalysisResult, which PassesFile writes. Each section is serialized in its own thread and compressed with Zstandard; its header carries the size, the tag, the version and an XXH64 of the raw bytes. The file is written beside the real one and takes its place when complete, so a failure leaves the old file as it was. A reader skips sections it does not know and refuses a known section of another version, and checks what a file this code wrote must satisfy (sizes that fit, resource IDs consecutive, structures in order); one that fails is refused. The sections are listed in passes_format.h. The container is the same for the other files: SectionedFile (sectioned_file.h) packs and reads the sections of .passes, .deps and .textures, and writes the file beside the real one. .passes starts with a header of its own (a magic, the file version and the key scheme version, which a reader must find equal to its own); .deps and .textures start with the AnalysisFileHeader (a magic, the file version and the analysis version), which SectionedFile::check_analysis_header checks against the AnalysisFileKind of the reader; their sections are listed in deps_format.h and textures_format.h. Each file remembers which workload it is of (its size and hashes of 4 KiB from its start, middle and end), and the query tools refuse the wrong capture.

The three extractors share one flow (ExtractorTool::run): read the arguments, read the workload with an AnalysisSession while the progress is printed, say once if the workload ends in the middle of a segment, then do the program's own step with what the session found. They take -o, --max-frames, --progress-interval, --stats and --threads (and --skip-chunks-above, which the texture extractor refuses, since the pixels it needs are in the data chunks), and exit with 0 (done), 1 (bad arguments), 2 (workload cannot be read), 3 (output cannot be written) or 4 (the texture extractor only: what the workload holds of the textures could not all be kept). The warning about a cut workload, and the is_truncated that .passes and .deps keep and info shows, are about the file ending early: a run that stops at --max-frames before the end is not truncated. The three query programs share one flow too (QueryTool::run): read the file, check it against the workload it names (--no-verify skips that, --workload says where the workload is; a workload that cannot be found is not an error), ask, print JSON. They take --compact, --limit (default 100, 0 is all) and --offset, and exit with 0 (done), 1 (bad arguments), 2 (file cannot be read), 3 (nothing there by that id) or 4 (wrong workload).

The converter inside a program runs the same AnalysisSession, fed by CallFeeder with the calls as they are made, built without history: no frame records, no representative detail, no camera series. What it keeps grows only with the kinds of frames, passes and draws. It needs two things the running program provides: the draw signature of each draw, as it is issued, to match against the recipe, and the shape key of each frame, when the present is made, to ease toward the scene's convergence distance.

What it does not do

  • Only Direct3D 8 and Direct3D 7 have a complete front end. The one of OpenGL follows the contexts, the matrices, the clears, the frames, the draws of immediate mode and of arrays, the display lists, and the textures that are GL_TEXTURE_2D (their levels, the pixels that are given them, what is copied to them, the levels that the driver makes). It follows no more than that, and it does not pass over what it does not follow: a function that it neither follows nor knows to be of no matter (a shader, a buffer object, an evaluator, the selection, an accumulation buffer, a rectangle, what changes how pixels are converted, glCallLists, glBitmap, glDrawPixels, glCopyPixels), a texture of another target or a kind that it does not follow (cube maps, volumes, arrays, multisampled and compressed ones, a texture that is a part of a framebuffer), and pixels that go to a buffer or come from one end the process with a message that says the function (AI_ASSERT_ALWAYS). What it leaves out on purpose has a reason in GLFunctionPolicy: the values for the vertices that follow, the state of the arrays that a draw reads (the draw comes with a snapshot of them), names, the state of the rendering that only changes how a draw looks (lighting, fog, texture environment, polygon offset and the like), and the queries. What is made relative to the model-view matrix of the moment (the position of a light, a clip plane, the raster position) is let through, and told as such to the lists (GLFunctionPolicy::bakes_current_matrix). The state that decides what a draw writes, or how its pixels are combined with what is there (the stencil test and what it does, the logic op, the blend equation, the winding of faces), is not followed and ends the process too (GLFunctionPolicy::changes_what_a_draw_writes): a frame that has only such a draw could be taken for one that writes nothing. Reads of pixels into the memory of the program are counted: what the program makes of them is in the calls that follow. Calls of an API that has no front end are counted and skipped.
  • The Direct3D front ends do not pass over a call either. Each function is followed, or left out on purpose with a reason in D3D8FunctionPolicy or D3D7FunctionPolicy (the queries, the hints about where the driver keeps a resource, the state that only changes how a draw looks such as materials and clip planes, the display-only calls such as gamma and the cursor, and the locks, whose data is stored with the unlock), or it ends the process with a message that says the function and why (AI_ASSERT_ALWAYS). Those are: state blocks, MultiplyTransform, ProcessVertices, palettes, and in Direct3D 8 also patches, additional swap chains, GetFrontBuffer, volume unlocks and the vertex and pixel shader constants (which can be the matrices that a replay for the other eye has to change); in Direct3D 7 also overlays, GDI contexts of surfaces, color keys, DeleteAttachedSurface, BltBatch, SetSurfaceDesc and the calls that restore surfaces or try or change the display mode. A call that failed changed nothing and is passed over. The tests keep the list of the functions that are followed against the two tables, so that a function that nobody decided on is found.
  • It never reads pixels: contents appear only as the hash in a resource's description key. Vertices are read, while the file is made, for the surface depth (a sample of each draw), and only histograms are kept.
  • It does not judge. Scene against interface is for the recipe.
