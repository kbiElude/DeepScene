Analysis

A workload says what a program did. The analysis says what it meant: which draws make the scene, which the interface, how deep the scene is, and which frames depend on which. It lives in libs/analysis.

What it is for

For stereo the converter needs two things for every draw: whether it is part of the 3D scene (to be drawn once per eye) or flat (drawn once), and the convergence distance of the scene it is in. The program will not say either. The analysis reads the capture once and records the facts from which both are decided, and the recipe keeps the decision in a form the live converter can follow. The analysis itself never judges: which passes are an interface is for the recipe, by rules, or by the person who writes them.

The model

A capture of a demo has hundreds of thousands of frames but only a few dozen kinds of frames. The model is built around that: what is kept grows with the variety of what the program did, not with the length of the capture.

How a call goes through

AnalysisSession::run() reads the workload one segment at a time (a block of calls with their data chunks, as the dumper cut it) and never holds more than the one in hand. For each call it takes the API group, counts the call under it, tells the model builder which call this is (so that everything that comes out can be traced to a call index and time), hands the call to the front end of the group, and notes whether the call ended a frame. The totals it keeps include calls unfollowed (an object the front end does not know, or arguments it could not read) and unsupported (things it does not follow at all); both mean that what was found may be wrong, and a good capture has none.

One front end per API

A front end follows the state of one API and reports what its calls come to, with everything resolved: a draw is reported with the resources it uses, not with the calls that bound them. It is the only part of the analysis that knows what a function is called, what its arguments mean, or what state a device has. The contract is IAPIFrontend::on_call and a fixed set of events to the model builder:

EventMeaning
on_create_resource, on_destroy_resourceA resource appears or goes, with its description.
on_set_attachments, on_set_viewportWhat is rendered to, and where.
on_update_constantA constant takes a value, with a meaning if the front end knows one (a matrix of the model, the view, the projection).
on_clear, on_copy, on_uploadWork that touches a resource and is not a draw.
on_drawA draw, described with every resource and piece of state it uses.
on_frame_presentedThe frame ends.

What a front end must not do is let its API show through. The shared vocabulary is chosen so that more than one API can say what it means in it: a binding point (where a resource is bound, in three numbers), a constant location (a range of bytes in a block of one of four kinds: a buffer, loose shader constants, fixed-function state, push constants), a resource with a format class (colour, compressed, depth, depth-stencil), shader stages that include compute and tessellation, and resolution hazards (calls whose meaning depends on the size of the target in pixels, which say whether the program can be rendered larger without noticing). Some of this room is unused today; it is there so that adding an API does not mean changing the model.

Direct3D 8 and Direct3D 7 have front ends, in frontends/d3d8 and frontends/d3d7. What they share is in frontends/shared: the call view, the object tracker (what is alive at which address, and what it is in the model; an address is forgotten when its object is released), FixedFunctionState (the fixed-function pipeline's state, from which the state key is made) and FixedFunctionFrontend, the base class that follows the objects and that state for both. What differs is what a resource is: in Direct3D 8 a texture, vertex buffer or surface; in Direct3D 7 a DirectDraw surface, whose roles (primary, back buffer, depth, texture) come from its caps. AnalysisSession routes calls to them. Adding one is described in Contributing.

Passes and draws

The model builder works with passes. A pass starts with the first draw or clear after the previous pass ended, and ends when what is rendered to changes, when a clear or a viewport change comes after a draw, when a copy or an upload touches what the pass renders to, or when the frame ends. A buffer written between two draws does not end a pass.

When a pass ends its pass structure is made: where it renders to and how, the kinds of draws it holds (sorted, each once) and the constants in effect (by what they are, not their values). A draw is described twice. The draw structure says what the draw is: the keys of its buffers, shaders and textures, its state, vertex layout and topology, with the counts left out. The draw signature says what the draw is at the moment it is issued, which is all a live converter can know.

Keys

Addresses, creation order and times differ from run to run, and several threads can change the order of creation calls. Everything the analysis stores as an identity is therefore a key: a 64-bit digest of the values that make the thing what it is, which comes out the same in another run. The rule for what is hashed (Hasher in libs/utils/hashing: integers little-endian, floats by their bits, sizes with what has a variable size) must never change, since keys are written into .passes files and recipes. A hash is the digest of bytes (the contents of a resource, the code of a shader); a key is the identity of a structure, built from values by KeyBuilder, and can contain hashes.

The one that matters most is the draw signature key. The pass a draw belongs to is not known until the pass ends, so the signature uses the unwritten keys of the structure and the targets. It is what a live converter can match, and what a recipe's rules are about: the same code makes the keys offline and in the running program, so a rule baked from a capture matches a draw of the program as it runs. Two different structures with the same key are possible in principle; they are counted and compared when interned, so a collision does no harm beyond the count.

The depth of a draw

When a draw is made, the builder also works out how deep it is and counts it into the depth histogram of the open pass, from which the recipe's convergence distances come.

  • Depth is the translation of the model matrix (the identity if none was set), carried through the view matrix. It is only worked out for a pass with a view matrix and a perspective projection: an orthographic one has nothing to converge at.
  • Weight is the vertex count, so a large object counts for more than a particle. Bins are logarithmic, eight to each doubling of the distance from 1/128 to 217 (192 bins); a draw behind the camera or nearer than the first bin is not counted.
  • Surface depth is the same measure for the vertices of the draw. The origin of a large mesh can be far away, or behind the camera, while its walls are close (a tunnel made of a few polygons around the camera), so the front end also follows what is written to vertex and index buffers and, for a draw, samples up to 64 of its vertices, carries each to camera space and counts it if it is in front of the near plane and inside the view. Only positions in model space are read; pre-transformed vertices and vertex-shader inputs are not. This is done only by the offline analysis, which has the time: the converter inside a program keeps no buffers and reads no vertex.
  • Covering the view. A draw whose vertices reach all four edges of the picture (within half a percent) is a flash or a fade, and must not be pushed or moved sideways. A signature does not tell them from text (both go through one dynamic buffer with one state), so the key used is the signature and the size of the draw, kept if any draw with it covered the view and baked as covering_draws. A key is not proof, so the converter also looks at the vertices the draw uses.

Frames, shapes and what is recorded

A present ends a frame. The builder then ends the open pass, makes the frame's shape (the sorted numbers of its pass structures; order is ignored, since independent passes may run in any order) and interns it, so a frame becomes a small record that points at its shape; it adds the depth histogram of each pass to the one of the same pass structure in the same shape; it closes the books on resource access; and it keeps the detail of the frame (the instance of each pass, the copies and uploads between them) only if it is a representative frame of its shape: the first frame of the shape, then the lightest and the heaviest by draw count if those are others.

  • Resource access (ResourceAccessTracker): for each resource, its first read and first and last write, and in how many frames it was read, written and loop carried (read before it was written in the frame, and written in it: what feedback effects do). It is classed loop carried, unused, unread, static (made once and read afterwards) or frame local. This tells what a replay must carry from one frame to the next.
  • Camera constants are tracked only when the front end gave them a meaning; the camera ones are recorded as a time series per pass structure, a sample only when the value changes.
  • The timeline (built when a query asks): frames in time order as runs of one shape, how often each shape and pass occurs, and the setup frames, which are much longer than a typical frame.

Dependencies between frames

The model says what the passes of a frame are, not how frames depend on each other, which a stereo replay needs: a frame played once per eye reads what the frame before it left in the resources, and that is not the same for both eyes if the frame before rendered it. The dependencies are made apart, by a pass of their own over the workload, and kept in a .deps file.

The model builder tells every use of a resource to a sink (IAccessSink): what it is used as, whether it is read, written or both, how much of it a write reaches, which part, on which queue. The front ends only translate their calls into these events, so a front end for another API makes the dependencies without the analysis knowing it. From them the DependencyAnalyzer says, for each resource and frame, whether the frame uses what an earlier frame left in it: certainly, possibly (only part was written first, or how much is not known), or not at all. It can only over-report what is carried, never under-report it.

  • Per-eye textures. A resource needs a copy for each eye when it is rendered to and some frame uses what an earlier frame left in it, whether that frame writes it too or not. RecipeBake --deps puts them in the recipe. Targets that frames write by turns (a double buffer, a swap chain's images) are a rotation group and are listed together, so an eye never finds what another eye's frame rendered.
  • Dead frames. A frame is dead for a seek if nothing the target frame or any later frame reads comes of it. The replay uses this to leave out most of the work when it jumps to a frame (Replay).

The files, and the same analysis live

The model, the summary and the reference to the workload make an AnalysisResult, which PassesFile writes. Each section is serialized in its own thread and compressed with Zstandard; its header carries the size, the tag, the version and an XXH64 of the raw bytes. The file is written beside the real one and takes its place when complete, so a failure leaves the old file as it was. A reader skips sections it does not know and refuses a known section of another version, and checks what a file this code wrote must satisfy (sizes that fit, resource IDs consecutive, structures in order); one that fails is refused. The sections are listed in passes_format.h. A .passes file remembers which workload it is of (its size and hashes of 4 KiB from its start, middle and end), and the query tools refuse the wrong capture.

The converter inside a program runs the same AnalysisSession, fed by CallFeeder with the calls as they are made, built without history: no frame records, no representative detail, no camera series. What it keeps grows only with the kinds of frames, passes and draws. It needs two things the running program provides: the draw signature of each draw, as it is issued, to match against the recipe, and the shape key of each frame, when the present is made, to ease toward the scene's convergence distance.

What it does not do

  • Only Direct3D 8 and Direct3D 7 have a front end. Calls of an API that has none are counted and skipped; a capture of an OpenGL program gives an empty model.
  • Unsupported calls (state blocks, patches, additional swap chains, MultiplyTransform, volume unlocks in Direct3D 8; state blocks, MultiplyTransform, ProcessVertices and GDI contexts of surfaces in Direct3D 7) are not followed; passes and draws made with them are not right, and the summary says how many there were.
  • It never reads pixels: contents appear only as the hash in a resource's description key. Vertices are read, while the file is made, for the surface depth, and only histograms are kept.
  • It does not judge. Scene against interface is for the recipe.
