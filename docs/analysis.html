Analysis

A demo never explains itself. It just makes calls, millions of them. The analysis watches a recording of those calls once and works out what the demo was doing: which draws build the 3D scene, which are text and logos, how far away things are, and which frames lean on which. It lives in src/libs/analysis.

1The problem

Picture a demo at the moment of one frame. It draws a tunnel, a robot, a scrolling line of text and a logo. To the graphics card they are all the same kind of thing: a pile of triangles with a texture. Nothing in the calls says "this is the world" and "this is a sticker on the screen".

For stereo 3D that difference is everything. The world has to be drawn twice, once per eye, with each point shifted by how far away it is. The text has to be drawn once and placed in front of the world. If the converter gets it wrong, the scroller floats inside the tunnel wall.

So the analysis reads the capture once and writes down the facts the answers come from. The recipe keeps the decision in a form the live converter can follow, and the convergence distance of each scene comes out of the depth facts. The analysis itself never judges. Whether a pass is an interface is for the recipe, by rules, or for the person who writes them.

2A long capture, a small demo

A few minutes of a demo is hundreds of thousands of frames and gigabytes of calls. But ask what the demo does and the answer is short: it has a few dozen kinds of frame, built from a few dozen kinds of pass, drawing a few hundred kinds of thing. Frame 4,000 is frame 4,001 with the camera nudged.

The model is built on that. It never grows with the length of the capture, only with the variety of what the program did.

3A call walks in

Follow one call. It comes out of the workload as part of a segment, a block of calls with their data as the dumper cut it. A receptionist, AnalysisSession, looks at which API the call belongs to, counts it, and hands it to the translator for that API. The translator works out what the call means and tells the model builder in plain terms. The model builder never meets a function name.

The session keeps tallies as it goes. Two of them are warnings: unfollowed calls (an object the front end does not know, or arguments it could not read) and unsupported ones (things it does not follow at all). Either means what was found may be wrong, and a good capture has neither. The session also notes whether a call ended a frame, and tells the model builder the call's index and time, so everything that comes out can be traced back to the call that caused it.

4One translator per API

Direct3D 8 says DrawPrimitive. Direct3D 7 says DrawPrimitive too, but on a different object, with different arguments. OpenGL says glBegin, then a hundred glVertex calls, then glEnd, and expects you to remember what state you were in. Three languages for the same job.

The analysis hires one translator per language. A front end follows the state of one API, the way a spectator follows a game, and reports what each call comes to, already resolved: a draw is reported together with the resources it uses, not with the six calls that bound them. It is the only part of the analysis that knows what a function is called or what its arguments mean. Everything downstream speaks one neutral language.

Keeping the API from leaking

The one rule of a good translator is that its accent must not show. The shared vocabulary is chosen so that more than one API can say what it means in it:

  • a binding point says where a resource is bound, in three numbers;
  • a constant location is a range of bytes in a block of one of four kinds: a buffer, loose shader constants, fixed-function state, push constants;
  • a resource has a format class: color, compressed, depth, depth-stencil;
  • shader stages include compute and tessellation;
  • a resolution hazard is a call whose meaning depends on the size of the target in pixels. It says whether the program can be rendered larger without noticing.

The three that exist

Direct3D 8, Direct3D 7 and OpenGL have front ends, in api_dump_analysis/frontends/D3D8, .../D3D7 and .../OpenGL. Their common ground is frontends/shared:

OpenGL, the one with the most to remember

Direct3D hands the front end objects. OpenGL hands it a running commentary and a lot of hidden state: which context is current on this thread, which matrix is being edited, what glPopAttrib is about to undo. So the OpenGL front end is a small team. OpenGLFrontend routes each call, and each handler owns one slice of the state.

Here is what that team follows, one slice at a time.

Contexts, the window, matrices, attributes
  • Contexts. Which context each thread has current, and the state of each (a wglMakeCurrent that failed changes nothing).
  • The window. The screen is not a resource in the workload, so the front end makes one: the window is the default framebuffer, made at the first clear with the size of the viewport by then. A program need not call glViewport: the viewport and the scissor box of a context start as the client area of the window it is first made current to, which the front end takes from the calls that make the window (GLWindowExtents: CreateWindowEx and GetDC).
  • Viewport, scissor, clears. The viewport, the scissor box and test, and the values a clear uses.
  • Attributes. The stack of attributes: glPopAttrib puts back what the program set after the glPushAttrib, as far as the mask says.
  • Matrices. A stack each for the model-view and the projection matrix, and for the texture and color ones (those are only kept right).
  • Model and view. OpenGL has one matrix for model and view together, so the front end tells the model builder the two as they are, each when it changes: MODEL_VIEW_MATRIX and PROJECTION_MATRIX. It does not tell a model from a view.
  • Handedness. A draw is of a right-handed camera: its depth is the distance in front of the eye.
  • The end of a frame. SwapBuffers, which is a GDI32 function.
Draws
  • Immediate mode. One draw for each glBegin and glEnd with vertices in them, of the topology its mode makes.
  • Its state. The pipeline state set when the draw ended: the enabled capabilities, the depth, alpha and blend functions, the masks, the culling and polygon modes and the shade model.
  • Arrays. glDrawArrays and glDrawElements. The dumper stores the part of each array the draw reads.
  • Array buffers. The front end makes a buffer resource of each array and of the indices, once for each different bytes, so the same data is the same resource in any draw or frame, and it keeps the bytes of each.
  • How long the bytes live. The bytes of a piece are kept for the frame it is seen in (each eye of a stereo frame draws it), and kept on if the piece is seen in a second frame, which is reuse across frames.
  • What the key sees. Such a buffer is told apart in the match key by its kind alone (is_application_memory), so a draw is told apart by its layout, topology and state and not by the bytes it reads.
Display lists
  • Kept and replayed. The calls made between glNewList and glEndList are kept in the list, with the data they refer to (the workload they were made in is let go of before the list is called). They are made again at each glCallList, whatever the state is then, and at once too for GL_COMPILE_AND_EXECUTE.
  • Shared and bounded. The lists of the contexts are shared, as wglShareLists makes them. A list that calls itself is stopped at a depth of 64.
  • Eye dependence. Each list is told what it does to what an eye has of its own (GLListEyeDependence), as the table says.

  • Textures. A texture of the program is a resource once its first glTexImage2D gives it a size. The pixels in the call are an upload. What the OpenGL front end does not follow is listed in What it does not do. AnalysisSession routes calls to the three front ends, and adding a fourth is described in Contributing.

5Where one scene ends and the next begins

A frame is not one picture. It is usually several: the demo renders the 3D world into an off-screen image, blurs that into another, and finally lays text over the result on the screen. Each of those steps is a pass, and the analysis cuts the stream of calls into them.

A pass starts with the first draw or clear after the previous pass ended. It ends when what is rendered to changes, when a clear or a viewport change comes after a draw, when a copy reads or writes what the pass renders to (or an upload writes it), or when the frame ends. A buffer written between two draws does not end a pass.

When a pass ends, its pass structure is made: where it renders to and how, the kinds of draws it holds (sorted, each once) and the constants in effect (by what they are, not their values).

A draw is described twice, for two different readers:

  • the draw structure says what the draw is: the keys of its buffers, shaders and textures, its state, vertex layout and topology, with the counts left out;
  • the draw signature says what the draw is at the moment it is issued, which is all a live converter can know.

6Names that survive a restart

Run the same demo twice and nothing about it is the same: the addresses of objects differ, so does the order threads create things in, and so do the times. Yet the analysis writes down identities that a recipe will carry into a later run of the program, and they have to match. So nothing is named by where or when it was made. It is named by what it is.

That name is a key: a 64-bit digest of the values that make the thing what it is, which comes out the same in another run. A hash is the digest of bytes (the contents of a resource, the code of a shader); a key is the identity of a structure, built from values by MatchKeyBuilder, and may contain hashes.

The rule for what is hashed (StableHasher in libs/utils/hashing: integers little-endian, floats by their bits, sizes with what has a variable size) must never change, since keys are written into .passes files and recipes. StableHasher::hash_bytes takes an AVX2 path for big data on a processor that has it, and gives the same digest as the plain one.

The key that matters most

The draw signature key is the one the whole project leans on. The pass a draw belongs to is not known until the pass ends, so the signature uses the unwritten keys of the structure and the targets: it is made as if nothing had been rendered yet.

That is exactly what a live converter can know when the draw is issued. The same code makes the keys offline and in the running program, so a rule baked from a capture matches a draw of the program as it runs.

Two different structures with the same key are possible in principle. They are counted and compared when interned, so a collision does no harm beyond the count.

7How far away is it?

Stereo is, at heart, a question of distance. A point at the screen stays where it is for both eyes; a point far behind it drifts one way; a point close in front drifts the other. So for every draw the analysis asks how deep it is, and keeps the answers in a histogram per pass, from which the recipe's convergence distances come.

The depth of the origin

  • What it is. The translation of the model matrix (the identity if none was set), carried through the view matrix. It is only worked out for a pass with a view matrix and a projection that is not orthographic: an orthographic one (or the identity) has nothing to converge at.
  • Weight. The vertex count, so a large object counts for more than a particle.
  • The picture's width. The x scale of a perspective projection, weighted by vertices, goes into a mean for the pass: how wide the picture is. It lives in the PROJ section of the file, and the comfort of a recipe needs it.

The depth of the surfaces

The origin of a big mesh can be far away, or even behind the camera, while its walls are close: think of a tunnel made of a few polygons around the camera. So the analysis also measures surfaces. For a draw it samples up to 64 of its vertices (GeometrySampler), carries each to camera space, and counts it if it is in front of the near plane and inside the view.

  • Where the positions come from. The Direct3D 8 and Direct3D 7 front ends read the position of each vertex by its FixedFunctionVertexFormat: in model space (the first three floats), or pre-transformed (x and y in pixels, and the reciprocal of the depth). A pre-transformed vertex takes its depth from that reciprocal and is measured against the viewport instead of a projection.
  • Where the bytes come from. Direct3D 8 reads them from the buffers of a draw, and from the memory of the application that a DrawPrimitiveUP or DrawIndexedPrimitiveUP call brings with it. Direct3D 7 reads the vertices that come with its draw calls. Vertex-shader inputs are not read.
  • Offline only. This is done only by the offline analysis, which has the time. The converter inside a program keeps no buffers and reads no vertex.
  • Who measures. DrawMeasurer (api_dump_analysis/draw_measurer.h) measures the depth of the origin and of the surfaces, the width of the picture, whether a draw reaches the edges of the view, and the draw facts (below).
  • What it keeps. Nothing: the model builder says what the draw is made with (the constants, the viewport) and where the results go.

Not everything is in the world

Depth makes sense for a tunnel. It makes no sense for a fade-to-black, a scrolling bar or the dials of a control panel. Those need to be recognized and left alone, or placed by their own rules. The analysis counts, for every kind of draw, what it has seen it do, and the baker turns the counts into lists.

8Many frames, few shapes

When the program presents a frame, the analysis closes the books on it. It ends the open pass, writes down the frame's shape (the sorted numbers of its pass structures; order is ignored, since independent passes may run in any order), and files it. Most of the time the shape already exists, so the frame becomes a few bytes: a pointer to its shape.

On the way, the builder adds the depth histogram of each pass to the one of the same pass structure in the same shape, and closes the books on resource access. Three more things are recorded alongside:

  • Resource access (ResourceAccessTracker). For each resource: its first read and first and last write, and in how many frames it was read, written and loop carried (read before it was written in the frame, and written in it: what feedback effects do). A resource counts as a whole, so a level or a rectangle is the entire resource; that can only over-report loop carried ones. The class tells a replay what it must carry from one frame to the next (table below).
  • Camera constants. Tracked only when the front end gave them a meaning. The camera ones are recorded as a time series per pass structure, a sample only when the value changes.
  • The timeline (built when a query asks). Frames in time order as runs of one shape, how often each shape and pass occurs, and the setup frames, which are much longer than a typical frame.

9What a frame leaves behind

Stereo has a catch. If frame 100 renders into a texture and frame 101 reads it, then playing frame 101 for the left eye is easy. For the right eye, frame 101 must read what the right eye's frame 100 rendered, not the left's. So a stereo replay has to know which frames depend on what the frames before them left in the resources.

The dependencies are made apart from the model, by a pass of their own over the workload, and kept in a .deps file.

How they are worked out

The model builder tells every use of a resource to a sink (IAccessSink): what it is used as, whether it is read, written or both, how much of it a write reaches, which part, on which queue. The front ends only translate their calls into these events, so a front end for another API makes the dependencies without the analysis knowing it.

From them the DependencyAnalyzer says, for each resource and frame, whether the frame uses what an earlier frame left in it: certainly, possibly (only part was written first, or how much is not known), or not at all. It can only over-report what is carried, never under-report it.

The rectangles and the inputs

For a resource whose writes all say where they land (a copy and an upload tell the rectangle of the level they reach), the file also keeps the rectangle each frame wrote (written_rectangle_vec of each version) and the one that holds all of them (written_extent).

For such a resource it also keeps, for each version, the resources whose content before the frame flows into it through the calls of the frame, in the order they are made in (input_resource_vec). A draw that samples a texture after the copy to the resource has no part in the version. One that samples it before does, in which case the version says nothing and its writer is taken to need all that it uses. APIDumpDependencyQuery resource prints both.

What it is used for

  • Per-eye textures. A resource needs a copy for each eye when it is rendered to and some frame uses what an earlier frame left in it, whether that frame writes it too or not. RecipeBake --deps puts them in the recipe. Targets that frames write by turns (a double buffer the program makes itself) are a rotation group and are listed together, so an eye never finds what another eye's frame rendered.
  • Swap chain images. They are left out of the list: the player keeps what a frame carries over in the back buffer apart for each eye, by its pixels.
  • Dead frames. A frame is dead for a seek if nothing the target frame or any later frame reads comes of it. The replay uses this to leave out most of the work when it jumps to a frame (Replay).

10The life of a texture

Textures are where a demo hides its content. Some are loaded with pixels, some are painted by the demo itself (a copy of the window into a texture is how a mirror or a blur gets made), some are filled in by the driver. The analysis keeps a diary of each level of each texture: what happened to it, when, and what it looked like after. That diary is the .textures file.

The front end of an API tells the model builder each event (ITextureSink), with the call and the frame it is in, and TextureCollector keeps them in the order of the calls. A region's x, y, width and height are in texels, whatever the format; a region of a compressed texture starts on a block and ends on one or at the edge of the level.

The four kinds of event

  • Upload. The pixels of a call are the content of a region. They are in the workload already, so the file keeps no copy: the table of contents has the data chunk, with the size and two hashes of the bytes, and a reader that takes the chunk from the workload can tell that it is the one. A null pointer gives the level a size and no content (see below).
  • Render write. A copy from the window. The window (the swapchain) is never stored.
  • Generated levels. glGenerateMipmap and GL_GENERATE_MIPMAP make the levels below the first, each told as an event, and to the dependencies as a copy of the level above.
  • Snapshot. The first time that something reads a level whose content is not in the workload (rendering made it, or the driver did) after it changed, its content at that call is to be kept: a snapshot point. A change of such a level, by a copy, a part laid over it or the making of levels, makes it be read again the next time it is read.

Uploads without pixels, and snapshots

  • A null pointer. An upload with a null pointer gives the level a size and no content. The dumper makes a data chunk of every pointer to pixels, and of a null pointer one that has no bytes, so a chunk with no bytes is that (a texture that is to be copied to, such as one of 1024 by 512 texels).
  • What a snapshot covers. The smallest rectangle that holds what rendering has made of the level since it was given (a level that is given a size and no pixels, then filled in a part by copies, is snapshot in that part, not whole), and the whole level for the levels that the driver makes.
  • What is not kept. The analysis only says where the points are; the content of rendered levels is not kept. APIDumpTextureExtractor --include-render-content ends with a message instead of writing a file that lacks it (APIDumpTextureQuery info shows includes_render_content, which is false).

Formats and blobs

The formats are named in the words of no API (Utils::Graphics::TextureFormat, with the block, the bytes and whether it is compressed, has depth or stencil, or is sRGB). The front end of each API turns its own values into them, and keeps the value of the API beside a format it does not know. What a stored content is made of is kept in the file of blobs, the name of the .textures file with .data after it: each content a Zstandard frame with a checksum, after a filter that loses nothing, once for each content.

Who tells

Only the OpenGL front end tells the textures. The Direct3D ones send no texture events, so their .textures files are empty of events.

  • What it follows. GL_TEXTURE_2D textures: their levels, the pixels given to them (with the rows laid out as glPixelStorei says), the parts of levels, what is copied to them, and the levels the driver makes. The textures it does not follow are listed in What it does not do.
  • The texture handler. GLTextureHandler (frontends/OpenGL/gl_texture_handler.h) follows the calls about textures and keeps the textures and their parameters.
  • Copies of the window. The front end keeps the window, so it makes the copies of the window to a texture, with the parts of the handler that make a level.

11The files, the tools, and the live twin

Reading a capture takes minutes, so the analysis does it once and writes the result down. Three small programs read a workload and write a file; three more answer questions about a file; and the baker turns the files into a recipe. The same analysis also runs, in a trimmed form, inside the running program.

The files

The model, the summary and the reference to the workload make an AnalysisResult, which PassesFile writes.

  • Sections. Each section is serialized in its own thread and compressed with Zstandard; its header carries the size, the tag, the version and an XXH64 of the raw bytes. The sections of .passes are listed in passes_format.h.
  • Safe to write. The file is written beside the real one and takes its place when complete, so a failure leaves the old file as it was.
  • Safe to read. A reader skips sections it does not know and refuses a known section of another version. It also checks what a file this code wrote must satisfy (sizes that fit, resource IDs consecutive, structures in order); one that fails is refused.
  • One container. SectionedFile (sectioned_file.h) packs and reads the sections of .passes, .deps and .textures, and writes the file beside the real one.
  • Which capture. Each file remembers which workload it is of (its size and hashes of 4 KiB from its start, middle and end), and the query tools refuse the wrong capture.

How the extractors and the queries behave

The three extractors share one flow (ExtractorProgramRunner::run): read the arguments, read the workload with an AnalysisSession while the progress is printed, say once if the workload ends in the middle of a segment, then do the program's own step with what the session found.

  • Options: -o, --max-frames, --progress-interval, --stats and --threads, and --skip-chunks-above, which the texture extractor refuses, since the pixels it needs are in the data chunks.
  • Exit codes: 0 done, 1 bad arguments, 2 workload cannot be read, 3 output cannot be written, 4 (the texture extractor only) what the workload holds of the textures could not all be kept.
  • The warning about a cut workload, and the is_truncated that .passes and .deps keep and info shows, are about the file ending early: a run that stops at --max-frames before the end is not truncated.

The three query programs share one flow too (QueryProgramRunner::run): read the file, check it against the workload it names, ask, print JSON.

  • Options: --compact, --limit (default 100, 0 is all) and --offset. --no-verify skips the check against the workload, and --workload says where the workload is; a workload that cannot be found is not an error.
  • Exit codes: 0 done, 1 bad arguments, 2 file cannot be read, 3 nothing there by that id, 4 wrong workload.

The same analysis, inside the program

The converter inside a program runs the same AnalysisSession, fed by LiveCallAnalyzer with the calls as they are made, but built without history: no frame records, no representative detail, no camera series. What it keeps grows only with the kinds of frames, passes and draws.

It needs two things the running program provides: the draw signature of each draw, as it is issued, to match against the recipe, and the shape key of each frame, when the present is made, to ease toward the scene's convergence distance.

12What it does not do

An analysis that quietly guesses is worse than one that stops. So when the front end meets something it does not follow, the rule is: either it was left out on purpose, with a reason written down, or the process ends with a message that names the function. The one thing it does not do is pass over a call it was never told about.

Direct3D 8 and Direct3D 7

Both follow every function except those below, and neither passes over a call. Each function falls in one of three groups, decided in D3D8FunctionPolicy and D3D7FunctionPolicy:

  • Followed. The front end handles it by name.
  • Left out on purpose, with a reason written beside it: the queries, the hints about where the driver keeps a resource, the state that only changes how a draw looks (materials, clip planes), the display-only calls (gamma, the cursor), and the locks, whose data is stored with the unlock.
  • Ends the process with a message that says the function and why (AI_ASSERT_ALWAYS). These are the functions below.

The functions that end the process:

  • Both: state blocks, MultiplyTransform, ProcessVertices (and ProcessVerticesStrided in Direct3D 7), palettes.
  • Direct3D 8 also: patches, additional swap chains, GetFrontBuffer, RegisterSoftwareDevice, volume unlocks and the vertex and pixel shader constants (which can be the matrices that a replay for the other eye has to change).
  • Direct3D 7 also: overlays, GDI contexts of surfaces, color keys, DeleteAttachedSurface, BltBatch, FlipToGDISurface, SetSurfaceDesc, and the calls that restore surfaces or try or change the display mode.

A call that failed changed nothing and is passed over. The tests keep the list of the functions that are followed against the two tables, so a function that nobody decided on is found.

Everywhere

The analysis never reads pixels: contents appear only as the hash in a resource's description key. Vertices are read, while the file is made, for the surface depth and the draw facts (a sample of each draw), and only histograms and the extents of draws are kept.
