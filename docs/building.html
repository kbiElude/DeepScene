Building & testing

CMake, MSVC, C++14. Two builds (32-bit and 64-bit) are needed because the injected parts are 32-bit and the presenter and the player 64-bit.

Get the code

git clone --recurse-submodules <this repository>

Two submodules are in deps/: APIInterceptor, which has submodules of its own (Detours, googletest, Zstd, Dear ImGui), and OpenXR-SDK. A clone without --recurse-submodules needs git submodule update --init --recursive.

Build

build.bat                    :: incremental, x86 + x64, outputs in build_final\
build.bat --from-scratch     :: wipe, configure, build
build.bat --debug            :: Debug instead of Release

build.bat is a line which runs the script of API Interceptor, deps\APIInterceptor\build.bat, on this project (--source-dir): the two build trees and the release are made here. The OpenXR loader is built statically in the 64-bit build only.

Of API Interceptor only what a program of this project needs is built (its libraries and hooks), and the tools which capture a program, which a release has. Its tests are built when the tests of this project are. The options are set in the root CMakeLists.txt before the submodule is added.

The collected build

build_final\ is what a release is, so that it can be zipped as it is and unpacked anywhere. build.bat empties it at the start of its collecting step, and then installs both build trees into it (cmake --install with --prefix build_final, once for build_x86 and once for build_x64):

  • at the root, VRPlayer.exe;
  • runtime\: the programs it starts, StereoPresenter_x64.exe, and StereoLauncher and StereoConverterDLL of both architectures;
  • apps\, with the catalog, the recipes and the applications;
  • tools\api_dumper\: what captures a program, the dumper and its DLL of both architectures and the printer (from API Interceptor);
  • tools\analysis\: the extractors and the query tools of the analysis (of the passes and of the dependencies), the slicer, and the baker of the recipes;
  • tools\stereo_replay\: the replay player, the replay engine and the consistency checker, of both architectures.

Every program but VRPlayer has the architecture it is built for in the name of its file, _x64 or _x86 (StereoLauncher_x64.exe, RecipeBake_x64.exe), in a build folder as in the release (cmake/Architecture.cmake sets it); the ones of API Interceptor get it as they are installed. A program looks for the ones it starts or loads next to itself (the launcher for the converter), which is why a group is installed as a whole. VRPlayer looks for the launchers and the presenter in runtime\ beside itself, and next to itself when there is none (a build folder). What goes where, and under which name, is written in cmake/Install.cmake, as an install rule for each program, with the helpers of API Interceptor (InstallHelpers.cmake). Only the programs named there are installed, so a program that is not a target any more cannot end up in build_final, and a program that is missing makes the install fail instead of leaving a hole.

The files that the programs read are in one place, apps/ of the repository: the catalog apps.json and the recipes in apps/recipes/. The install copies both to build_final\apps\, where VRPlayer looks first; run from the build tree, it finds apps\ of the repository. The applications themselves are not part of either: each is downloaded into apps\<id>\ the first time it is launched, so the folder of VRPlayer has to be one which can be written to (nothing is written anywhere else, and if it cannot be written, the window says so).

Source layout

The source tree is the release. A program has a folder in the folder its file is in, named after the file in snake_case, without the prefix its group gives: src/vr_player for VRPlayer.exe, src/runtime/launcher for runtime\StereoLauncher_*.exe, src/tools/analysis/recipe_bake for tools\analysis\RecipeBake_x64.exe, and src/tools/stereo_replay/player for tools\stereo_replay\StereoReplayPlayer*.exe. All folders of the source are lower-case with underscores. The libraries are in src/libs, five of them (utils, which the others use, analysis, stereo, headset and vr_player), each a folder of parts (src/libs/analysis/recipe); a part is a namespace of its library, in PascalCase (Analysis::Recipe). Headers are beside the sources they belong to; there is no include/ folder. The tests are in src/tests. docs/components.html has the table of what is where and what each project is for.

An include names a library from src/libs (#include "stereo/core/stereo_core.h"), or a program from src when a program takes a header of another (#include "tools/stereo_replay/engine_dll/types.h"); what a program includes of its own folder is named as it is (#include "command_line.h"). The headers of API Interceptor are found through its libraries, with the same rule (#include "Capture/APIDumpLoader/api_info.h"). A test, Layout, fails if a program that cmake/Install.cmake installs has no folder of its name (as above) where it is installed, or if the folder of a program is not installed.

CMake layout

The root CMakeLists.txt holds the settings every project shares, adds API Interceptor as a subproject (add_subdirectory with EXCLUDE_FROM_ALL), adds the third-party code which the libraries use (miniz, and the OpenXR loader in the 64-bit build), and then adds a folder for each library and for each program, in this order: the libraries, the programs, and the 64-bit ones. Each of those folders has a CMakeLists.txt of its own, with what the project is for, its sources (globbed with CONFIGURE_DEPENDS, so a new file is picked up by the next build) and what it links. Before the libraries the root includes cmake/Architecture.cmake, which has the function that gives a program the architecture in its name; after the programs it includes three more files of cmake/: Tests.cmake, Install.cmake (what the release holds) and Folders.cmake (the folders of the solution). The order matters: a target must exist before it is given a folder.

Solution layout

The generated Visual Studio solution groups projects in folders which are the folders of the source: libs, runtime, tools/analysis, tools/stereo_replay, vr_player and tests, and the folders of API Interceptor and of the third party code.

Tests

One test program, DemoVRPlayerTests, with googletest; it is built with -DDEMOVRPLAYER_BUILD_TESTS=ON, in the 64-bit build and in the 32-bit one (which leaves out the tests of the headset, since the headset is of the 64-bit programs). The data files of the tests (a slice of a capture of fr08, and recipes) are in src/tests/data, and are reached through Tests::DataFixtures. The test support of API Interceptor (APIInterceptorTestSupport) and its googletest are used, which is why API Interceptor builds its tests target (not run, and not part of ALL) when the tests of this project are asked for.

Code conventions

The conventions of API Interceptor apply (see its Building & testing): named namespaces and qualified definitions, no anonymous namespaces, alphabetical members, one return per function, aligned runs of statements.
