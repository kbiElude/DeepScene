Building & testing

CMake, MSVC, C++14. Two builds (32-bit and 64-bit) are needed because the injected parts are 32-bit and the presenter and the player 64-bit.

Get the code

git clone --recurse-submodules <this repository>

Two submodules are in deps/: APIInterceptor, which has submodules of its own (Detours, googletest, Zstd, Dear ImGui), and OpenXR-SDK. A clone without --recurse-submodules needs git submodule update --init --recursive.

Build

build.bat                    :: incremental, x86 + x64, outputs in build_final\
build.bat --from-scratch     :: wipe, configure, build
build.bat --debug            :: Debug instead of Release

build.bat is a line which runs the script of API Interceptor, deps\APIInterceptor\build.bat, on this project (--source-dir): the two build trees and the release are made here. The OpenXR loader is built statically in the 64-bit build only.

Of API Interceptor only what a program of this project needs is built (its libraries and hooks), and the tools which capture a program, which a release has. Its tests are built when the tests of this project are. The options are set in the root CMakeLists.txt before the submodule is added.

The collected build

build_final\ is what a release is, so that it can be zipped as it is and unpacked anywhere. build.bat empties it at the start of its collecting step, and then installs both build trees into it (cmake --install with --prefix build_final, once for build_x86 and once for build_x64):

  • at the root, VRPlayer.exe;
  • runtime\: the programs it starts, StereoPresenter.exe, and StereoLauncher and StereoConverterDLL of both architectures;
  • apps\, with the catalog, the recipes and the applications;
  • tools\APIDumper\: what captures a program, the dumper and its DLL of both architectures and the printer (from API Interceptor);
  • tools\Analysis\: the extractor and the query tool of the analysis, and the baker of the recipes;
  • tools\Replay\: the replay player, the replay engine and the consistency checker, of both architectures.

Where a program has both architectures, the 64-bit one has the suffix _x64 and the 32-bit one _x86. A program looks for the ones it starts or loads next to itself (the launcher for the converter), which is why a group is installed as a whole. VRPlayer looks for the launchers and the presenter in runtime\ beside itself, and next to itself when there is none (a build folder). What goes where, and under which name, is written in cmake/Install.cmake, as an install rule for each program, with the helpers of API Interceptor (InstallHelpers.cmake). Only the programs named there are installed, so a program that is not a target any more cannot end up in build_final, and a program that is missing makes the install fail instead of leaving a hole.

The files that the programs read are in one place, apps/ of the repository: the catalog apps.json and the recipes in apps/recipes/. The install copies both to build_final\apps\, where VRPlayer looks first; run from the build tree, it finds apps\ of the repository. The applications themselves are not part of either: each is downloaded into apps\<id>\ the first time it is launched, so the folder of VRPlayer has to be one which can be written to (nothing is written anywhere else, and if it cannot be written, the window says so).

Source layout

Public headers are in include/ and sources in src/; both have the same groups, and a module is include/<Group>/<Module> and src/<Group>/<Module>. An include names the group: #include "Stereo/Core/stereo_core.h". The namespaces follow the same path. Under Stereo, the name of the target (and of the file it makes) is the path of the module without the slashes: Stereo/Replay/Player is StereoReplayPlayer. The headers of API Interceptor are found through its libraries, with the same rule (#include "Analysis/RecipeLoader/recipe_loader.h").

CMake layout

The root CMakeLists.txt holds the settings every project shares and adds API Interceptor as a subproject (add_subdirectory with EXCLUDE_FROM_ALL), then includes one file per group from cmake/, in this order: Analysis.cmake (the analysis, the recipes and their tools), Replay.cmake (the replay engine, the player and the checker), Stereo.cmake (the converter, the transport and the launcher), VR.cmake (the window of the tools, the player, the catalog, the devices, the headset and the presenter), Tests.cmake, Install.cmake (what the release holds) and Folders.cmake (the folders of the solution). The order matters: the files share variables, and a target must exist before it is given a folder.

Solution layout

The generated Visual Studio solution groups projects in folders: Analysis (Libraries, Tools), Stereo (Libraries, Programs, Replay), VR Player, Tests, and the folders of API Interceptor and of the third party code. File lists are globbed with CONFIGURE_DEPENDS, so a new file is picked up by the next build.

Tests

One test program, DemoVRPlayerTests, with googletest; it is built with -DDEMOVRPLAYER_BUILD_TESTS=ON (64-bit only). The data files of the tests (a slice of a capture of fr08, and recipes) are reached through Tests::DataFixtures. The test support of API Interceptor (APIInterceptorTestSupport) and its googletest are used, which is why API Interceptor builds its tests target (not run, and not part of ALL) when the tests of this project are asked for. The 32-bit build has no tests.

Code conventions

The conventions of API Interceptor apply (see its Building & testing): named namespaces and qualified definitions, no anonymous namespaces, alphabetical members, one return per function, aligned runs of statements.
