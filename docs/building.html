Building & testing

CMake, MSVC, C++14. Two builds (32-bit and 64-bit) are needed because the injected parts are 32-bit and the presenter and the player 64-bit.

Get the code

git clone --recurse-submodules <this repository>

Three submodules are in deps/:

SubmoduleWhat it is
APIInterceptorHas submodules of its own: Detours, googletest, Zstd, Dear ImGui.
OpenXR-SDKThe OpenXR loader and headers.
minizZip reading, used for the downloads.

A clone without --recurse-submodules needs git submodule update --init --recursive.

Build

build.bat                    :: incremental, x86 + x64, outputs in build_final\
build.bat --from-scratch     :: wipe, configure, build
build.bat --debug            :: Debug instead of Release
build.bat --clean            :: wipe the two build trees, build nothing
CommandEffect
build.batIncremental build of both trees; the result is collected in build_final\.
build.bat --from-scratchEmpties the trees, configures, builds.
build.bat --debugDebug instead of Release.
build.bat --cleanEmpties the two build trees and builds nothing.
--source-dir <dir>Builds the CMake project in that folder (the root build.bat passes its own folder); the build trees and build_final\ are made there.

What the script does

TopicDetail
Scriptbuild.bat is a line which runs the script of API Interceptor, deps\APIInterceptor\build.bat, on this project (--source-dir): the two build trees and the release are made here.
OpenXRThe OpenXR loader is built statically in the 64-bit build only. The OpenXR SDK asks for CMake 3.16 at least.
GeneratorVisual Studio 2026 (Visual Studio 18 2026, set in that script), so the CMake has to know it.
Build treesbuild_x86 and build_x64 in the repository root.
ConfiguringAn incremental run configures a tree only if it has no CMakeCache.txt, so an option given to CMake by hand stays. --from-scratch and --clean empty the trees, and the options are gone with the caches.
API InterceptorOnly what a program of this project needs is built (its libraries and hooks), and the tools which capture a program, which a release has. Its tests are built when the tests of this project are. The options are set in the root CMakeLists.txt before the submodule is added.

The collected build

build_final\ is what a release is, so that it can be zipped as it is and unpacked anywhere. build.bat empties it at the start of its collecting step, and then installs both build trees into it (cmake --install with --prefix build_final, once for build_x86 and once for build_x64).

What is in it

File names and where programs look

TopicRule
NamesEvery program but VRPlayer has the architecture it is built for in the name of its file, _x64 or _x86 (StereoLauncher_x64.exe, RecipeBake_x64.exe), in a build folder as in the release (cmake/architecture.cmake sets it). The ones of API Interceptor get it as they are installed.
NeighboursA program looks for the ones it starts or loads next to itself (the launcher for the converter), which is why a group is installed as a whole.
VRPlayerLooks for the launchers and the presenter in runtime\ beside itself, and next to itself when there is none (a build folder).
What goes whereWritten in cmake/install.cmake, as an install rule for each program, with the helpers of API Interceptor (install_helpers.cmake).
Only named programsA program that has no target cannot end up in build_final, and a program that is missing makes the install fail instead of leaving a hole.

The catalog and the applications

The files that the programs read are in one place, apps/ of the repository: the catalog apps.json and the recipes in apps/recipes/. The install copies both to build_final\apps\.

TopicDetail
Where VRPlayer looks for apps.jsonNext to itself, then in an apps\ next to itself, then in the apps\ of the folder above.
From a build folder(build_x64\bin\Release) none of those is the one of the repository, so it is given with --catalog apps\apps.json.
32-bit programsThe 32-bit launcher and converter are in the other build tree, so the programs of the catalog (all 32-bit) are played from build_final.
The applicationsThey are part of neither tree: each is downloaded into apps\<id>\ the first time it is launched, so the folder of VRPlayer has to be one which can be written to (nothing is written anywhere else, and if it cannot be written, the window says so).

CMake layout

The root CMakeLists.txt does these things, in this order:

  1. Holds the settings every project shares.
  2. Adds API Interceptor as a subproject (add_subdirectory with EXCLUDE_FROM_ALL).
  3. Adds the third-party code which the libraries use (miniz, and the OpenXR loader in the 64-bit build).
  4. Includes cmake/architecture.cmake, which has the function that gives a program the architecture in its name.
  5. Adds a folder for each library, then for each program, then the 64-bit ones.
  6. Includes three more files of cmake/: tests.cmake, install.cmake (what the release holds) and folders.cmake (the folders of the solution).

The order matters: a target must exist before it is given a folder. Each library and program folder has a CMakeLists.txt of its own, with what the project is for, its sources (globbed with CONFIGURE_DEPENDS, so a new file is picked up by the next build) and what it links.

Solution layout

The generated Visual Studio solution groups projects in folders which are the folders of the source: libs, runtime, tools/analysis, tools/stereo_replay, vr_player and tests, and the folders of API Interceptor and of the third party code.

Tests

One test program, DemoVRPlayerTests, with googletest. It is built when a tree is configured with -DDEMOVRPLAYER_BUILD_TESTS=ON, in the 64-bit build and in the 32-bit one (which leaves out the tests of the headset, since the headset is of the 64-bit programs). build.bat does not set the option; a tree that is not wiped keeps it.

Build and run

cmake -B build_x64 -DDEMOVRPLAYER_BUILD_TESTS=ON .
cmake -B build_x86 -DDEMOVRPLAYER_BUILD_TESTS=ON .
build.bat
build_x64\bin\Release\DemoVRPlayerTests.exe
build_x86\bin\Release\DemoVRPlayerTests.exe

A part of the tests can be run with googletest's own switch, --gtest_filter=DuplicateCode.*.

Code conventions

The conventions of API Interceptor apply (see its Building & testing):

  • named namespaces and qualified definitions;
  • no anonymous namespaces and no using directives (in src/libs, src/runtime, src/tools and src/vr_player; tests excepted);
  • alphabetical members;
  • one return per function;
  • aligned runs of statements.
