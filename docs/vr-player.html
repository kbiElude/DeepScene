VR player

The front end: pick a program from the catalog, pick an output, choose the depth and the image quality, press Launch.

The first launch

A program of the catalog which is not on the computer yet is marked so, with the size of what is downloaded. Launch starts the download (the zip file, from the addresses of the catalog, one after the other until one works), and the window shows the progress, with a button to cancel. The file is checked against the hash of the catalog and unpacked into apps\<id>\ beside VRPlayer.exe, and the program then starts by itself. The next launches start it at once. If something goes wrong (the network, a file which is not the expected one, a folder which cannot be written to, a virus scanner which removes the program), a window says what, and nothing is left half done.

Pieces

Controls

ControlWhat it does
DeviceThe output: a headset found through OpenXR, or the preview window alone.
DepthReduced, Natural or More: a strength that scales the eye separation of each scene. The comfort limit of the recipe is a ceiling that no choice passes. It can be changed while the program runs.
Image qualityFull renders at the native resolution of the headset (from OpenXR), with the proportions of the program; Half and A quarter of the pixels are for a graphics card that cannot keep up. Set when the program starts; no effect without a headset.

Three things have no control: the 2D overlays are pushed toward the viewer by the amount the recipe gives (comfort.overlay_parallax) for a program whose recipe has one, the program is paced to the headset, and no log is written unless VR Player is started with --log. The pacing and the log are options of the programs that VR Player starts (--no-pacing, --log).

The distance between the eyes of the person is read from OpenXR while the program runs, and its ratio to 64 mm (limited to 0.7 to 1.4) scales the separation, so a narrow or wide IPD is followed without a control.

Headset path

  1. The presenter maps the frame channel and the uploader opens its memory as a D3D12 heap (at the allocation base of the mapped view; a pointer inside the view does not work) and places a cross-adapter buffer over it.
  2. A thread of the headset sink takes the newest frame from the channel about every millisecond, so that nothing which waits for the screen of the PC (a window that is drawn once a refresh) sets its pace.
  3. The images of a swap chain hold whatever was in the memory when it is made, which flickers (a stroboscope effect while the application loads). So the session makes the swap chains of the recommended eye size as soon as it runs, every image is cleared to black on the GPU (D3D12TextureClearer of Utils), and black is shown from the start; if the frames of the application are of another size the swap chains are made again, and cleared again, so that no image is ever shown that nothing was written to.
  4. For each new frame, each eye is copied from the buffer (a source box per eye, footprint offset = pixel pointer minus base) into the eye's OpenXR swapchain image.
  5. The screen is a world-locked quad, or a cylinder if the runtime supports XR_KHR_composition_layer_cylinder, two metres away and sized to fill about 92% of the shared field of view. One layer per eye with eyeVisibility.
  6. A recenter action puts the screen in front of the viewer again.

Code map

HeadsetSession keeps its state in a private Impl (headset_session_impl.h) and is implemented in four files: headset_session.cpp (interface, logging), headset_session_setup.cpp (runtime, device, session, spaces, swap chain format, recenter action), headset_session_swapchains.cpp (the images of the eyes) and headset_session_frame.cpp (events and the frames of the compositor, the screen layers).

The window and AppSession (which starts the launcher and the presenter) are the program, in src/vr_player. What does not draw is the library libs/vr_player (target VRPlayerBackend), in the namespace VRPlayer as the program is: AppCatalog reads the catalog, and AppInstaller installs a program that is not there yet, with the download, the hash and the unpacking of Utils::Files. The window itself is a UIHost of libs/utils, which the presenter and the replay player use too. The headset is libs/headset.

Devices

The device dropdown is filled by OpenXrVrDeviceProvider. With no OpenXR runtime or headset it shows only 2D preview only and is disabled; Launch still works.

Windows: the active OpenXR runtime must be set in the vendor's software (for a Quest, Meta Quest Link). If the registry names a runtime that is not installed, the loader finds none and the presenter logs “The headset is not used” and keeps showing frames in the window.

Logs

With --log on StereoLauncher, or on VRPlayer (which passes it on to both programs), a session writes %TEMP%\apistereo_<session>.log; without it, only what stops the application or the headset is written. Lines ending in “(presenter)” come from the headset path. Each second it has three lines of timings, in milliseconds, as count, mean, worst and how many were late: Pacing (the converter: the presents of the program, the frames passed on, what the copies cost, the wait for the screen), Frames to the headset (the presenter: when the frames arrive, taking the images, the copy to them, how far into a frame the images are ready, the delay of the pace) and Frames of the compositor (the frames of the headset, and how many showed new images, repeated ones or none). They tell where a stutter comes from.
