Recipes

A recipe is the one file that says how to turn one program into stereo: which draws are the scene, which are flat, and the numbers that go with them. Everything that needs to know about a program reads its recipe; nothing at play time reads the capture.

What a recipe holds

A recipe is JSON, in two kinds of parts. A person (often with an LLM reading the analysis) writes the decisions; RecipeBake adds the measurements in a section called baked and never touches the rest.

The numbers in the right-hand column are what Stereo explains: the convergence distance, the ceiling of the separation, and the pushing of the interface. Two version numbers guard the file: key_scheme_version must equal that of the build that reads it (or the keys would not match anything), and the baked signature_scheme_version the same for signatures. The loader refuses a recipe of another scheme instead of guessing.

Baking: from what is known offline to what is known live

An offline replay knows more than a converter inside a running program. The replay knows the pass a draw belongs to; the converter, when the draw is issued, does not, since the pass is not over yet. A converter can only match a draw by its signature and the view matrix. The baker bridges the two.

RecipeBake also checks a recipe without writing anything: --check lists the frame shapes and draw signatures of a capture that the recipe does not know (exit code 5), and a pass left alone whose vertices are at many depths, which is a 3D scene seen from one place and not an overlay (exit code 6). --overlays prints the draws that may be 2D overlays, by the recipe and by the hint of the analysis, and where the two disagree.

How one is made

The steps are captured in Adding an app: capture, extract, investigate the analysis (an LLM reading the query tool's JSON is good at this), draft the rules, bake, check offline with the replay tools, try live. The recipes that ship are in apps/recipes.

The format

RecipeLoader checks everything that needs no program: names, numbers and keys are valid, and no unknown field is left. The keys and the baked section do not depend on the API. The rules section does: a rule names the call it applies to (and the state of that call) in the terms of its API. A rule can name IDirect3DDevice8::SetTransform or IDirect3DDevice7::SetTransform today (the table is in recipe_loader_rules.cpp); the example is Direct3D 8, and a recipe for another API would name that API's calls.

  {
    "recipe_version": 0,
    "key_scheme_version": 1,                       must equal this build's, or the keys would not match
    "target": { "name": "fr08", "description": "text for people" },                                     (optional)
    "known_shape_keys": [ "0x0123456789abcdef" ],  the frame shapes the recipe was made for              (optional)
    "on_unknown_frame": "mono",                    for a frame not in known_shape_keys: mono (default), skip or fail
    "comfort": {                                    how much the eyes can be asked to do; without it, no scene has a limit
      "max_near_parallax": 0.03,                   how far apart the pictures of the eyes may be at the nearest surface of a
                                                   scene, as a part of the width of the picture (above 0, up to 1)
      "near_fraction": 0.001,                      which part of the surfaces of a scene (by vertices) is its nearest: the
                                                   nearest thousandth (above 0, below 1; default 0.001)
      "overlay_parallax": 0.04                     how far toward the viewer the draws that are left alone (unaffected) can be pushed, if
                                                   they are made to what is presented: the two pictures of them are that far apart,
                                                   as a part of the width of the picture (0 to 0.5). What the application wants: VR Player
                                                   pushes by it unless the person turns it off; 0 or left out: the application wants none.
                                                   Draws of pre-transformed vertices are pushed the same way (every x moved by half the
                                                   amount, in pixels, the other way for each eye), unless they cover the whole view
    },
    "screen_parallax": {                           for an application whose vertices are already in the space of the picture (pre-transformed:
                                                   Direct3D's x and y in pixels, and the reciprocal of the depth), which no matrix moves;
                                                   without it, such vertices are left as they are
      "convergence_distance": 5.0,                 the distance at which the eyes converge, in the units of the camera of the application; what
                                                   is at it is not moved. For a scene which the analysis found nothing in; the others converge at
                                                   the distance that RecipeBake baked (scene_convergence), and are no further apart than its limit
                                                   (scene_max_separation: from comfort and the nearest surfaces). Above 0; it must be said
      "field_of_view_degrees": 90.0                the angle of view of the width of the picture (above 0, below 180; default 90): there is no
                                                   projection to read it from
    },
    "unaffected": {                                draws which the rules leave alone (a 2D overlay): all others are affected
      "pass_keys": [ "0x..." ],                    every draw of these passes
      "draw_keys": [ "0x..." ],                    these draws, wherever they are
      "pass_draws": [ { "pass_key": "0x...", "draw_key": "0x..." } ]   this draw in this pass only: a draw structure is often in several passes (a scene and
                                                   the pass that draws over it), and a converter that plays the application as it runs does not know the
                                                   passes, so it cannot tell this from the draw
    },
    "affected": { "draw_keys": [ "0x..." ] },      draws which are affected inside an unaffected pass (a draw in a pass beats a draw key, which beats a pass key)
    "baked": {                                     made from the lists above by RecipeBake; do not edit
      "signature_scheme_version": 1,               must equal this build's, or the signatures would not match
      "known_signatures": [ "0x..." ],             the signatures the analysis saw; a draw of another is one the recipe knows nothing of
      "covering_draws": [ "0x..." ],        the keys (signature and size) of the draws that cover the whole of the view (a flash, a
                                                   fade): found by the analysis, and not pushed toward the viewer, since moving them would
                                                   leave a strip bare
      "per_eye_textures": [                        the textures that are rendered to and that a frame uses what an earlier frame left in (see the dependencies; RecipeBake --deps), which
        { "description_key": "0x...", "ordinal": 1 }   each eye has a copy of: told by the key of how the texture was made and by the number
      ],                                           of the textures made like it before it, so that a replay knows when the application makes it
      "scene_convergence": [                       the distance at which the eyes converge in a kind of frame (a scene), by the shape
        { "shape": "0x...", "distance": 12.5 }     key of its frames; the converter follows the frame before, and uses the distance
      ],                                           of the draw (below) for a shape that is not listed
      "scene_max_separation": [                    how far apart the eyes may be in a scene, in the units of the camera,
        { "shape": "0x...", "separation": 0.5 }    by the shape key of its frames: baked from comfort and the nearest surfaces
      ],                                           of the scene; a scene that is not listed has no limit
      "convergence": [                             the distance at which the eyes converge, for the draws of a signature
        { "signature": "0x...", "distance": 12.5 } measured from how deep the passes that draw it are; in the units of the camera
      ],
      "draw_rules": [                              what a draw is, by what is known when it is issued; tried in order, and a
        {                                          draw which none applies to is affected
          "signature": "0x...",
          "class": "unaffected",                   affected, skipped or unaffected
          "when": {                                                                                      (optional)
            "constant": "view_matrix",             the only constant known so far
            "equals_any": [ [ 16 numbers ] ]       the rule applies while the constant has one of these values
          }
        }
      ]
    },
    "skipped": {                                   draws which are not played, in either eye (the calls which set their state are)
      "pass_keys": [ "0x..." ],                    every draw of these passes
      "draw_keys": [ "0x..." ],                    these draws, wherever they are
      "pass_draws": [ { "pass_key": "0x...", "draw_key": "0x..." } ]   this draw in this pass only (what the overlay probe leaves out)
    },
    (pass_keys and pass_draws are for the replay, which knows the pass of a draw. A converter that plays the application as it runs does
     not, and leaves them out: it writes a warning to its log for each such list.)
    "rules": [
      {
        "name": "scene camera",                                                                     (optional)
        "call": "IDirect3DDevice8::SetTransform",
        "when": {                                                                                      (optional)
          "state": "D3DTS_VIEW",                   a D3DTS_* name (D3DTRANSFORMSTATE_* for Direct3D 7), or a number
          "matrix": "perspective",                 any (default), perspective or orthographic
          "pass_keys": [ "0x..." ],                the call is in one of these pass structures
          "shape_keys": [ "0x..." ]                the frame is one of these shapes
        },
        "action": {
          "type": "multiply",                      multiply, replace, eye_offset or eye_convergence
          "order": "post",                         post (M * X) or pre (X * M); multiply and eye_offset only
          "left":  [ 16 numbers, row by row ],     X for the left eye                  (multiply and replace)
          "right": [ 16 numbers, row by row ]      X for the right eye                 (multiply and replace)
        }
        for eye_offset, X is a translation along "axis" ("x", "y" or "z") by half of the eye separation, which is a setting of
        the replay (a command-line option, the depth choice), not a part of the recipe:
        "action": {
          "type": "eye_offset",
          "order": "post",
          "axis": "x"
        }
        eye_convergence takes nothing: for a rule about the perspective projection (D3DTS_PROJECTION), the projection of each eye is
        sheared so that what is at the convergence distance is at the same place in both eyes (it
        seems to be at the screen). The distance of a draw is the one the baked section has for its signature (measured, see
        "convergence" above), unless the replay sets one for all; with neither, the rule changes nothing. The rule for the view has
        to be eye_offset.
        "action": {
          "type": "eye_convergence"
        }
      }
    ]
  }

Keys are the strings APIDumpAnalysisQuery prints.
