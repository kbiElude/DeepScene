Build and test

CMake, MSVC, C++14, two builds: 32-bit for what is injected into a program, 64-bit for the rest. build.bat makes both and collects a release in build_final\; the tests are built in both. Close VRPlayer before running it, since it empties build_final\ (which also removes the downloaded applications). The details, the layout of the release and the CMake files are in Building & testing.

Where things go

Put code where its dependencies say it belongs. Something with no knowledge of the rest (files, JSON, windows, hashes) goes into utils; something that knows what a draw is goes into analysis or stereo; something that knows an API's calls goes into an API's folder (frontends/D3D8, converter_dll/D3D7). A program's own folder holds only what that program does. The table of every project and its purpose is the Components.

Pitfalls

  • Folder names. Never name a folder common, capture, interception or replay. API Interceptor has folders of those names on the include path, and since the disk is case-insensitive, "common/types.h" from here can resolve to the wrong one with an error that points nowhere. What the front ends of the analysis share is in shared for this reason.
  • Build the result before you commit. Both builds and both test programs: a header that is missing in one architecture only is a common failure (the headset is 64-bit only, windows.h is needed where a constant of it is used).
  • Direct and indirect includes. A header is included by the file that uses a name from it; after a file is split, each part includes what it uses, not what the old file happened to pull in.
  • The 32-bit side. Code that runs in the injected converter cannot use what the 64-bit side has (the headset, D3D12). Keep the two separated by the frame channel, and keep what both need in utils or stereo.

Adding an application

A program is supported when it has a recipe: a file that says which draws are the 3D scene, which are an interface and where the eyes should converge. The work is: capture it, analyse it, decide with evidence what each pass is, write and bake the recipe, check it, and add it to the catalog. Adding an application has every step, the commands and a prompt that works for the part an LLM does well. Background: Analysis (what the tools tell you), Recipes (what a recipe holds and how it is baked), Replay (how to check it without the headset).

Adding an API

An API is added in layers, each of which can be finished and tested before the next. The layers are in the order they are needed; the stereo maths, the recipe format, the frame channel, the presenter and the VR player do not change, which is the point of the design (see Architecture).

  1. Capture. The program's calls must reach a workload file: hooks for the API's entry points and the description of its functions and structures. That is API Interceptor's work, described in its own docs; the Direct3D 7 hooks there are a worked example.
  2. A front end for the analysis. A class in frontends/<api> that follows the state of the API and reports through the events of the front end contract. For an API with a fixed-function pipeline, derive from FixedFunctionFrontend in frontends/shared, which already follows the objects and the fixed-function state; what you write is what a resource is in your API, how its roles are told, and what the draw calls mean. Anything the shared vocabulary cannot say is a hint to extend it in an API-neutral way, not to put the API's words in the model. Register the front end in AnalysisSession, and test it on a captured slice (the Direct3D 7 tests use a call builder and a harness over it, d3d7_call_builder.h and d3d7_frontend_harness.h). From here the extractor, the query tools, the recipe rules and the baker work for the API.
  3. Replay. The replay engine runs the calls of a workload and has them executed for each eye through the executor interfaces of tools/stereo_replay/engine_dll (IEyeExecutor and the ones beside it). The API's executor is a folder there, as D3D7/ is. The consistency checker is how it is verified: the images of the converted replay must equal the images of the original in the modes that must be equal (see Replay).
  4. A live adapter. In runtime/converter_dll/<api>: an eye renderer (draw what the program draws for the second eye, with the decisions of StereoCore), a windowed mode (have the program render to something that is not shown, at the size of the headset's image), and an exporter (pass the finished frame to the frame channel). Converter holds the adapters and gives each call to the one of its API. Anything the adapter cannot follow it must refuse at once and say so, not render something wrong (Decisions and adapters).
  5. The edges. Add the API to the table of What is supported, and its limits to the pages whose limits it changes. Check that the layout test still passes with the new folders, and that both builds and both test programs are green.
The order matters for effort as well: after step 2 you can already read a program of the new API, decide what its passes are and write recipes; after step 3 you can check them with no headset. Do not start the live adapter before the replay shows the recipes are right.
