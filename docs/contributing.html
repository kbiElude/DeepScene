Build and test

The project is built twice, 32-bit and 64-bit, by build.bat; see Building & testing for that, the tests and the release.

Close VRPlayer before running build.bat: it empties build_final\, and the downloaded applications go with it.

Conventions and what checks them

Most rules are checked by review; a few are checked by a test or by CMake. The tables group them by what they are about.

The duplicate-code test

  • One line of src/tests/data/known_duplicates.txt is one group of files: the number of runs they share, and the files.
  • The list is for the real exceptions (such as the Direct3D 7 and 8 sides of API Interceptor, which mirror each other), and not a way to keep a copy.

The conventions of API Interceptor, which this project follows, are in its Building & testing.

Pitfalls

PitfallWhy, and what to do
Folder namesNever name a folder common, capture, interception or replay. API Interceptor has folders of those names on the include path, and since the disk is case-insensitive, "common/types.h" from here can resolve to the wrong one with an error that points nowhere. What the front ends of the analysis share is in shared for this reason.
Build the result before you commitBoth builds and both test programs: a header that is missing in one architecture only is a common failure (the headset is 64-bit only, windows.h is needed where a constant of it is used).
Direct and indirect includesA header is included by the file that uses a name from it; after a file is split, each part includes what it uses, not what the old file happened to pull in.
The 32-bit sideCode that runs in the injected converter cannot use what the 64-bit side has (the headset, D3D12). Keep the two separated by the frame channel, and keep what both need in utils or stereo.

Adding an API

An API is added in layers, each of which can be finished and tested before the next. The layers are in the order they are needed; the stereo maths, the recipe format, the frame channel, the presenter and the VR player do not change, which is the point of the design (see Architecture).

1. Capture

The program's calls must reach a workload file: hooks for the API's entry points and the description of its functions and structures. That is API Interceptor's work, described in its own docs; the Direct3D 7 and 8 hooks there are worked examples.

2. A front end for the analysis

A class in frontends/<api> (of libs/analysis/api_dump_analysis) that follows the state of the API and reports through the events of the front end contract.

If the APIThen
has a fixed-function pipelineDerive from FixedFunctionFrontendBase in frontends/shared, which already follows the objects and the fixed-function state (the Direct3D 7 and 8 front ends do).
does not use the shared fixed-function front endDerive from IAPIFrontend directly and use the other helpers of shared (ObjectTracker, GeometrySampler, MipChain), as the OpenGL front end does.
  • What you write is what a resource is in your API, how its roles are told, and what the draw calls mean.
  • Anything the shared vocabulary cannot say is a hint to extend it in an API-neutral way, not to put the API's words in the model.
  • Register the front end in AnalysisSession.
  • Test it on a captured slice. The Direct3D 7 tests use a call builder and a harness over it (d3d7_call_builder.h and d3d7_frontend_harness.h); the OpenGL ones have gl_call_builder.h and gl_frontend_fixture.h.

From here the extractor, the query tools, the recipe rules and the baker work for the API.

3. Replay

The replay engine runs the calls of a workload and has them executed for each eye through the executor interfaces of tools/stereo_replay/engine_dll (IEyeExecutor and the ones beside it).

  • The API has an executor of its own there (stereo_d3d7_call_executor.h, stereo_gl_call_executor.h), and what only it needs is in a folder of its name (D3D7/).
  • The consistency checker is how it is verified: the images of the converted replay must equal the images of the original in the modes that must be equal (see Replay).

4. A live adapter

In runtime/converter_dll/<api>, three parts:

PartWhat it does
Eye rendererDraws what the program draws for the second eye, with the decisions of StereoCore.
Off-screen renderingA way to have the program render to something that is not shown, at the size of the headset's image (a windowed mode for Direct3D, the eye targets and the scaler for OpenGL).
ExporterPasses the finished frame to the frame channel.

LiveStereoConverter holds the adapters and gives each call to the one of its API. Anything the adapter cannot follow it must refuse at once and say so, not render something wrong (Decisions and adapters).

5. The edges

Add the API to the table of What is supported, and its limits to the pages whose limits it changes. Check that both builds and both test programs are green.

The order matters for effort as well: after step 2 you can read a program of the new API, decide what its passes are and write recipes; after step 3 you can check them with no headset. Do not start the live adapter before the replay shows the recipes are right.
