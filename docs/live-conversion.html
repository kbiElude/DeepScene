Live conversion

The converter lives inside the program it converts. It watches each call, decides how a draw is treated, renders the second eye, and hands both images to another process. This page is about its structure and the three things that are not obvious: the split between decisions and adapters, the resolution, and the pacing.

Inside the program

Decisions and adapters

The converter is made of an adapter, which knows the API of the application, and of decisions that do not. StereoCore, ConvergenceModel, MatrixSlots, the frame channel, the presenter and the VR player have no API in them: an adapter tells StereoCore what the application does (it sets a matrix, it draws) and does what it answers.

PieceJob
ConverterRegisters the callbacks and orders the work of each call: feed the analysis, keep matrices, classify and render draws, take the settings the VR player changed.
CallFeederGives the analysis each call as a dump would, for Direct3D 7 and 8 alike; keeps the calls that wait for results in per-thread pools.
StereoCoreThe decisions: the class of a draw from the recipe and the view matrix, unknown draws and frames. Owns ConvergenceModel (where the eyes converge and how far apart they are) and MatrixSlots (the matrices a rule is about, and which to put in before a draw).

What a converter can know when a draw is issued is less than a replay knows: the pass is not known yet, so a draw is told by its signature and the view matrix, and a rule about a pass or a frame shape cannot be followed. Where a program needs more than that, the converter fails at once through StereoCore::require_fast_path instead of producing wrong images; the same goes for what an adapter cannot follow (a program that locks a render target, or resets the device).

A frame

  1. The program sets matrices and draws. The hook gives each call to the feeder. A draw is analysed immediately (its signature is needed before it runs); other calls are kept until their results are in.
  2. The core looks the draw up in the recipe. A scene draw is made for each eye with the eye's matrices; an interface draw is made once; a skipped one is not made. The maths of the matrices, the separation and the convergence is on the Stereo page.
  3. At the end of the frame the images go to the frame channel: the GPU copies them to system-memory surfaces the exporter keeps, and a thread of the exporter copies the rows to the channel while the program renders the next frame (two sets of surfaces; the program waits for the thread only when it has the next frame to hand over).

Resolution

A program like fr08 asks for a back buffer of 800 × 600, which is a small picture in a headset. The converter therefore renders it larger, at the resolution of the headset. The presenter asks the OpenXR runtime for the recommended size of the image of an eye (xrEnumerateViewConfigurationViews) and VR Player puts it in the frame channel before the program starts (FrameChannel::set_target_eye_size()). When the program makes its device, the scaler works out the scale from the size the program asked for (ResolutionPolicy::get_fit_scale()): the largest that fits the eye with the program's own proportions, so nothing is stretched. For example, 800 × 600 in an eye of 2064 × 2208 is a scale of 2.58 and a back buffer of 2064 × 1548. The back buffer and every render target are made that many times larger; the scale is never below 1 or above 4, and what is passed on has to fit the channel.

The only setting is Image quality in the VR player: Full (the headset's resolution), Half of the pixels and A quarter of the pixels, which bring the target down by the square root of that in each direction, for a card that is hard pressed. Without a headset nothing is made larger. The analysis must see what the program asked for, not what was scaled, so the scaler restores the original values in the data the feeder sees (CallFeeder::set_chunk_func).

Keeping the frames even

In a headset two things are felt: how late a picture is, and whether the motion is even. A frame that is shown twice with the one after it skipped is judder, and it is felt even when every frame is fast. The converter and the presenter therefore do three things: they get a frame from the program to the headset with as little work on the program's own thread as they can, they make the program produce one frame for each frame of the headset, and they hold the headset's frame for an image that is a few milliseconds late.

The way of a frame

Each frame passes four threads. None waits for the one after it, except that the program waits for the exporter's thread when it has its next frame to hand over.

One frame for each frame of the headset

A program that renders as fast as it can, and a headset that shows frames at a fixed rate, drift against each other: a frame of the program is made that the compositor never takes, or a frame is taken twice. It is felt as judder even when nothing is slow.

With the headset, the presenter therefore tells the program when to make a frame. Each time the compositor asks for one (xrWaitFrame returns) the presenter signals the frame channel (FrameChannel::signal_pace(), a named event). The converter, after the program has presented a frame, waits for that signal (wait_for_pace()) and only then lets the program begin the next one.

  • The delay. The frame is not begun at the signal but a delay after it, so that its images are ready at the right moment. The delay is counted from the signal, not from the moment the program notices it: a frame that has to wait is then not longer by the delay, and one that is late goes on at once. The wait uses a timer fine to a millisecond or less, since a coarser one would be a frame.
  • The right moment. The compositor builds its layers as soon as it asks for a frame, from the images that are ready by then. The presenter measures how far into a frame of the headset each set of images is ready (HeadsetSink::tune_pace()) and moves the delay until it is ready at 0.3 of a frame. The copy takes more than a frame, so this cannot be worked out beforehand.
  • Where it cannot hurt. A program is not made to wait for a presenter that has not signalled for a quarter of a second (a headset that was taken off), nor longer than 100 ms for one signal. The delay and the signal are in the header of the channel.

An image that is a few milliseconds late

The copy of a frame to the headset takes a good part of a frame and varies, so the images are sometimes ready just after the compositor asks. Without help, that frame shows the one before again, and the next shows the new images a frame late: a repeat and a skip for one late copy. The compositor's frame can be ended any time within its period, and it is ended in under a millisecond, so there is room to wait.

The lag of the picture behind what the program did is the work of the four threads plus the margin before the next request: about two frames of the headset. The program's own sound is not delayed, so the picture trails the music by that much. The margin is on purpose; a smaller one gives a shorter lag and more repeats when a copy is late.

  • No preview with the headset. The channel has room for one reader, and the preview's copy of each image costs the same memory bandwidth as the headset's. The window says so; without a headset it previews as before.
  • Pacing can be turned off (--no-pacing on the presenter), to see the difference or for a program whose timing depends on how fast it presents. The VR player always paces.

Direct3D 7

A program of Direct3D 7 whose vertices are in pixels (Kasparov draws only those) is converted by the same pieces with a different renderer. The same CallFeeder follows its calls through the analysis, StereoCore decides each draw from the recipe, and what is done to the vertices is decided by ScreenParallaxPlanner, which the replay uses too, with the bytes moved by Stereo::D3D7::ScreenParallax (see Stereo).

  • The second eye. D3D7SurfaceTwins makes a copy of every surface the program renders to (render targets, depth buffers, its back buffer) as the program makes them. For each draw or clear, D3D7EyeRenderer puts the twins in the device, draws the right eye with the vertices moved one way, puts back what the program set, and draws the left with them moved the other way. The copies the program makes to a surface that has a twin (a clear with Blt) are made to the twin as well. A draw from a vertex buffer is read out of the buffer (locked to be read) and is then a draw of vertices in memory; a strided draw is made for the right eye as it is. What it cannot repeat is counted and told in the log.
  • The window. When another program shows the images, D3D7WindowedMode has the program render to an invisible window: the cooperative level is that of a window, the display mode is not set, the surface that is shown has no chain of buffers, and the back buffer the program gets is a surface of the converter's own, the size of the display mode times the render scale. The hooks cannot change an argument of Direct3D 7 in place, so the call is not made and the converter makes its own and writes the result where the program is to get it. A flip shows nothing. The window is hidden by InvisibleWindows, which also tells the program it is always active, since some programs pause while their window is not.
  • The resolution. The back buffer, its twin and the depth buffer are made as large as the images are shown (the same policy as Direct3D 8; surfaces are capped at 2048 on a side). The viewport, the rectangles of a clear and the positions of the vertices are scaled to match. A program that locks the whole back buffer, writes it and unlocks it (the ending screens of Kasparov) has it stretched to the whole after the unlock and copied to the twin. A lock to read, or of part of the surface, is only counted.
  • The images. The back buffer is read before a flip, or before the blit of the surface the program rendered to onto the primary surface (how a program in a window shows a frame), converted to B, G, R of 8 bits, into the channel, the two eyes side by side. With no program that shows the images, the converter itself holds the program to 60 frames a second, since there is no flip to wait for.

The frame channel

Shared memory between the 32-bit program and the 64-bit presenter, named from the session (Local\APIStereo_<session>). Three image slots: the producer writes one that is neither the newest nor the one being read, so nobody waits. Images start at multiples of 64 KB and rows at multiples of 256 bytes, so the GPU can import the memory as a heap.

The log and the switches

The log is off unless asked for (--log on the launcher and the presenter, which VRPlayer passes on): then %TEMP%\apistereo_<session>.log has statistics each second, as count, mean, worst and how many were late, in milliseconds. Off, only what has to be said is written: why the converter stops the application, a frame that cannot be passed on, a headset that cannot be used.

If the program's presents are even and the repeats are many, the delay is ours; seconds in which the program itself stalls (a scene that loads) show as fewer presents and many repeats, and nothing downstream can show images the program has not made. With --log --wait the launcher reads the last statistics when the application exits and says what the run came to: frames converted, and a line for each thing the converter could not do (draws of a signature the recipe does not know, frames of a scene it has no distance for, surfaces that could not be given a twin, calls not made for the right eye).

A run without the VR player takes its switches from the environment: APISTEREO_EYE_SEPARATION, APISTEREO_DEPTH_STRENGTH (1 is natural, and follows the limit of each scene), APISTEREO_PUSH_OVERLAY, APISTEREO_TARGET_EYE_WIDTH and _HEIGHT (which also have the program render to the invisible window), APISTEREO_DUMP_FRAME and APISTEREO_DUMP_EVERY (a frame, both eyes, to %TEMP%\apistereo_frame_N.bmp), and, to measure, APISTEREO_NO_RIGHT_EYE and APISTEREO_NO_FRAME_LIMIT.

A program that never exits by itself (the demos loop their credits) must be ended by the user or the launcher; a test script that starts one must always clean up.
